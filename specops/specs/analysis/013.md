# Analysis: FareLegJoinRuleValidator

## 1. Purpose

Validates each row of `fare_leg_join_rules.txt` for two independent concerns:

1. **Foreign key integrity for `from_network_id` and `to_network_id`**: Each field, when present, must resolve to a `network_id` in either `networks.txt` OR the `network_id` column of `routes.txt`. This is an OR-join across two parent tables — the field is valid if it appears in either source.

2. **Conditional co-presence of `from_stop_id` / `to_stop_id`**: These two fields are only meaningful as a pair. Supplying one without the other is an error: the missing half must be reported.

The validator does not check whether `from_stop_id` / `to_stop_id` reference valid stops — that FK check is handled separately by the annotation-driven load-time mechanism (both fields carry `@ForeignKey(table = "stops.txt", field = "stop_id")` in the schema).

## 3. Validation logic

### Skip condition

Run if and only if `fareLegJoinRuleTable` is not null (i.e., `fare_leg_join_rules.txt` is present in the feed). The `networks.txt` and `routes.txt` tables may be absent — the validator handles missing parent tables gracefully by finding no matches and emitting FK violation notices.

In Python:

```python
if "fare_leg_join_rules" not in feed or feed["fare_leg_join_rules"].is_empty():
    return []
```

### Per-row checks (applied to each row in `fare_leg_join_rules.txt`)

#### Check A: `from_network_id` foreign key

1. If `from_network_id` is present (non-null, non-empty):
   - Check whether the value appears in `networks.txt.network_id`.
   - If not found there, also check whether the value appears in `routes.txt.network_id`.
   - If found in neither: emit `foreign_key_violation` (ERROR).
2. If `from_network_id` is absent: skip this check (field-level absence is covered by required-field load validation).

#### Check B: `to_network_id` foreign key

Same logic as Check A, applied to `to_network_id`.

The two checks are independent. A single row may emit both a `from_network_id` FK violation and a `to_network_id` FK violation simultaneously.

#### Check C: `from_stop_id` / `to_stop_id` co-presence

Applied after the FK checks, independently:

- If `from_stop_id` is present AND `to_stop_id` is absent: emit `missing_required_field` for `to_stop_id`.
- If `to_stop_id` is present AND `from_stop_id` is absent: emit `missing_required_field` for `from_stop_id`.
- If both are present: no notice.
- If neither is present: no notice (both fields are only conditionally required).

### What is NOT checked here

- Whether `from_stop_id` or `to_stop_id` reference a valid stop in `stops.txt` (handled by load-time FK annotation).
- Whether `from_network_id` or `to_network_id` are non-empty when present (handled by required-field load validation).

## 4. Notices emitted

### `foreign_key_violation`

Severity: **ERROR**

Emitted when `from_network_id` or `to_network_id` cannot be resolved in either `networks.txt` or `routes.txt`.

| Field | Type | Description |
|---|---|---|
| `child_filename` | string | `"fare_leg_join_rules.txt"` |
| `child_field_name` | string | `"from_network_id"` or `"to_network_id"` |
| `parent_filename` | string | `"routes.txt or networks.txt"` (literal string, matching Java output) |
| `parent_field_name` | string | `"network_id"` |
| `field_value` | string | The offending ID value |
| `csv_row_number` | int | Row number of the offending record |

Note: The `parent_filename` value is the literal string `"routes.txt or networks.txt"` as produced by Java's string concatenation `GtfsRoute.FILENAME + " or " + GtfsNetwork.FILENAME`. The Python implementation must reproduce this exact string to maintain output compatibility.

### `missing_required_field`

Severity: **ERROR**

Emitted when exactly one of `from_stop_id` / `to_stop_id` is present and the other is absent.

| Field | Type | Description |
|---|---|---|
| `filename` | string | `"fare_leg_join_rules.txt"` |
| `csv_row_number` | int | Row number of the offending record |
| `field_name` | string | `"to_stop_id"` or `"from_stop_id"` (whichever is missing) |

## 5. Edge cases

- **`fare_leg_join_rules.txt` absent or null**: Skip entirely; no notices.
- **`networks.txt` absent**: No network IDs will match the first lookup; validator falls through to the `routes.txt` lookup. If `routes.txt` is also absent, all `from_network_id` / `to_network_id` values emit FK violations.
- **`routes.txt` absent**: Network ID lookup proceeds against `networks.txt` only; `routes.txt` lookup returns empty.
- **Both `networks.txt` and `routes.txt` absent**: Every non-null `from_network_id` and `to_network_id` emits a FK violation.
- **`from_network_id` matches `routes.txt` but not `networks.txt`**: Valid; no FK violation notice (the OR condition is satisfied).
- **`to_network_id` matches `networks.txt` but not `routes.txt`**: Valid; no FK violation notice.
- **Both `from_network_id` and `to_network_id` are invalid FK references**: Two independent FK violation notices emitted for that row.
- **`from_stop_id` present, `to_stop_id` absent**: One `missing_required_field` notice for `to_stop_id`.
- **`to_stop_id` present, `from_stop_id` absent**: One `missing_required_field` notice for `from_stop_id`.
- **Both stop IDs absent**: No notice for either (both conditionally required, pair-presence is not required when neither is supplied).
- **Both stop IDs present**: No notice.
- **A row has both a FK violation and a missing stop ID**: Both notices are emitted independently.
- **Multiple rows with violations**: Each row is evaluated independently; each produces its own notices.
- **Empty string vs. null for `from_network_id` / `to_network_id`**: Java's `hasFromNetworkId()` returns false for both null and the empty-string sentinel. The Python implementation should treat null and empty string as "absent" (skip the FK check); treat non-empty strings as present and subject to FK validation.

## 7. Implementation notes

### Validator type

File-level (cross-table) validator. Consumes `fare_leg_join_rules.txt` (per-row), `networks.txt` (lookup set), and `routes.txt` (lookup set).

### Validator signature

```python
def validate_fare_leg_join_rule(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

### Skip logic

```python
if "fare_leg_join_rules" not in feed or feed["fare_leg_join_rules"].is_empty():
    return []
```

### Polars implementation strategy

The FK checks require set lookups against two parent tables. Build lookup sets once, then use Polars anti-joins or `is_in` expressions for vectorized matching.

Recommended approach:

1. Build `network_ids_set`: union of `networks.txt.network_id` values and `routes.txt.network_id` values (both filtered to non-null).
2. For each of `from_network_id` and `to_network_id`:
   - Filter `fare_leg_join_rules` to rows where the field is non-null and non-empty AND the value is NOT in `network_ids_set`.
   - Iterate over the filtered (violation) rows to emit one `foreign_key_violation` notice per row.
3. For the stop ID co-presence check:
   - Filter to rows where `from_stop_id` is non-null/non-empty AND `to_stop_id` is null/empty → emit `missing_required_field` for `to_stop_id`.
   - Filter to rows where `to_stop_id` is non-null/non-empty AND `from_stop_id` is null/empty → emit `missing_required_field` for `from_stop_id`.

Avoid nested Python loops over large DataFrames. All filters should be Polars expressions.

### Notice codes (Python)

| Java notice class | Python notice code |
|---|---|
| `ForeignKeyViolationNotice` | `foreign_key_violation` |
| `MissingRequiredFieldNotice` | `missing_required_field` |

Both notice types are generic and shared across multiple validators. The `foreign_key_violation` dataclass and `missing_required_field` dataclass should already be defined in `notices.py`.

### `parent_filename` string for FK notice

The Java code constructs `parentFilename` as:

```java
GtfsRoute.FILENAME + " or " + GtfsNetwork.FILENAME
```

Which evaluates to `"routes.txt or networks.txt"`. This exact string must appear as `parent_filename` in the Python notice to preserve output wire format.

### OR-lookup for network ID resolution

The lookup must check both parent tables before concluding the FK is violated. In Polars, collect both sets of valid IDs into a Python `set` (or a Polars Series) before running `is_in`:

```python
valid_network_ids = set()
if "networks" in feed:
    valid_network_ids |= set(feed["networks"]["network_id"].drop_nulls().to_list())
if "routes" in feed:
    valid_network_ids |= set(
        feed["routes"]["network_id"].drop_nulls().filter(
            feed["routes"]["network_id"].is_not_null()
        ).to_list()
    )
```

Or equivalently using Polars `is_in` with a combined Series.

### Relationship to load-time FK validation

The `from_stop_id` and `to_stop_id` fields carry `@ForeignKey(table = "stops.txt", field = "stop_id")` annotations. Their resolution against `stops.txt` is handled at load time by `load_validators.py`. This validator only checks co-presence of the two stop ID fields.

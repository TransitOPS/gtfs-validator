# Analysis: FeedValidTodayValidator

## 1. Purpose

Checks whether the feed covers today's date by comparing the minimum `feed_start_date` in `feed_info.txt` against the current validation date. If the earliest start date is strictly in the future, the feed is flagged as covering only the future.

## 2. Input tables

| Table | Columns used |
|---|---|
| `feed_info.txt` | `feed_start_date` |

### Schema reference

`feed_info.txt` (`GtfsFeedInfoSchema`, Python: `FEED_INFO`):

| Column | Type | Constraint |
|---|---|---|
| `feed_publisher_name` | string | Required |
| `feed_publisher_url` | URL (string) | Required |
| `feed_lang` | language code | Required |
| `feed_start_date` | date | Recommended |
| `feed_end_date` | date | Recommended |
| `feed_version` | string | Recommended |
| `feed_contact_email` | email (string) | Optional |
| `feed_contact_url` | URL (string) | Optional |

### External inputs

- **Current date**: Provided via `ValidationContext.date_for_validation` (corresponds to Java `DateForValidation`). This is the date the validation is being run against, typically today's date but overridable via CLI flags.

## 3. Validation logic

### Skip conditions

- If `feed_info.txt` is absent or empty, no rows are processed and no notices are emitted.
- If no row has a non-null `feed_start_date`, no notice is emitted (there is nothing to compare).

### Algorithm

1. Iterate over all rows in `feed_info.txt`.
2. Find the **minimum** `feed_start_date` among rows that have a non-null `feed_start_date`.
3. If no row has a non-null `feed_start_date`, return with no notices.
4. Compare the minimum `feed_start_date` against the current date:
   - If `min_feed_start_date > current_date`: emit `future_feed` notice.
   - If `min_feed_start_date <= current_date`: no notice.

### Pseudocode

```
current_date = ctx.date_for_validation

# Collect all non-null feed_start_date values
start_dates = [row.feed_start_date for row in feed_info if row.feed_start_date is not null]

if start_dates is empty:
    return []

min_start = min(start_dates)

if min_start > current_date:
    emit future_feed(
        feed_start_date=min_start,
        current_date=current_date,
    )
```

### What is NOT checked here

- Whether `feed_start_date` is a valid date (handled at load time).
- Whether both `feed_start_date` and `feed_end_date` are present together (handled by `FeedServiceDateValidator`).
- Whether the feed has expired (handled by `FeedExpirationDateValidator`).
- Whether `feed_start_date <= feed_end_date` (handled by load-time end-range check).

## 4. Notices emitted

### `future_feed`

Severity: **INFO**

Emitted when the minimum `feed_start_date` across all `feed_info.txt` rows is strictly greater than the current validation date. This means the feed covers only future service, which may be intentional (e.g., a feed published ahead of a service change) but is worth flagging.

| Field | Type | Description |
|---|---|---|
| `feed_start_date` | date (string, YYYYMMDD) | The minimum `feed_start_date` found across all rows |
| `current_date` | date (string, YYYYMMDD) | The current validation date |

This notice has no `csv_row_number` because it is an aggregate check across all rows, not tied to a specific row.

## 5. Edge cases

- **`feed_info.txt` absent from the feed**: No rows; no notices.
- **`feed_info.txt` empty (header only)**: No rows; no notices.
- **No row has `feed_start_date`**: All values are null; no minimum can be computed; no notice.
- **`feed_start_date` equals current date**: `min_start == current_date` is NOT greater than, so no notice is emitted. The feed is considered valid for today.
- **`feed_start_date` is one day in the future**: Notice is emitted (`min_start > current_date`).
- **`feed_start_date` is in the past**: No notice (feed already covers today or earlier).
- **Multiple rows** (spec violation for single-row table, but possible): The validator takes the minimum across all rows. If any row has a start date on or before today, no notice is emitted.
- **Date values that fail type casting**: By the time this validator runs, invalid date strings are null. If all dates are null due to parse failures, no notice is emitted (same as "no row has feed_start_date").

## 7. Implementation notes

### Validator type

Single-table, aggregate validator. The check aggregates across all rows (finds the minimum start date) then compares against the current date. No joins, no cross-table lookups. Requires access to the current validation date from `ValidationContext`.

### Validator signature

```python
def validate_feed_valid_today(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

### Skip logic

```python
if "feed_info" not in feed or feed["feed_info"].is_empty():
    return []
```

### Polars implementation strategy

`feed_info.txt` is a single-row table, so a simple Polars column min suffices. No iteration needed.

```python
import polars as pl
from gtfs_validator.notices import Notice, Severity
from gtfs_validator.context import ValidationContext

def validate_feed_valid_today(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
    if "feed_info" not in feed or feed["feed_info"].is_empty():
        return []

    df = feed["feed_info"]

    if "feed_start_date" not in df.columns:
        return []

    min_start = df.select(pl.col("feed_start_date").min()).item()

    if min_start is None:
        return []

    current_date = ctx.date_for_validation

    if min_start > current_date:
        return [Notice(
            code="future_feed",
            severity=Severity.INFO,
            fields={
                "feed_start_date": str(min_start),
                "current_date": str(current_date),
            },
        )]

    return []
```

### Notice codes (Python)

| Java notice class | Python notice code | Severity |
|---|---|---|
| `FutureFeedNotice` | `future_feed` | INFO |

### Relationship to other validators

- **`FeedExpirationDateValidator`** (analysis 019): Checks if `feed_end_date` is in the past or expiring soon. Complementary to this validator.
- **`FeedServiceDateValidator`** (analysis 020): Checks that `feed_start_date` and `feed_end_date` are both present or both absent. Independent check.

### Relationship to load-time validation

The following are handled at load time and must not be duplicated here:

- `feed_start_date` type validation (valid date strings).
- `feed_start_date` end-range check relative to `feed_end_date`.
- Single-row enforcement for `feed_info.txt`.

### Python schema reference

The `FEED_INFO` table definition in `src/gtfs_validator/schemas.py` includes `feed_start_date` typed as `_DATE` and marked `_REC` (recommended). After the two-phase load, values are `datetime.date` objects or `null`.

### ValidationContext dependency

This validator requires `ctx.date_for_validation` (a `datetime.date`). The `ValidationContext` class in `src/gtfs_validator/context.py` already provides this field.

# Analysis: MissingStopsFileValidator

## 1. Purpose

Emits an error when neither `stops.txt` nor `locations.geojson` is present in the feed, enforcing the GTFS requirement that at least one of these two files must exist.

## 2. Input tables

| Input | Role |
|---|---|
| `stops.txt` | Checked for presence/absence only; no columns are read. |
| `locations.geojson` | Checked for presence/absence only; no features are read. |

No columns from either file are accessed. The entire check is purely about file presence.

## 3. Validation logic

1. **Check `stops.txt` presence**: Determine whether `stops.txt` was loaded into the feed (i.e., the file existed in the GTFS archive or directory).
2. **Check `locations.geojson` presence**: Determine whether `locations.geojson` was loaded into the feed.
3. **Both absent → notice**: If and only if **both** files are missing, emit one `missing_required_file` notice with `filename = "stops.txt"`.
4. **Either present → no notice**: If at least one of the two files is present (even if empty), the validator is satisfied and emits nothing.

The notice filename is always `"stops.txt"` regardless of which file (or combination) is absent. The Java code hardcodes this string.

## 4. Notices emitted

### `missing_required_file` (ERROR)

A required file is absent from the feed.

| Field | Type | Value |
|---|---|---|
| `filename` | string | `"stops.txt"` (hardcoded) |

Condition: `stops.txt` is absent **AND** `locations.geojson` is absent.

Severity: ERROR.

Exactly one notice is emitted per feed when the condition is met; zero notices otherwise.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| Both `stops.txt` and `locations.geojson` absent | Emit one `missing_required_file` notice with `filename="stops.txt"`. |
| `stops.txt` present (even empty), `locations.geojson` absent | No notice. |
| `stops.txt` absent, `locations.geojson` present (even empty) | No notice. |
| Both present | No notice. |
| `stops.txt` present and `locations.geojson` present | No notice. |
| Feed is otherwise empty (all other files missing too) | Still emits the notice for `stops.txt` — this validator has no dependency on other files. |

The Java `isMissingFile()` check corresponds directly to whether the file was found in the archive. Empty files that were successfully parsed are not missing.

In the Python implementation: "present" means the key exists in the `feed` dict. The orchestrator only populates `feed` keys for files that were actually found and parsed; absent files are simply omitted. Therefore the guard is `"stops" not in feed` and `"locations_geojson" not in feed`.

## 6. Test contracts

### `stopsTxtMissingFileShouldGenerateNotice`

- **Setup**: `stops.txt` status = MISSING_FILE. `locations.geojson` status = MISSING_FILE.
- **Expected**: Exactly one `MissingRequiredFileNotice` with `filename = "stops.txt"`.

### `stopsTxtMissingFileShouldNotGenerateNotice`

- **Setup**: `stops.txt` status = MISSING_FILE. `locations.geojson` is present (created with an empty entity list — zero features, but the container is considered present/loaded).
- **Expected**: No notices.
- **Key contract**: When `locations.geojson` is present (even with zero features), the absence of `stops.txt` does not produce a notice.

No test covers the case where `stops.txt` is present and `locations.geojson` is absent, but the symmetric logic makes it a required case for the Python implementation.

## 7. Implementation notes

### Approach

This validator requires no Polars operations at all. It is a pure presence check on the feed dict keys.

```python
def validate_missing_stops_file(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
    """Emit an error when neither stops.txt nor locations.geojson is present."""
    stops_present = "stops" in feed
    geojson_present = "locations_geojson" in feed
    if not stops_present and not geojson_present:
        return [
            Notice(
                code="missing_required_file",
                severity=Severity.ERROR,
                fields={"filename": "stops.txt"},
            )
        ]
    return []
```

### Notice code reuse

The `missing_required_file` notice code with `filename` field is already used in the Python codebase — see `src/gtfs_validator/validators/missing_feed_info.py` (which emits it when `feed_info.txt` is absent and `translations.txt` is present) and `src/gtfs_validator/loading.py`. No new notice type is needed.

### Feed dict key names

- `stops.txt` → `"stops"` key in `feed`
- `locations.geojson` → `"locations_geojson"` key in `feed` (matches existing validator convention in `src/gtfs_validator/validators/__init__.py`)

### Relationship to other validators

- `MissingFeedInfoValidator` (Python: `missing_feed_info.py`) uses the same `missing_required_file` notice code for a different file. The pattern is identical.
- The `loading.py` module also emits `missing_required_file` for other required files during schema-driven loading. Confirm that `stops.txt` is not already handled there — if it is emitted by `loading.py` for all required files unconditionally, this validator's role is specifically the conditional exemption when `locations.geojson` is present.
- If `loading.py` already emits `missing_required_file` for `stops.txt` whenever it is absent, this validator's primary function is to **suppress** that notice by being the single authoritative check that accounts for the GeoJSON alternative. Verify the current `loading.py` behavior before implementing to avoid double-emitting the notice.

### Validator registration

Register in `src/gtfs_validator/validators/__init__.py` with `requires=[]` (no tables required — the validator runs regardless of what is present). The guard logic inside the function handles the presence checks.

Alternatively, since the validator must run even when the files are absent, the `requires` list must not include either `"stops"` or `"locations_geojson"` — the runner's `should_skip` logic would otherwise prevent execution when both are absent, defeating the purpose.

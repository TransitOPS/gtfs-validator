# Analysis: TimeframeOverlapValidator

## 1. Purpose

Checks that no two entries in `timeframes.txt` sharing the same
`timeframe_group_id` and `service_id` have overlapping time intervals.

## 2. Input tables

| Table | Columns used |
|---|---|
| `timeframes.txt` | `timeframe_group_id`, `service_id`, `start_time`, `end_time`, `csv_row_number` |

### Column semantics

- `timeframe_group_id` — string ID; groups timeframe entries that belong to
  the same logical timeframe. Together with `service_id` it forms the grouping
  key for overlap detection.
- `service_id` — required string; identifies the calendar service for which
  this timeframe applies. Part of the grouping key.
- `start_time` — conditionally required `GtfsTime`; the inclusive start of the
  time interval. Per the schema (`@EndRange(field = "end_time", allowEqual =
  false)`), `start_time` must be strictly less than `end_time`; this is
  enforced at load time, not by this validator.
- `end_time` — conditionally required `GtfsTime`; the exclusive end of the
  time interval.
- `csv_row_number` — integer; used to identify which rows are involved in a
  violation.

## 3. Validation logic

### Step 1 — Guard: timeframes.txt absent or empty

If `timeframes.txt` is absent from the feed or contains zero rows, there is
nothing to check. Return immediately with no notices.

### Step 2 — Group rows by (timeframe_group_id, service_id)

Partition all rows of `timeframes.txt` into groups where every row in a group
shares the same `timeframe_group_id` AND the same `service_id`. Groups with
different `timeframe_group_id` or different `service_id` are independent and
are checked separately.

### Step 3 — Sort each group by start_time, then end_time

Within each group, sort the rows in ascending order of `start_time`. Where
`start_time` values are equal, sort by `end_time` ascending (secondary key).

### Step 4 — Scan consecutive pairs for overlap

Iterate sorted rows in each group as consecutive pairs `(prev, curr)`:

```
for i in range(1, len(group)):
    prev = group[i-1]
    curr = group[i]
    if curr.start_time < prev.end_time:
        emit TimeframeOverlapNotice(...)
```

The overlap condition is strictly: `curr.start_time < prev.end_time`.

- If `curr.start_time == prev.end_time` (adjacent intervals), no overlap —
  no notice emitted.
- If `curr.start_time > prev.end_time` (gap between intervals), no overlap —
  no notice emitted.
- If `curr.start_time < prev.end_time` (intervals cross), overlap — emit one
  notice for this pair.

Because the list is sorted by `start_time`, if `curr.start_time >= prev.end_time`
then no later element can overlap with `prev` either. However, the Java
implementation does **not** apply that optimization: it only checks consecutive
pairs, not all pairs. This means that for a group of three entries where entry
A and entry C overlap but A and B do not and B and C do not, no notice would
be emitted. The implementation is pairwise-consecutive, not all-pairs.

### Step 5 — One notice per overlapping consecutive pair

Each overlapping pair `(prev, curr)` produces exactly one notice. All groups
are checked independently.

## 4. Notices emitted

### `timeframe_overlap` (ERROR)

Emitted when two consecutive timeframe entries (after sorting by `start_time`,
then `end_time`) within the same `timeframe_group_id` + `service_id` group
have overlapping time intervals (`curr.start_time < prev.end_time`).

| Field | Type | Source | Description |
|---|---|---|---|
| `prev_csv_row_number` | int | `timeframes.csv_row_number` (first entry) | Row number of the earlier timeframe entry |
| `prev_end_time` | string (HH:MM:SS) | `timeframes.end_time` (first entry) | End time of the earlier timeframe |
| `curr_csv_row_number` | int | `timeframes.csv_row_number` (second entry) | Row number of the later timeframe entry |
| `curr_start_time` | string (HH:MM:SS) | `timeframes.start_time` (second entry) | Start time of the later timeframe |
| `timeframe_group_id` | string | `timeframes.timeframe_group_id` | The shared group ID |
| `service_id` | string | `timeframes.service_id` | The shared service ID |

Severity: ERROR.

Condition: within a group sharing `(timeframe_group_id, service_id)`, after
sorting rows by `(start_time ASC, end_time ASC)`, the `start_time` of the
current row is strictly less than the `end_time` of the previous row.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `timeframes.txt` absent from feed | Return `[]` immediately. |
| `timeframes.txt` present but empty (zero rows) | Return `[]` immediately (no groups to check). |
| Single row per `(timeframe_group_id, service_id)` group | No notice; a single entry cannot overlap with itself. |
| Two rows with `curr.start_time == prev.end_time` (adjacent) | No notice; this is exactly-touching, not overlapping. |
| Two rows with `curr.start_time < prev.end_time` (overlap) | One notice emitted. |
| Two groups with same times but different `timeframe_group_id` | Checked independently; no cross-group comparison. |
| Two groups with same times but different `service_id` | Checked independently; no cross-group comparison. |
| Three rows A, B, C where A and C overlap but neither overlaps B | If after sorting A-B-C are consecutive, and A.end > B.start then A-B notice; if B.end > C.start then B-C notice; A-C is not directly compared. Only adjacent pairs are checked. |
| Null `start_time` or `end_time` | These are conditionally required and the schema's `@EndRange` enforces them at load time. If they are null after loading, `GtfsTime` comparison behavior in Java would likely throw/NPE; in Python treat as a guard: skip rows with null `start_time` or `end_time`. |
| `start_time` values are equal across two rows | Secondary sort by `end_time` determines order; the earlier-ending row becomes `prev`. If `curr.start_time == prev.start_time` and `curr.start_time < prev.end_time` (always true since `start_time < end_time`), a notice is emitted. |

## 6. Test contracts

The Java test file (`TimeframeOverlapValidatorTest.java`) contains six test
methods.

### `testSingleTimeframe`

- One row: `timeframe_group_id="PEAK"`, `service_id="WEEKDAY"`,
  `start_time=00:00:00`, `end_time=24:00:00`, `csv_row_number=2`.
- Expected: no notices.
- Rationale: a single entry in the group cannot overlap with anything.

### `testNoOverlap`

- Two rows, same group and service, non-adjacent:
  - Row 2: `start_time=08:00:00`, `end_time=09:00:00`
  - Row 3: `start_time=17:00:00`, `end_time=18:00:00`
- Expected: no notices.
- Rationale: `17:00:00 >= 09:00:00`, so no overlap.

### `testNoOverlapButAdjacent`

- Two rows, same group and service, touching at `09:00:00`:
  - Row 2: `start_time=08:00:00`, `end_time=09:00:00`
  - Row 3: `start_time=09:00:00`, `end_time=10:00:00`
- Expected: no notices.
- Rationale: `curr.start_time == prev.end_time` — touching but not overlapping.
  The condition `curr.start_time < prev.end_time` is false (equal, not less).

### `testOverlap`

- Two rows, same group and service:
  - Row 2: `start_time=08:00:00`, `end_time=09:00:00`
  - Row 3: `start_time=08:30:00`, `end_time=09:30:00`
- Expected: exactly one `TimeframeOverlapNotice` with:
  - `prev_csv_row_number=2`
  - `prev_end_time=09:00:00`
  - `curr_csv_row_number=3`
  - `curr_start_time=08:30:00`
  - `timeframe_group_id="PEAK"`
  - `service_id="WEEKDAY"`
- Rationale: `08:30:00 < 09:00:00` — clear overlap.

### `testWithDifferentServiceIds`

- Two rows with identical times and `timeframe_group_id="PEAK"` but different
  `service_id` values (`"WEEKDAY"` vs `"WEEKEND"`), `csv_row_numbers` 2 and 3.
- Expected: no notices.
- Rationale: rows are in different groups (different `service_id`); each group
  has only one entry, so no overlap check occurs.

### `testWithDifferentGroupIds`

- Two rows with identical times and `service_id="WEEKDAY"` but different
  `timeframe_group_id` values (`"PEAK"` vs `"NON-PEAK"`), `csv_row_numbers` 2
  and 3.
- Expected: no notices.
- Rationale: rows are in different groups (different `timeframe_group_id`);
  each group has only one entry, so no overlap check occurs.

### What is NOT covered by the Java test suite

- `timeframes.txt` absent from the feed entirely.
- Empty `timeframes.txt`.
- Three or more rows in one group with complex overlap patterns.
- Rows with null `start_time` or `end_time`.
- Two rows where `start_time` values are identical (tie-breaking by `end_time`).
- Multiple overlapping pairs within the same group (multiple notices from one
  group).
- Multiple groups each contributing an overlap notice.

## 7. Implementation notes

### Algorithm strategy

The Java implementation groups rows in memory by `(timeframe_group_id,
service_id)`, sorts each group by `(start_time, end_time)`, then scans
consecutive pairs. This is a classic interval-sweep algorithm.

Per the AGENTS.md guidance: "Use plain Python algorithms for graph/geometry/
interval logic when clearer and safer than forcing Polars." The interval sweep
on a per-group basis fits this description well. The recommended approach is:

1. Use Polars to filter out null `start_time` / `end_time` rows and to extract
   the required columns as Python-native structures.
2. Use plain Python `itertools.groupby` or a `dict`-based grouping to partition
   rows by `(timeframe_group_id, service_id)`.
3. Sort each group with Python's `sorted()`.
4. Scan consecutive pairs with a plain Python loop.

Alternatively, a fully Polars approach using `sort` + `shift` + `filter` on
the grouped DataFrame is possible and may be preferred for consistency.

### Recommended Polars approach

```python
def validate_timeframe_overlap(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "timeframes" not in feed or feed["timeframes"].is_empty():
        return []

    tf = feed["timeframes"].select(
        "timeframe_group_id", "service_id", "start_time", "end_time", "csv_row_number"
    )

    # Drop rows where start_time or end_time are null (load-time guards
    # should already flag these, but be defensive here)
    tf = tf.drop_nulls(subset=["start_time", "end_time"])
    if tf.is_empty():
        return []

    # Sort by group key, then start_time, then end_time
    tf_sorted = tf.sort(
        ["timeframe_group_id", "service_id", "start_time", "end_time"]
    )

    # Use shift to align each row with its predecessor within the same group
    prev_end_time = tf_sorted["end_time"].shift(1)
    prev_csv_row = tf_sorted["csv_row_number"].shift(1)
    prev_group_id = tf_sorted["timeframe_group_id"].shift(1)
    prev_service_id = tf_sorted["service_id"].shift(1)

    tf_pairs = tf_sorted.with_columns([
        prev_end_time.alias("prev_end_time"),
        prev_csv_row.alias("prev_csv_row_number"),
        prev_group_id.alias("prev_timeframe_group_id"),
        prev_service_id.alias("prev_service_id"),
    ])

    # Only compare within the same group (filter out cross-group boundaries)
    # and only where the current start_time < previous end_time
    violations = tf_pairs.filter(
        (pl.col("timeframe_group_id") == pl.col("prev_timeframe_group_id"))
        & (pl.col("service_id") == pl.col("prev_service_id"))
        & (pl.col("start_time") < pl.col("prev_end_time"))
    )

    notices: list[Notice] = []
    for row in violations.iter_rows(named=True):
        notices.append(
            TimeframeOverlapNotice(
                prev_csv_row_number=row["prev_csv_row_number"],
                prev_end_time=row["prev_end_time"],
                curr_csv_row_number=row["csv_row_number"],
                curr_start_time=row["start_time"],
                timeframe_group_id=row["timeframe_group_id"],
                service_id=row["service_id"],
            )
        )
    return notices
```

### Time representation in Polars

GTFS `start_time` and `end_time` are "HH:MM:SS" strings that can exceed
`23:59:59` (e.g. `24:00:00` for service past midnight). Standard Python/Polars
`time` types cannot represent values >= 24:00:00. The existing `schemas.py`
likely stores these as either:

- Plain strings (Utf8), in which case lexicographic comparison is valid only
  for zero-padded equal-length strings.
- Integers (seconds since midnight), which allows direct numeric comparison.

Confirm the column dtype in `schemas.py` before writing comparisons. If stored
as seconds-since-midnight integers, the comparison `curr.start_time <
prev.end_time` is a direct integer comparison. If stored as strings, convert to
seconds for comparison: `HH * 3600 + MM * 60 + SS`.

### Null handling

`start_time` and `end_time` are conditionally required (schema annotation
`@ConditionallyRequired`). The load-time validators should have already flagged
missing values. This validator should defensively drop rows with null
`start_time` or `end_time` rather than crashing on null comparisons.

### Notice dataclass

```python
@dataclass
class TimeframeOverlapNotice:
    code: ClassVar[str] = "timeframe_overlap"
    severity: ClassVar[str] = "ERROR"
    prev_csv_row_number: int
    prev_end_time: str  # or int if stored as seconds
    curr_csv_row_number: int
    curr_start_time: str  # or int if stored as seconds
    timeframe_group_id: str
    service_id: str
```

### Notice code derivation

The Java class is `TimeframeOverlapNotice`. The Python notice code follows
snake_case convention: `"timeframe_overlap"`.

### Feed dict key

- `"timeframes"` — `timeframes.txt`

### Validator registration

Required tables: `["timeframes"]`.

Feature flag: none. The validator self-guards on the presence and size of
`timeframes.txt`.

### Consecutive-pairs-only semantics

The Java implementation compares only adjacent pairs after sorting; it does
NOT compare all `O(n^2)` pairs. The shift-based Polars approach above exactly
replicates this: `shift(1)` aligns each row with its immediately preceding
neighbor after sorting, and the cross-group boundary filter ensures no
comparison spans two different groups. This is behaviorally identical to the
Java loop.

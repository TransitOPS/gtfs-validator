# Analysis: FareTransferRuleDurationLimitTypeValidator

## 1. Purpose

Validates that `duration_limit` and `duration_limit_type` in `fare_transfer_rules.txt` are either both present or both absent. These two fields are mutually dependent: a duration limit is meaningless without knowing how that duration is measured (the type), and a duration limit type is meaningless without an actual duration value. Either field appearing alone is an error.

There are two distinct error conditions:

1. `duration_limit` is set but `duration_limit_type` is absent.
2. `duration_limit_type` is set but `duration_limit` is absent.

Each condition emits its own distinct notice code. The validator processes each row independently with no cross-row state.

## 2. Input tables

| Table | Columns used |
|---|---|
| `fare_transfer_rules.txt` | `duration_limit`, `duration_limit_type`, `csv_row_number` |

|---|---|---|

| `ARRIVAL_TO_ARRIVAL` | 3 | Duration measured from arrival to arrival |

## 3. Validation logic

### Skip condition

None. The validator runs for every row in `fare_transfer_rules.txt`. If the table is absent or empty, no rows are processed and no notices are emitted.

### Algorithm

The validator is a `SingleEntityValidator`, meaning it operates on each row independently. For each row in `fare_transfer_rules.txt`:

1. If `duration_limit` is present AND `duration_limit_type` is absent:
   - Emit `fare_transfer_rule_duration_limit_without_type` with the row's `csv_row_number`.

2. If `duration_limit` is absent AND `duration_limit_type` is present:
   - Emit `fare_transfer_rule_duration_limit_type_without_duration_limit` with the row's `csv_row_number`.

3. If both are present: valid, no notice.

4. If both are absent: valid, no notice.

The two checks are independent conditionals (not mutually exclusive in the logic, but since each checks the opposite presence combination, they cannot both fire for a single row).

### Pseudocode

```
for each row in fare_transfer_rules:
    if row.duration_limit is not null AND row.duration_limit_type is null:
        emit fare_transfer_rule_duration_limit_without_type(csv_row_number=row.csv_row_number)
    if row.duration_limit is null AND row.duration_limit_type is not null:
        emit fare_transfer_rule_duration_limit_type_without_duration_limit(csv_row_number=row.csv_row_number)
```

### What is NOT checked here

- Whether `duration_limit` is a positive integer (schema-level `@Positive` constraint, handled at load time).
- Whether `duration_limit_type` is a valid enum value (enum domain check, handled at load time).
- Whether any other conditionally-required field (`transfer_count`, `fare_product_id`) is present.
- Cross-row or cross-table relationships.

## 4. Notices emitted

### `fare_transfer_rule_duration_limit_without_type`

Severity: **ERROR**

Emitted when a row in `fare_transfer_rules.txt` has `duration_limit` set but `duration_limit_type` is absent.

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending row |

### `fare_transfer_rule_duration_limit_type_without_duration_limit`

Severity: **ERROR**

Emitted when a row in `fare_transfer_rules.txt` has `duration_limit_type` set but `duration_limit` is absent.

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending row |

## 5. Edge cases

- **Both `duration_limit` and `duration_limit_type` present**: No notice. Both fields satisfy the mutual dependency.
- **Both `duration_limit` and `duration_limit_type` absent**: No notice. A row may have no duration constraint at all; that is valid.
- **`duration_limit` present, `duration_limit_type` absent**: `fare_transfer_rule_duration_limit_without_type` emitted.
- **`duration_limit_type` present, `duration_limit` absent**: `fare_transfer_rule_duration_limit_type_without_duration_limit` emitted.
- **`fare_transfer_rules.txt` absent or empty**: No rows; no notices.
- **Multiple rows violating the same condition**: Each violating row emits its own notice independently. Multiple notices of the same code may appear with different `csv_row_number` values.
- **`duration_limit = 0`**: The schema annotates `duration_limit` with `@Positive`, so a value of 0 would be caught at load time as a separate error. From this validator's perspective, a value of 0 would still be treated as "present" (hasDurationLimit() returns true for any set integer field), so the mutual dependency check applies normally. However, such a row would also already have a load-time error.
- **Invalid `duration_limit_type` enum value**: Caught at load time. An invalid enum value leaves `duration_limit_type` unset (hasDurationLimitType() returns false), meaning an invalid type combined with a valid `duration_limit` would trigger `fare_transfer_rule_duration_limit_without_type` from this validator in addition to the load-time enum error.

## 7. Implementation notes

### Validator type

Single-table, row-level validator. No joins or cross-row state required. Each row is checked independently.

### Validator signature

```python
def validate_fare_transfer_rule_duration_limit_type(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

### Skip logic

```python
if "fare_transfer_rules" not in feed or feed["fare_transfer_rules"].is_empty():
    return []
```

### Polars implementation strategy

Both checks are naturally vectorized as column-level filter operations. "Present" means the column value is not null; "absent" means the column value is null.

```python
df = feed["fare_transfer_rules"]
notices: list[Notice] = []

# Check 1: duration_limit present, duration_limit_type absent
has_limit_no_type = df.filter(
    pl.col("duration_limit").is_not_null() & pl.col("duration_limit_type").is_null()
)
for row in has_limit_no_type.iter_rows(named=True):
    notices.append(Notice(
        code="fare_transfer_rule_duration_limit_without_type",
        severity=Severity.ERROR,
        fields={"csv_row_number": row["csv_row_number"]},
    ))

# Check 2: duration_limit_type present, duration_limit absent
has_type_no_limit = df.filter(
    pl.col("duration_limit_type").is_not_null() & pl.col("duration_limit").is_null()
)
for row in has_type_no_limit.iter_rows(named=True):
    notices.append(Notice(
        code="fare_transfer_rule_duration_limit_type_without_duration_limit",
        severity=Severity.ERROR,
        fields={"csv_row_number": row["csv_row_number"]},
    ))

return notices
```

Since violations are expected to be rare, iterating over the small filtered result set with `iter_rows` is acceptable. For very large feeds, both filters run as Polars expressions over the full column, which is efficient.

### Relationship to load-time validation

The following are handled at load time and must not be duplicated here:

- `fare_transfer_type` required and non-null.
- `duration_limit` must be a positive integer when present (`@Positive` constraint).
- `duration_limit_type` must be a valid enum value (0–3) when present.
- `from_leg_group_id` and `to_leg_group_id` FK checks into `fare_leg_rules.leg_group_id`.
- `fare_product_id` FK check into `fare_products.fare_product_id`.
- Composite PK uniqueness for `(from_leg_group_id, to_leg_group_id, fare_product_id, transfer_count, duration_limit)`.

This validator adds only the mutual dependency business rule between `duration_limit` and `duration_limit_type`.

### Null semantics in Python/Polars

In the Java implementation, `hasDurationLimit()` and `hasDurationLimitType()` return false for any field that was not set (i.e., the CSV cell was empty or absent). In Python/Polars, after the two-phase load (raw string → typed cast), a missing or empty cell for an optional integer/enum column is represented as `null`. The `is_null()` / `is_not_null()` Polars predicates map directly to the Java `has*()` methods.

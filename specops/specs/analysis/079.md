# Analysis: TripUsabilityValidator

## 1. Purpose

For every trip in `trips.txt`, validate that it has at least two stop time entries in `stop_times.txt`; trips with zero or one stop time are unusable for passengers because there is no meaningful boarding-and-alighting journey.

---

## 2. Input tables

| Table | Columns used |
|---|---|
| `trips.txt` | `trip_id`, `csv_row_number` (row number for notice context) |
| `stop_times.txt` | `trip_id` (used only to count rows per trip) |

### Column semantics

- `trips.trip_id` — required string; primary key; used to look up associated stop times.
- `stop_times.trip_id` — foreign key back to `trips.trip_id`; used to group and count stop time records per trip.

No other columns from either table are read or compared.

---

## 3. Validation logic

For each trip row in `trips.txt`:

### Step 1: Look up stop times for the trip

```
stop_times_for_trip = stop_times WHERE trip_id == trip.trip_id
count = len(stop_times_for_trip)
```

### Step 2: Check the count threshold

```
if count <= 1:
    emit UnusableTripNotice(csv_row_number=trip.csv_row_number, trip_id=trip.trip_id)
```

The condition is strictly `<= 1`, so:
- 0 stop times → notice emitted (trip has no stops at all).
- 1 stop time → notice emitted (trip visits exactly one stop, which is not a usable journey).
- 2 or more stop times → no notice emitted.

No other checks are performed. The validator does not inspect `stop_sequence`, `stop_id`, departure/arrival times, or any other column beyond counting rows.

---

## 4. Notices emitted

### `unusable_trip` (WARNING)

A trip has fewer than two stop time entries.

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | int | `trips.txt` row number | The 1-based row number of the offending trip record in the CSV file |
| `trip_id` | string | `trips.trip_id` | The ID of the trip that has too few stop times |

Severity: **WARNING**.

Conditions:
- The trip exists in `trips.txt`.
- The count of rows in `stop_times.txt` with a matching `trip_id` is 0 or 1.

---

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `trips.txt` absent or empty | Validator is not invoked (runner guard) or returns `[]` immediately — no trips to iterate over. |
| `stop_times.txt` absent or empty | Every trip has a count of 0 stop times; every trip emits `unusable_trip`. |
| Trip has 0 stop times | Notice emitted (`0 <= 1`). |
| Trip has exactly 1 stop time | Notice emitted (`1 <= 1`). |
| Trip has exactly 2 stop times | No notice emitted (`2 > 1`). |
| Trip has many stop times | No notice emitted. |
| Multiple trips, some with 0/1 stops | Each offending trip emits its own notice independently; valid trips produce no output. |
| `stop_times` rows for a trip have duplicate `stop_sequence` values | The validator only counts rows; duplicates are counted and may suppress a notice even if stop positions are semantically wrong. Deduplication is not performed here. |
| `trip_id` in `stop_times.txt` references a trip not in `trips.txt` | Irrelevant — the validator iterates trips, not stop times. Orphaned stop time rows are silently ignored. |

---

## 6. Test contracts

The Java test file contains two test cases:

### `tripServingMoreThanOneStopShouldNotGenerateNotice`

Setup:
- 2 trips: `t0` (row 1), `t1` (row 3).
- 4 stop times: `t0` has 2 entries (`s0` at sequence 2, `s1` at sequence 3); `t1` has 2 entries (`s3` at sequence 5, `s4` at sequence 9).

Expected: no notices emitted. Both trips have 2 stop times, which is `> 1`.

### `tripServingOneStopShouldGenerateNotice`

Setup:
- 2 trips: `t0` (row 1), `t1` (row 3).
- 3 stop times: `t0` has 1 entry (`s0` at sequence 2); `t1` has 2 entries (`s3` at sequence 5, `s4` at sequence 9).

Expected: exactly one `UnusableTripNotice` for `t0` with `csv_row_number=1` and `trip_id="t0"`. Trip `t1` is valid and emits no notice.

### What is NOT covered by the Java test suite

- `trips.txt` absent or empty.
- `stop_times.txt` absent or empty (trip with 0 stop times).
- Multiple trips all producing notices simultaneously.
- Trips with a very large number of stop times.
- `trip_id` present in `stop_times.txt` but absent from `trips.txt` (orphaned stop times).

---

## 7. Implementation notes

### Algorithm strategy

The validator is a simple grouped-count join. The most natural Polars approach:

1. Count stop times per `trip_id` from `stop_times.txt` using `group_by("trip_id").agg(pl.count().alias("stop_time_count"))`.
2. Left-join `trips` → `stop_time_count` on `trip_id`. Trips with no stop time rows will have a null count after the join.
3. Fill null counts with `0` (a trip with no matching stop times has 0 stop times).
4. Filter to rows where `stop_time_count <= 1`.
5. Iterate the filtered result and emit one `UnusableTripNotice` per row.

This avoids any Python-level loop over the full trip table and is fully vectorized until the final notice-emission step.

### Polars vs plain Python

| Operation | Approach |
|---|---|
| Count stop times per `trip_id` | Polars: `group_by("trip_id").agg(pl.len().alias("stop_time_count"))` |
| Join trips to counts | Polars: left join on `trip_id`, fill null counts with `0` |
| Filter trips with `<= 1` stop time | Polars filter expression: `pl.col("stop_time_count") <= 1` |
| Emit one notice per violating row | Plain Python loop over the small filtered result |

### Guard clauses

```python
def validate_trip_usability(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "trips" not in feed or "stop_times" not in feed:
        return []
    trips = feed["trips"]
    stop_times = feed["stop_times"]
    if trips.is_empty():
        return []
```

When `stop_times` is empty but `trips` is not, do not short-circuit — let the join proceed so that every trip receives a count of 0 and all trips emit notices.

### Notice dataclass

```python
@dataclass
class UnusableTripNotice:
    code: ClassVar[str] = "unusable_trip"
    severity: ClassVar[Severity] = Severity.WARNING
    csv_row_number: int
    trip_id: str
```

### Row number handling

The Java validator passes `trip.csvRowNumber()` directly to the notice. In Polars, the CSV row number must be preserved during loading as an explicit column (e.g., added at load time via `with_row_index` adjusted for the header row, or stored in the schema). The spec for `csv_row_number` follows the same convention used by all other validators in this project: it is 1-based and represents the physical row in the source CSV file (header = row 1, first data row = row 2).

### Required tables for registry

Primary tables: `["trips", "stop_times"]`. Both must be present; if either is absent, return `[]`.

### Behavioral notes

- The check is purely a count: the `stop_sequence` values, times, or stop IDs are not examined. Two stop time rows for the same stop (same `stop_id`, duplicate `stop_sequence`) would satisfy the `>= 2` threshold even though they represent the same location.
- The validator does not cross-check whether `stop_times.stop_id` values resolve to real stops; that is the responsibility of FK validators.
- The validator does not check whether the trip is active on any service date; it operates on raw structural data only.

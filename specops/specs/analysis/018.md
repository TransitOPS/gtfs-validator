# Analysis: FeedContactValidator

## 1. Purpose

Validates that `feed_info.txt` provides at least one of `feed_contact_email` or `feed_contact_url`.

The GTFS Best Practices for `feed_info.txt` recommend that a feed include at least one contact field so that consumers can reach the feed publisher. When both fields are absent or blank, the validator emits a single warning per row (in practice `feed_info.txt` is a single-row table).

The validator has one detection condition:

- Both `feed_contact_email` and `feed_contact_url` are absent or blank: emit `missing_feed_contact_email_and_url`.

Either field being present and non-blank satisfies the check. There is no format validation of the email address or URL beyond the schema-level `@FieldType` constraint applied at load time.

The validator processes each row independently with no cross-row or cross-table state. Because `feed_info.txt` is declared `singleRow = true`, at most one notice will ever be generated in practice.

| Table | Columns used |

`feed_info.txt` (`GtfsFeedInfoSchema`, Python: `FEED_INFO`):

## 3. Validation logic

### Skip condition

If `feed_info.txt` is absent or empty, no rows are processed and no notices are emitted.

### Algorithm

The validator is a `SingleEntityValidator`, meaning it operates on each row independently. For each row in `feed_info.txt`:

**Condition — both contact fields are blank or absent:**

- `feed_contact_email` is absent (null) OR blank (whitespace-only string)
- AND `feed_contact_url` is absent (null) OR blank (whitespace-only string)

If the condition holds: emit `missing_feed_contact_email_and_url` with `csv_row_number`.

Otherwise (at least one contact field is present and non-blank): no notice.

### Pseudocode

```
for each row in feed_info:
    email_missing = row.feed_contact_email is null OR row.feed_contact_email.isBlank()
    url_missing   = row.feed_contact_url   is null OR row.feed_contact_url.isBlank()
    if email_missing AND url_missing:
        emit missing_feed_contact_email_and_url(
            csv_row_number=row.csv_row_number,
        )
```

### What is NOT checked here

- Email address format validation (handled at load time via `@FieldType(FieldTypeEnum.EMAIL)`).
- URL format validation for `feed_contact_url` (handled at load time via `@FieldType(FieldTypeEnum.URL)`).
- Whether `feed_publisher_name`, `feed_publisher_url`, or `feed_lang` are present (required field checks handled at load time).
- Whether `feed_start_date` precedes `feed_end_date` (handled by load-time end-range check).
- Uniqueness or cross-table relationships (not applicable; `feed_info.txt` has no FK columns).

## 4. Notices emitted

### `missing_feed_contact_email_and_url`

Severity: **WARNING**

Emitted when a row in `feed_info.txt` has neither `feed_contact_email` nor `feed_contact_url` set to a non-blank value. The GTFS Best Practices recommend providing at least one contact field.

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending row |

## 5. Edge cases

- **Both fields present and non-blank**: No notice.
- **`feed_contact_email` set, `feed_contact_url` absent (null)**: No notice. One contact field is sufficient.
- **`feed_contact_email` set, `feed_contact_url` blank (`""`)**: No notice. Email alone satisfies the check.
- **`feed_contact_url` set, `feed_contact_email` absent (null)**: No notice.
- **`feed_contact_url` set, `feed_contact_email` blank (`""`)**: No notice. URL alone satisfies the check.
- **Both fields absent (null)**: Emits `missing_feed_contact_email_and_url`.
- **Both fields blank (`""`)**: Emits `missing_feed_contact_email_and_url`.
- **One field null, one field blank**: Emits `missing_feed_contact_email_and_url`. A null field and a blank string are both treated as "missing".
- **Whitespace-only string (e.g., `"   "`)**: The Java implementation uses `isBlank()`, which returns `true` for strings containing only whitespace. A whitespace-only value is treated as absent and triggers the notice if the other field is also absent or blank.
- **`feed_info.txt` absent**: No rows; no notices.
- **`feed_info.txt` empty (header only)**: No rows; no notices.
- **Multiple rows** (spec violation, but theoretically possible before load-time single-row enforcement): Each row is checked independently; each violating row emits its own notice.

## 7. Implementation notes

### Validator type

Single-table, row-level validator. No joins, no cross-row state, no cross-table lookups required. Each row is checked independently.

### Validator signature

```python
def validate_feed_contact(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

### Skip logic

```python
if "feed_info" not in feed or feed["feed_info"].is_empty():
    return []
```

### Polars implementation strategy

The check is a simple row-level predicate on two nullable string columns. Both columns can be null (absent in CSV) or blank (empty/whitespace string). The `isBlank()` Java method maps to checking whether a string is null or contains only whitespace. In Polars, use `is_null()` combined with a strip-and-length check.

```python
df = feed["feed_info"]
notices: list[Notice] = []

def is_blank(col: str) -> pl.Expr:
    return pl.col(col).is_null() | (pl.col(col).str.strip_chars() == "")

violating = df.filter(is_blank("feed_contact_email") & is_blank("feed_contact_url"))

for row in violating.iter_rows(named=True):
    notices.append(Notice(
        code="missing_feed_contact_email_and_url",
        severity=Severity.WARNING,
        fields={"csv_row_number": row["csv_row_number"]},
    ))

return notices
```

Because `feed_info.txt` is a single-row table, `iter_rows` over the violating subset imposes no performance concern.

### Notice codes (Python)

| Java notice class | Python notice code | Severity |
|---|---|---|
| `MissingFeedContactEmailAndUrlNotice` | `missing_feed_contact_email_and_url` | WARNING |

### Null and blank semantics in Python/Polars

The Java implementation uses two distinct checks per field:
- `!entity.hasFeedContactEmail()` — the field was absent or not set (maps to `null` in Polars after two-phase load).
- `entity.feedContactEmail().isBlank()` — the field was set but is empty or whitespace-only.

In Python/Polars, after the two-phase load, absent or empty CSV cells for optional string columns are represented as `null`. A whitespace-only string, if present in the CSV, would be loaded as a non-null Polars string. The `is_blank` helper above handles both cases: a null value is considered blank, and a non-null string that strips to `""` is also considered blank. This faithfully replicates the Java `!hasX() || x().isBlank()` pattern.

### Relationship to load-time validation

The following are handled at load time and must not be duplicated here:

- `feed_publisher_name` required and non-null.
- `feed_publisher_url` required, non-null, and valid URL format.
- `feed_lang` required and a valid BCP-47 language code.
- `feed_contact_email` format validation (valid email address) when present.
- `feed_contact_url` format validation (valid URL) when present.
- `feed_start_date` end-range check relative to `feed_end_date`.
- Single-row enforcement (at most one row in `feed_info.txt`).

This validator adds only the Best Practices recommendation check that at least one of the two contact fields is populated.

### Python schema reference

The `FEED_INFO` table definition already exists in `src/gtfs_validator/schemas.py` and includes `feed_contact_email` (type `_EMAIL`) and `feed_contact_url` (type `_URL`), both optional with no requirement constraint. No schema changes are needed to implement this validator.

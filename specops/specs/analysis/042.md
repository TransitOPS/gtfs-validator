# Analysis: PathwayLoopValidator

## 1. Purpose

Validates that no pathway in `pathways.txt` is a loop — i.e., that `from_stop_id` and `to_stop_id` are not the same value.

## 2. Input tables

| Table | Columns used |
|---|---|
| `pathways.txt` | `pathway_id`, `from_stop_id`, `to_stop_id`, `csv_row_number` |

This is a single-table validator. No joins to other tables are required.

## 3. Validation logic

### Rule: pathway must not reference the same stop at both endpoints

For each row in `pathways.txt`:

1. Check whether `from_stop_id` is present (non-null, non-empty).
2. Check whether `to_stop_id` is present (non-null, non-empty).
3. If **both** are present and `from_stop_id == to_stop_id`, emit `pathway_loop`.
4. If either field is absent, skip the check — no notice emitted.

The equality check is a simple string equality on the raw ID values. No normalization is performed.

## 4. Notices emitted

### `pathway_loop` (WARNING)

Emitted when a pathway row has the same value in `from_stop_id` and `to_stop_id`.

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | integer | `pathways.txt` row | Row number of the offending pathway |
| `pathway_id` | string | `pathways.pathway_id` | ID of the looping pathway |
| `stop_id` | string | `pathways.from_stop_id` | The stop ID that appears on both endpoints |

Severity: WARNING.

Java class: `PathwayLoopNotice`.

Note: The `stop_id` field in the notice is populated from `from_stop_id` (not `to_stop_id`), because both values are identical when the notice fires. The Java constructor explicitly reads `pathway.fromStopId()`.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `pathways.txt` absent from feed | Return immediately, no notices. |
| `pathways.txt` present but empty | No rows to evaluate; no notices. |
| `from_stop_id` is null/absent | Guard check fails; skip row silently; no notice. |
| `to_stop_id` is null/absent | Guard check fails; skip row silently; no notice. |
| Both `from_stop_id` and `to_stop_id` absent | Both guard checks fail; skip row silently; no notice. |
| `from_stop_id != to_stop_id` | No notice; valid pathway. |
| `from_stop_id == to_stop_id` | Emit `pathway_loop`. |
| Multiple loop rows in the feed | One notice emitted per offending row; all are independent. |

## 6. Test contracts

### `loop_yieldsNotice`

- Pathway: `csv_row_number = 2`, `pathway_id = "pw1"`, `from_stop_id = "platform1"`, `to_stop_id = "platform1"`.
- Expected: exactly one `PathwayLoopNotice` with `{csvRowNumber: 2, pathwayId: "pw1", stopId: "platform1"}`.
- Confirms: same stop ID on both endpoints triggers the notice.

### `noLoop_yieldsNoNotice`

- Pathway: `csv_row_number = 2`, `pathway_id = "pw1"`, `from_stop_id = "platform1"`, `to_stop_id = "entrance2"`.
- Expected: no notices.
- Confirms: distinct endpoint IDs are valid.

### `noEndpoints_yieldsNoNotice`

- Pathway: `csv_row_number = 2`, `pathway_id = "pw1"`, no `from_stop_id` or `to_stop_id` set.
- Expected: no notices.
- Confirms: absent endpoint fields cause the check to be skipped entirely.

## 7. Implementation notes

### Algorithm choice

This check is naturally vectorized. The entire validation reduces to a single Polars filter:

```python
violations = pathways.filter(
    pl.col("from_stop_id").is_not_null()
    & pl.col("to_stop_id").is_not_null()
    & (pl.col("from_stop_id") == pl.col("to_stop_id"))
)
```

Iterate over the resulting rows to emit notices. No joins or cross-table lookups are required.

### Recommended Python implementation sketch

```python
import polars as pl
from gtfs_validator.notices import Notice
from gtfs_validator.context import ValidationContext


def validate_pathway_loop(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    pathways = feed.get("pathways")
    if pathways is None or pathways.is_empty():
        return []

    violations = pathways.filter(
        pl.col("from_stop_id").is_not_null()
        & pl.col("to_stop_id").is_not_null()
        & (pl.col("from_stop_id") == pl.col("to_stop_id"))
    )

    notices: list[Notice] = []
    for row in violations.select(
        ["csv_row_number", "pathway_id", "from_stop_id"]
    ).iter_rows(named=True):
        notices.append(
            Notice(
                code="pathway_loop",
                severity="WARNING",
                fields={
                    "csvRowNumber": row["csv_row_number"],
                    "pathwayId": row["pathway_id"],
                    "stopId": row["from_stop_id"],
                },
            )
        )
    return notices
```

### Notice field name convention

Follow camelCase field keys in the notice `fields` dict:
- `csvRowNumber`
- `pathwayId`
- `stopId`

### Feed dict key

- `"pathways"` — `pathways.txt`

### Required columns

From `pathways.txt`: `csv_row_number`, `pathway_id`, `from_stop_id`, `to_stop_id`.

### Null semantics

Both `from_stop_id` and `to_stop_id` are `@Required` in the schema (`GtfsPathwaySchema`), so they will normally be non-null after loading. The null guards mirror the Java `hasFromStopId()` / `hasToStopId()` checks, which return `false` for fields that were absent or empty in the CSV. The Polars filter uses `is_not_null()` on both columns to replicate this guard before comparing values.

### Determinism

Emit notices in the order rows appear in `pathways.txt` (ascending `csv_row_number`). The Polars filter preserves input row order.

### Validator registration

Requires: `["pathways"]`.

### Notice code mapping

| Java class | Python notice code |
|---|---|
| `PathwayLoopNotice` | `pathway_loop` |

# Analysis: BookingRulesEntityValidator

## 1. Purpose

Validates individual rows in `booking_rules.txt` to enforce field-level constraints that depend on the `booking_type` value. Each booking type (real-time, same-day, prior-day) has a different set of allowed and required prior-notice fields. The validator ensures that forbidden fields are not populated, required fields are present, and numeric/day ranges are internally consistent.

This is a single-entity (row-level) validator -- it examines each booking rule row independently with no cross-table joins.

## 2. Input tables

| Table | Columns used |
|---|---|
| `booking_rules.txt` | `booking_rule_id`, `booking_type`, `prior_notice_duration_min`, `prior_notice_duration_max`, `prior_notice_start_day`, `prior_notice_start_time`, `prior_notice_last_day`, `prior_notice_last_time`, `prior_notice_service_id` |

No other tables are referenced. This is purely a row-level validator on `booking_rules.txt`.

## 3. Validation logic

The validator performs eight checks per row, grouped into categories:

### 3a. Forbidden fields by booking type

Each `booking_type` forbids certain prior-notice fields from being populated. If any forbidden field has a value, a single notice is emitted listing all offending field names.

**REALTIME (0)** -- all prior-notice fields are forbidden:
- `prior_notice_duration_min`
- `prior_notice_duration_max`
- `prior_notice_last_day`
- `prior_notice_last_time`
- `prior_notice_start_day`
- `prior_notice_start_time`
- `prior_notice_service_id`

**SAMEDAY (1)** -- the following day-based fields are forbidden:
- `prior_notice_last_day`
- `prior_notice_last_time`
- `prior_notice_service_id`

**PRIORDAY (2)** -- the duration-based fields are forbidden:
- `prior_notice_duration_min`
- `prior_notice_duration_max`

### 3b. Missing prior_notice_duration_min for SAMEDAY

When `booking_type` is SAMEDAY (1) and `prior_notice_duration_min` is not set, emit `missing_prior_notice_duration_min`.

### 3c. Duration min vs max range check

When both `prior_notice_duration_min` and `prior_notice_duration_max` are present, check that `prior_notice_duration_max >= prior_notice_duration_min`. If max < min, emit `invalid_prior_notice_duration_min`. This check applies regardless of booking type.

### 3d. Missing required PRIORDAY fields

When `booking_type` is PRIORDAY (2):
- If `prior_notice_last_day` is missing, emit `missing_prior_notice_last_day`.
- If `prior_notice_last_time` is missing, emit `missing_prior_notice_last_time`.

These are checked independently (can emit both).

### 3e. prior_notice_start_day forbidden with prior_notice_duration_max

When both `prior_notice_duration_max` and `prior_notice_start_day` are set (regardless of booking type), emit `forbidden_prior_notice_start_day`. These two fields represent mutually exclusive booking window specifications.

### 3f. prior_notice_last_day vs prior_notice_start_day range

When both `prior_notice_last_day` and `prior_notice_start_day` are set, check that `prior_notice_last_day <= prior_notice_start_day`. If last_day > start_day, emit `prior_notice_last_day_after_start_day`. Note: these day values represent "days before travel" so a higher number means further in the past; last_day should be closer to travel (smaller or equal number).

### 3g. prior_notice_start_time / prior_notice_start_day co-dependency

- If `prior_notice_start_time` is set but `prior_notice_start_day` is NOT set, emit `forbidden_prior_notice_start_time`.
- If `prior_notice_start_day` is set but `prior_notice_start_time` is NOT set, emit `missing_prior_notice_start_time`.

These are mutual: the two fields must both be present or both be absent.

## 4. Notices emitted

All notices have severity **ERROR**.

| Notice code | Fields | Description |
|---|---|---|
| `forbidden_real_time_booking_field_value` | `csvRowNumber`, `bookingRuleId`, `fieldNames` (comma-separated) | Prior-notice fields populated for a REALTIME booking rule |
| `forbidden_same_day_booking_field_value` | `csvRowNumber`, `bookingRuleId`, `fieldNames` (comma-separated) | Day-based prior-notice fields populated for a SAMEDAY booking rule |
| `forbidden_prior_day_booking_field_value` | `csvRowNumber`, `bookingRuleId`, `fieldNames` (comma-separated) | Duration-based fields populated for a PRIORDAY booking rule |
| `invalid_prior_notice_duration_min` | `csvRowNumber`, `bookingRuleId`, `priorNoticeDurationMin`, `priorNoticeDurationMax` | `prior_notice_duration_max` < `prior_notice_duration_min` |
| `missing_prior_notice_duration_min` | `csvRowNumber`, `bookingRuleId` | SAMEDAY rule missing required `prior_notice_duration_min` |
| `forbidden_prior_notice_start_day` | `csvRowNumber`, `bookingRuleId`, `priorNoticeStartDay`, `priorNoticeDurationMax` | `prior_notice_start_day` set when `prior_notice_duration_max` is also set |
| `prior_notice_last_day_after_start_day` | `csvRowNumber`, `priorNoticeLastDay`, `priorNoticeStartDay` | `prior_notice_last_day` > `prior_notice_start_day` |
| `forbidden_prior_notice_start_time` | `csvRowNumber`, `bookingRuleId`, `priorNoticeStartTime` | `prior_notice_start_time` set without `prior_notice_start_day` |
| `missing_prior_notice_start_time` | `csvRowNumber`, `bookingRuleId`, `priorNoticeStartDay` | `prior_notice_start_day` set without `prior_notice_start_time` |
| `missing_prior_notice_last_day` | `csvRowNumber`, `bookingRuleId` | PRIORDAY rule missing required `prior_notice_last_day` |
| `missing_prior_notice_last_time` | `csvRowNumber`, `bookingRuleId` | PRIORDAY rule missing required `prior_notice_last_time` |

## 5. Edge cases

- **Multiple forbidden fields**: When a booking type has multiple forbidden fields set, they are reported as a single notice with all field names comma-joined (not one notice per field).
- **No forbidden fields**: When a row has the correct booking type and no forbidden fields populated, no notice is emitted.
- **Cross-type field checks are independent of booking-type checks**: The duration min/max range check, the start_day/start_time co-dependency check, and the last_day/start_day range check all run regardless of `booking_type`. This means a row can trigger both a forbidden-field notice (from its booking type) AND a range/co-dependency notice simultaneously.
- **Null/missing field semantics**: "has" checks correspond to the field being non-null/non-default. Integer fields default to 0 when not set (and `has*` returns false), time fields default to null.
- **prior_notice_last_day_after_start_day notice is missing bookingRuleId**: Unlike most other notices, this notice only includes `csvRowNumber`, `priorNoticeLastDay`, and `priorNoticeStartDay` -- it does not include `bookingRuleId`.
- **booking_type not set or unrecognized**: If `booking_type` is missing/unrecognized, none of the type-specific forbidden-field checks or missing-field checks fire (the entity will not match any of the three enum values). The type-independent checks (3c, 3e, 3f, 3g) would still run.

## 7. Implementation notes

### Validator type
Single-entity (row-level). In the Python migration this should iterate over each row of `booking_rules.txt` independently. Since all checks are row-local with simple conditionals, a vectorized Polars approach is natural: use `pl.when().then()` expressions with null-checking to build each notice condition as a boolean mask, then collect rows matching each condition.

### Forbidden field grouping
The Java code collects all forbidden fields into a list and emits one notice per booking-type check with the field names comma-joined. The Python version should replicate this behavior -- one notice per row per booking-type violation, with a `field_names` string listing all offending fields.

### Field presence semantics
In Java, `has*()` returns false when the field was not provided in the CSV. In Polars, this maps to checking `is_not_null()` for nullable columns. Integer fields like `prior_notice_duration_min` should be loaded as nullable integers (not defaulting to 0) so that null-checks correctly represent "field not provided."

### Booking type enum
- 0 = REALTIME
- 1 = SAMEDAY
- 2 = PRIORDAY

### Multiple notices per row
A single row can emit multiple notices. For example, a PRIORDAY row with duration fields set AND missing last_day AND missing last_time would emit three notices: `forbidden_prior_day_booking_field_value`, `missing_prior_notice_last_day`, and `missing_prior_notice_last_time`.

### Notice field naming
The `prior_notice_last_day_after_start_day` notice omits `bookingRuleId` in its fields -- this is an inconsistency in the Java source. The Python migration should preserve this behavior for compatibility.

# Analysis: InconsistentRouteTypeForInSeatTransferValidator

## 1. Purpose

Warns when an in-seat transfer (`transfer_type=4`) connects two routes that have different `route_type` values, indicating a mode mismatch for a same-vehicle continuation.

## 2. Input tables

| Table | Columns used |
|---|---|
| `transfers.txt` | `from_route_id`, `to_route_id`, `transfer_type` |
| `routes.txt` | `route_id`, `route_type` |

### Key relationships

- `transfers.from_route_id` and `transfers.to_route_id` are foreign keys to `routes.route_id`.
- Only transfers with `transfer_type = 4` (IN_SEAT_TRANSFER_ALLOWED) are examined.

## 3. Validation logic

1. **Guard clause** (`shouldCallValidate`): Skip validation entirely if:
   - `transfers.txt` is missing or null.
   - `routes.txt` is missing or null.
   - `transfers.txt` does not contain a `from_route_id` column.
   - `transfers.txt` does not contain a `to_route_id` column.
   - `transfers.txt` does not contain a `transfer_type` column.
2. Filter `transfers.txt` to rows where `transfer_type = 4` (IN_SEAT_TRANSFER_ALLOWED).
3. For each such transfer row:
   a. Look up `from_route_id` in `routes.txt` to get the from-route's `route_type`.
   b. Look up `to_route_id` in `routes.txt` to get the to-route's `route_type`.
   c. If either route lookup fails (route_id not found), skip this transfer row silently.
   d. If both routes are found and their `route_type` values differ, emit a notice.

## 4. Notices emitted

| Code | Severity | Fields | Condition |
|---|---|---|---|
| `inconsistent_route_type_for_in_seat_transfer` | WARNING | `csv_row_number` (int), `from_route_id` (str), `to_route_id` (str), `from_route_type` (int), `to_route_type` (int) | An in-seat transfer connects two routes with different route_type values |

### Notice field details

- `csv_row_number`: The row number from `transfers.txt` for the offending transfer.
- `from_route_id`: The `from_route_id` value of the transfer.
- `to_route_id`: The `to_route_id` value of the transfer.
- `from_route_type`: The `route_type` of the from-route (integer enum value).
- `to_route_type`: The `route_type` of the to-route (integer enum value).

In the Python implementation, field names should follow snake_case convention as listed above.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `transfers.txt` missing | Skip validation, no notices |
| `routes.txt` missing | Skip validation, no notices |
| `from_route_id` column absent from transfers | Skip validation, no notices |
| `to_route_id` column absent from transfers | Skip validation, no notices |
| `transfer_type` column absent from transfers | Skip validation, no notices |
| `transfer_type` is not 4 (e.g., 0=RECOMMENDED) | Transfer is not examined, no notice |
| `from_route_id` not found in `routes.txt` | Skip this transfer row silently (FK violation handled elsewhere) |
| `to_route_id` not found in `routes.txt` | Skip this transfer row silently (FK violation handled elsewhere) |
| Both routes exist and have the same `route_type` | No notice |
| Both routes exist and have different `route_type` | Emit one notice per transfer row |
| Empty `transfers.txt` | No notices |
| Empty `routes.txt` | No notices (all route lookups fail) |
| Multiple in-seat transfers with mismatches | One notice per mismatched transfer |

## 6. Test contracts

### Test: `sameRouteTypeForInSeatTransferDoesNotGenerateNotice`

- **Setup**: Two routes (`r0`, `r1`) both with type `BUS`. One transfer (`r0` -> `r1`, `transfer_type=4`).
- **Expected**: No notices emitted.

### Test: `otherTransferTypeForInSeatTransferDoesNotGenerateNotice`

- **Setup**: Two routes (`r0` = `BUS`, `r1` = `RAIL`). One transfer (`r0` -> `r1`, `transfer_type=0` / RECOMMENDED).
- **Expected**: No notices emitted (different route types are only flagged for in-seat transfers).

### Test: `differentRouteTypeForInSeatTransferGeneratesNotice`

- **Setup**: Two routes (`r0` = `BUS`, `r1` = `RAIL`). One transfer (`r0` -> `r1`, `transfer_type=4`).
- **Expected**: Exactly one notice emitted.

### Additional test cases to implement in Python

- `transfers.txt` missing -- no notices.
- `routes.txt` missing -- no notices.
- `from_route_id` or `to_route_id` not found in routes -- no notice for that transfer.
- Empty transfers table -- no notices.
- Multiple in-seat transfers: one consistent, one inconsistent -- exactly one notice.
- Transfer with `transfer_type=5` (IN_SEAT_TRANSFER_NOT_ALLOWED) and different route types -- no notice (only type 4 is checked).

## 7. Implementation notes

### Polars approach (recommended)

This validator is well-suited to a fully vectorized Polars implementation using two left joins:

1. **Filter** `transfers` to rows where `transfer_type == 4`.
2. **Join** filtered transfers with `routes` on `from_route_id = route_id` to get `from_route_type`.
3. **Join** the result with `routes` on `to_route_id = route_id` to get `to_route_type`.
4. **Filter** rows where both route types are non-null (both routes exist) and `from_route_type != to_route_type`.
5. **Emit** one notice per remaining row.

```python
def validate_inconsistent_route_type_for_in_seat_transfer(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
    transfers = feed.get("transfers")
    routes = feed.get("routes")
    if transfers is None or routes is None:
        return []
    if transfers.is_empty() or routes.is_empty():
        return []
    for col in ("from_route_id", "to_route_id", "transfer_type"):
        if col not in transfers.columns:
            return []

    in_seat = transfers.filter(pl.col("transfer_type") == 4)
    if in_seat.is_empty():
        return []

    route_lookup = routes.select("route_id", "route_type")

    joined = (
        in_seat.select("csvRowNumber", "from_route_id", "to_route_id")
        .join(
            route_lookup.rename({"route_id": "from_route_id", "route_type": "from_route_type"}),
            on="from_route_id",
            how="inner",
        )
        .join(
            route_lookup.rename({"route_id": "to_route_id", "route_type": "to_route_type"}),
            on="to_route_id",
            how="inner",
        )
    )

    bad = joined.filter(pl.col("from_route_type") != pl.col("to_route_type"))

    notices = []
    for row in bad.iter_rows(named=True):
        notices.append(Notice(
            code="inconsistent_route_type_for_in_seat_transfer",
            severity=Severity.WARNING,
            csv_row_number=row["csvRowNumber"],
            from_route_id=row["from_route_id"],
            to_route_id=row["to_route_id"],
            from_route_type=row["from_route_type"],
            to_route_type=row["to_route_type"],
        ))
    return notices
```

### Key considerations

- Using inner joins naturally excludes transfers whose `from_route_id` or `to_route_id` do not exist in `routes.txt`, matching the Java `Optional.ifPresent()` behavior.
- The column rename approach avoids ambiguity when joining `routes` twice on different keys.
- The `iter_rows` loop over bad rows is acceptable since the number of mismatched in-seat transfers is expected to be very small.
- `transfer_type` values: 0=RECOMMENDED, 1=TIMED, 2=MINIMUM_TIME, 3=IMPOSSIBLE, 4=IN_SEAT_TRANSFER_ALLOWED, 5=IN_SEAT_TRANSFER_NOT_ALLOWED. Only value 4 triggers this validator.

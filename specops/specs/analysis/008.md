# Analysis: DateTripsValidator

## 1. Purpose

Validates that trip data covers at least the next 7 days from the current validation date. Specifically, it computes a "majority service window" -- the date range during which a significant proportion of trips are active -- and emits a warning if that window does not fully cover the 7-day period starting from the validation date.

This catches feeds where service data is about to expire or has not yet started, which would cause transit apps to show incomplete or missing service information.

Reference: https://github.com/MobilityData/gtfs-validator/issues/886#issuecomment-832237225

## 2. Input tables

| Table | Columns used |
|---|---|
| `calendar.txt` | `service_id`, `start_date`, `end_date`, `monday`..`sunday` |
| `calendar_dates.txt` | `service_id`, `date`, `exception_type` |
| `trips.txt` | `trip_id`, `service_id` |
| `frequencies.txt` | `trip_id`, `start_time`, `end_time`, `headway_secs` |

Additional input: the current validation date (injected via `DateForValidation`, typically today's date).

## 3. Validation logic

### 3a. Build service date map

1. Combine `calendar.txt` and `calendar_dates.txt` into a `Map<service_id, SortedSet<LocalDate>>` using `CalendarUtil`:
   - For each `calendar.txt` row: expand the weekly pattern (monday..sunday flags) over the `start_date` to `end_date` range to produce a set of active dates.
   - Apply `calendar_dates.txt` exceptions: `exception_type=1` (SERVICE_ADDED) adds dates, `exception_type=2` (SERVICE_REMOVED) removes dates.
   - If a service_id appears only in `calendar_dates.txt` (no corresponding `calendar.txt` row), create a service period from the added dates alone.

### 3b. Count trips per service date

2. For each trip, determine the number of "effective trips" it contributes:
   - If the trip has no entries in `frequencies.txt`, it counts as 1 trip.
   - If the trip has frequency entries, expand each frequency interval: `1 + floor((end_time - start_time - 1) / headway_secs)` trips per frequency row. Sum across all frequency rows for that trip.
3. Aggregate trip counts by `service_id`, then distribute across each service date: for each date in the service's date set, add the service's trip count to that date's total.
4. Result: a `NavigableMap<LocalDate, Integer>` mapping each active date to the total number of trips running on that date.

### 3c. Compute majority service coverage

5. Sort all trip counts (values from the date-to-count map).
6. Determine a "max trips" reference point, avoiding outliers:
   - Compute index = `max(floor(0.90 * N), N - 30)` where N is the number of dates with trips.
   - The trip count at this index in the sorted list is used as the "typical max."
7. Compute a majority threshold: `floor(0.75 * typical_max_trips)`.
8. Find the first date (scanning forward) where trip count >= threshold. This is `majorityStart`.
9. Find the last date (scanning backward) where trip count >= threshold. This is `majorityEnd`.
10. Return `DateInterval(majorityStart, majorityEnd)`.

### 3d. Check coverage against validation date

11. If the majority service interval is empty (no trips, no services), do nothing.
12. Otherwise, emit a notice if EITHER:
    - `majorityStart` is strictly after the validation date (service has not started yet), OR
    - `majorityEnd` is strictly before `validationDate + 7 days` (service ends within the next 7 days).

In other words, the condition for NO notice is:
- `majorityStart <= validationDate` AND `majorityEnd >= validationDate + 7`.

## 4. Notices emitted

All notices have severity **WARNING**.

| Notice code | Fields | Description |
|---|---|---|
| `trip_coverage_not_active_for_next_7_days` | `current_date`, `service_window_start_date`, `service_window_end_date` | The majority service window does not fully cover the next 7 days from the validation date |

Only one notice type is emitted, and at most one notice per feed (this is a feed-level check, not per-row).

### Notice field details

| Field | Type | Description |
|---|---|---|
| `current_date` | date (YYYYMMDD) | The validation date |
| `service_window_start_date` | date (YYYYMMDD) | Start of the majority service window |
| `service_window_end_date` | date (YYYYMMDD) | End of the majority service window |

## 5. Edge cases

- **No trips in feed**: `countTripsForEachServiceDate` returns an empty map, `computeMajorityServiceCoverage` returns `Optional.empty()`, no notice emitted.
- **No services (empty calendar and calendar_dates)**: Same as above -- empty service date map leads to empty trip counts.
- **Trips with service_ids not in calendar/calendar_dates**: Those service_ids will have no date set, so those trips contribute nothing to the date-trip counts.
- **All trips on a single date**: The majority coverage is a single-day interval. Unless that date happens to be validationDate and validationDate+7 is the same day (impossible), a notice will be emitted.
- **Frequency-based trips with headway_secs=0**: The formula `(end - start - 1) / 0` would be a division by zero. The Java code guards with `if (frequency.headwaySecs() > 0)`, so headway_secs=0 means the frequency entry adds exactly 1 trip (the base `++tripCount` before the headway check).
- **Service window starts exactly on validation date**: `majorityStart.isAfter(validationDate)` is false, so this part of the condition does not trigger. The end date check still applies.
- **Service window ends exactly on validationDate + 7**: `majorityEnd.isBefore(validationDate + 7)` is false, so no notice is emitted. The boundary is inclusive (>= 7 days is acceptable).
- **Service window ends on validationDate + 6**: This IS before validationDate + 7, so a notice is emitted.
- **Majority threshold rounding**: The threshold uses integer truncation (`(int)(0.75 * count)`), so there is implicit floor behavior.
- **MAX_SERVICE_DATE_TRIP_COUNT_LIMIT=30**: For feeds with fewer than ~33 dates, the `N - 30` term could go negative, but `max(floor(0.90*N), N-30)` ensures the index is at least 0 because `floor(0.90*N)` will be >= 0. For very small N values, the 90th percentile index is used.

## 7. Implementation notes

### Validator type
Feed-level (file-level) validator. Consumes four tables plus the validation context date.

### Complex utility pipeline
This validator relies heavily on two utility modules:
- `CalendarUtil`: builds the service_id-to-dates mapping from calendar.txt + calendar_dates.txt.
- `TripCalendarUtil`: counts trips per date and computes majority service coverage.

In the Python implementation, these utilities should be reusable helpers (likely in a `utils/` module or as methods on `ValidationContext`) since other validators (e.g., `FeedExpirationDateValidator`) also use them.

### Majority coverage algorithm constants

| Constant | Value | Purpose |
|---|---|---|
| `MAX_SERVICE_DATE_TRIP_COUNT_RATIO` | 0.90 | Percentile index for selecting "typical max" trip count |
| `MAX_SERVICE_DATE_TRIP_COUNT_LIMIT` | 30 | Maximum number of high-count dates to skip as outliers |
| `MAJORITY_TRIP_COUNT_RATIO` | 0.75 | Fraction of typical max that defines "majority" service |

These constants should be module-level in the Python implementation for testability and documentation.

### Polars implementation strategy
The service date expansion (weekly pattern + exceptions) is inherently iterative over date ranges and is best done in plain Python (or with `pl.date_range` + filtering). The trip counting and aggregation steps are well-suited to Polars:

1. Build service dates: For each calendar row, generate date range and filter by day-of-week pattern. Apply calendar_dates additions/removals. Result: a Python dict `{service_id: list[date]}`.
2. Count trips per service_id: Join `trips` with `frequencies` (left join on `trip_id`), compute effective trip count per trip, then group by `service_id` and sum. This is naturally a Polars pipeline.
3. Distribute counts to dates: Explode the service_id-to-dates mapping into a DataFrame `(service_id, date)`, join with trip counts, group by date and sum. Result: a date-to-count Series.
4. Compute majority coverage: Sort counts, compute threshold, find first/last dates meeting threshold. This is straightforward Python on the collected results.
5. Compare against validation date + 7 days.

### Validation date
The validation date comes from `ValidationContext` (the Python equivalent of `DateForValidation`). It is typically today's date but can be overridden via CLI for testing.

### Notice field naming
Java uses `currentDate`, `serviceWindowStartDate`, `serviceWindowEndDate`. Python equivalents: `current_date`, `service_window_start_date`, `service_window_end_date`.

### Reuse consideration
The service-date-to-trip-count map and majority coverage interval are also used by `FeedExpirationDateValidator` (which checks for 30-day coverage). Consider computing these once in `ValidationContext` and sharing across validators to avoid redundant work.

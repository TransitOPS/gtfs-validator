# Analysis: ContinuousPickupDropOffValidator

## 1. Purpose

Validates that routes with continuous pickup or drop-off behavior (values 0, 2, or 3 in `routes.continuous_pickup` or `routes.continuous_drop_off`) do not have stop times with pickup/drop-off windows defined. Specifically, if a route has continuous pickup/drop-off enabled, then none of its trips' stop times should have `start_pickup_drop_off_window` or `end_pickup_drop_off_window` set.

This is a cross-table validator joining `routes.txt`, `trips.txt`, and `stop_times.txt`.

## 2. Input tables

| Table | Columns used |
|---|---|
| `routes.txt` | `route_id`, `continuous_pickup`, `continuous_drop_off` |
| `trips.txt` | `trip_id`, `route_id` |
| `stop_times.txt` | `trip_id`, `start_pickup_drop_off_window`, `end_pickup_drop_off_window` |

Join path: `routes` -> `trips` (via `route_id`) -> `stop_times` (via `trip_id`).

## 3. Validation logic

### 3a. Skip condition (shouldCallValidate)

The validator only runs when:
- Both `routeTable` and `stopTimeTable` are present (non-null), AND
- The routes file has `continuous_pickup` column OR (`continuous_drop_off` column AND (`start_pickup_drop_off_window` column OR `end_pickup_drop_off_window` column in stop_times))

Note: The Java code has an operator precedence subtlety. The expression is:
```
hasColumn(continuous_pickup)
|| hasColumn(continuous_drop_off)
    && (hasColumn(start_pickup_drop_off_window) || hasColumn(end_pickup_drop_off_window))
```
Because `&&` binds tighter than `||`, this evaluates as:
```
hasColumn(continuous_pickup)
|| (hasColumn(continuous_drop_off) && (hasColumn(start_...) || hasColumn(end_...)))
```
This means if `continuous_pickup` column exists, the validator runs regardless of whether the stop_times window columns exist. The window-column check only gates `continuous_drop_off`.

### 3b. Core validation

For each route:
1. Check if the route has continuous behavior enabled. A route is "continuous" if:
   - `continuous_pickup` is ALLOWED (0), MUST_PHONE (2), or ON_REQUEST_TO_DRIVER (3), OR
   - `continuous_drop_off` is ALLOWED (0), MUST_PHONE (2), or ON_REQUEST_TO_DRIVER (3)

   In other words, the only value that is NOT continuous is NOT_AVAILABLE (1). The default/unset value (0 = ALLOWED) is treated as continuous.

2. If the route is not continuous, skip to the next route.

3. For each trip belonging to the route (joined via `route_id`):
   - For each stop_time belonging to the trip (joined via `trip_id`):
     - If `start_pickup_drop_off_window` OR `end_pickup_drop_off_window` is present (has a value), emit a `forbidden_continuous_pickup_drop_off` notice.

### 3c. Continuous pickup/drop-off enum values

| Value | Name | Treated as continuous? |
|---|---|---|
| 0 | ALLOWED | Yes |
| 1 | NOT_AVAILABLE | No |
| 2 | MUST_PHONE | Yes |
| 3 | ON_REQUEST_TO_DRIVER | Yes |

## 4. Notices emitted

All notices have severity **ERROR**.

| Notice code | Fields | Description |
|---|---|---|
| `forbidden_continuous_pickup_drop_off` | `routeCsvRowNumber`, `tripId`, `stopTimeCsvRowNumber`, `startPickupDropOffWindow`, `endPickupDropOffWindow` | A stop time defines a pickup/drop-off window on a route that has continuous pickup or drop-off enabled |

Only one notice type is emitted. One notice is emitted per offending stop_time row (not per route or per trip).

## 5. Edge cases

- **Default enum value (0 = ALLOWED)**: When `continuous_pickup` or `continuous_drop_off` is not set in the CSV, it defaults to 0 (ALLOWED), which IS treated as continuous. This means routes with no explicit continuous values set will trigger the check. However, the `shouldCallValidate` guard prevents the validator from running unless the `continuous_pickup` or `continuous_drop_off` column actually exists in the file, so default-unset scenarios where the column is absent are safely skipped.
- **Both window fields present**: If a stop_time has both `start_pickup_drop_off_window` and `end_pickup_drop_off_window`, only one notice is emitted (the OR check triggers once).
- **Only one window field present**: A notice is still emitted if only one of the two window fields is present.
- **Multiple stop_times per trip**: Each offending stop_time generates its own notice. A trip with 5 stop_times that all have windows will produce 5 notices.
- **Multiple trips per route**: All trips for a continuous route are checked.
- **Route with no trips**: No notices emitted (inner loop over trips is empty).
- **Trip with no stop_times**: No notices emitted (inner loop over stop_times is empty).
- **Missing tables**: If `routeTable` or `stopTimeTable` is null, `shouldCallValidate` returns false and the validator is skipped entirely. The `tripTable` is not null-checked in `shouldCallValidate` but is required by the constructor.
- **Notice includes window values even when null**: The notice constructor accepts the `startPickupDropOffWindow` and `endPickupDropOffWindow` values directly. If only one is set, the other will be its default/null representation.

## 7. Implementation notes

### Validator type
Cross-table (file-level) validator. Requires joining three tables: `routes` -> `trips` -> `stop_times`.

### Polars implementation strategy
This validator is well-suited to a join-based Polars approach:

1. Filter `routes` to rows where `continuous_pickup != 1` OR `continuous_drop_off != 1` (i.e., at least one is continuous -- value 0, 2, or 3).
2. Join filtered routes to `trips` on `route_id`.
3. Join result to `stop_times` on `trip_id`.
4. Filter to rows where `start_pickup_drop_off_window` is not null OR `end_pickup_drop_off_window` is not null.
5. Emit one notice per remaining row.

### Skip condition
The Python validator should check that the required columns exist in the feed before running. The `shouldCallValidate` logic checks for column presence, not just table presence. In the Python orchestrator, this maps to checking whether the relevant columns appear in the loaded DataFrame headers.

### Enum handling
The `continuous_pickup` and `continuous_drop_off` fields use the `GtfsContinuousPickupDropOff` enum (0=ALLOWED, 1=NOT_AVAILABLE, 2=MUST_PHONE, 3=ON_REQUEST_TO_DRIVER). The check is effectively "value != 1" since all other valid values (0, 2, 3) are treated as continuous. Null/missing values should be treated as not triggering the continuous flag (the shouldCallValidate guard handles column absence, and null individual values should be treated as not matching any enum value).

### Notice field naming
In the Java notice, field names use camelCase (`routeCsvRowNumber`, `tripId`, `stopTimeCsvRowNumber`, `startPickupDropOffWindow`, `endPickupDropOffWindow`). The Python migration should use snake_case equivalents: `route_csv_row_number`, `trip_id`, `stop_time_csv_row_number`, `start_pickup_drop_off_window`, `end_pickup_drop_off_window`.

### Time field representation
The `startPickupDropOffWindow` and `endPickupDropOffWindow` are `GtfsTime` values in Java. In the Python implementation these will be string representations (HH:MM:SS format) since they are included in the notice for informational purposes only.

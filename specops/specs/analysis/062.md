# Analysis: StopTimeTravelSpeedValidator

## 1. Purpose

Validates that transit vehicles do not travel too fast between consecutive stops or between
any two far stops (> 10 km apart) within a trip, where the maximum allowed speed depends on
the route type.

## 2. Input tables

| Table | Columns used |
|---|---|
| `routes.txt` | `route_id`, `route_type` |
| `trips.txt` | `trip_id`, `route_id`, `csv_row_number` |
| `stop_times.txt` | `trip_id`, `stop_id`, `stop_sequence`, `arrival_time`, `departure_time`, `csv_row_number` |
| `stops.txt` | `stop_id`, `stop_lat`, `stop_lon`, `stop_name`, `parent_station` |

### Column semantics

- `routes.route_type` — integer enum; used to look up the max allowed speed threshold
  for the trip's route.
- `trips.trip_id` — string; used to group stop times into per-trip sequences.
- `trips.route_id` — string; FK to `routes.route_id`.
- `stop_times.trip_id` — string; used to join to trips.
- `stop_times.stop_id` — optional string; null indicates a GeoJSON flexible-service
  location with no fixed coordinates. Such rows are skipped for consecutive-stop checks.
- `stop_times.stop_sequence` — integer; defines the ordering of stop times within a trip.
- `stop_times.arrival_time` — optional integer (seconds since midnight); used as the
  arrival time at the end stop of each pair.
- `stop_times.departure_time` — optional integer (seconds since midnight); used as the
  departure time from the start stop of each pair.
- `stops.stop_lat`, `stops.stop_lon` — float; WGS-84 coordinates used for haversine
  distance calculation.
- `stops.parent_station` — optional string; if a stop lacks coordinates, the parent
  station's coordinates are used (up to 3 levels deep).
- `stops.stop_name` — string; included in notice payloads for human readability.

## 3. Validation logic

The validator performs two independent checks: **consecutive-stop speed** and **far-stop
speed**. Both operate on the same per-trip, sorted-by-stop-sequence stop time data.

### 3.1 Grouping and deduplication

Before running checks, trips with identical behavioral fingerprints are grouped. The
fingerprint covers: `route_id`, ordered `stop_id` list, ordered `arrival_time` list, and
ordered `departure_time` list. When multiple trips share the same fingerprint, the geometry
and speed checks are computed only once (using the first trip's data), and then one notice
is emitted per matching trip. This avoids redundant geodesic calculations for duplicate
schedule patterns.

In the Java implementation this is done with a hash (FarmHash fingerprint) keyed on route
ID, stop count, and per-stop-time (stop_id, arrival_time_secs, departure_time_secs).

### 3.2 Speed lookup by route type

| Route type (int) | Route type name | Max speed (km/h) |
|---|---|---|
| 0 | LIGHT_RAIL | 100 |
| 1 | SUBWAY | 150 |
| 2 | RAIL | 500 |
| 3 | BUS | 150 |
| 4 | FERRY | 80 |
| 5 | CABLE_TRAM | 30 |
| 6 | AERIAL_LIFT | 50 |
| 7 | FUNICULAR | 50 |
| 11 | TROLLEYBUS | 150 |
| 12 | MONORAIL | 150 |
| (other) | Unknown | 200 |

### 3.3 Coordinate resolution for stops

For each `stop_id` encountered in a stop time:

1. Look up the stop in `stops.txt`.
2. If the stop has `stop_lat`/`stop_lon`, use those directly.
3. If the stop lacks coordinates but has a `parent_station`, walk up to the parent and
   use its coordinates.
4. Walk at most 3 levels deep to prevent infinite loops from data bugs.
5. If no coordinates are found anywhere in the parent chain, treat the location as
   having no coordinates (`Optional.empty`).

When a stop has no resolvable coordinates, the pairwise distance to/from that stop is set
to 0.0 km (for the `distancesKm` array used by the far-stop check), and the pair is
skipped in the consecutive-stop check.

### 3.4 Consecutive-stop speed check (`validateConsecutiveStops`)

For each trip (or deduplicated group of trips), iterate pairs of adjacent stop times in
`stop_sequence` order. For each pair `(start, end)` where `start` is the earlier stop:

1. Resolve coordinates for both `start.stop_id` and `end.stop_id`. If either is missing
   (GeoJSON location or not in stops table), skip this pair and continue to the next.
2. Compute straight-line distance (km) between the two coordinates.
3. Skip the pair if `start` lacks `departure_time` or `end` lacks `arrival_time`.
4. Compute `speed_kph` using `getSpeedKphBetweenStops` (see section 3.6).
5. If `speed_kph > max_speed_kph` for the route type:
   - Emit one `fast_travel_between_consecutive_stops` notice per trip in the
     deduplicated group.

The `start` variable for the next iteration is set to `end` from the current iteration
(sliding window). Note: `start` does NOT advance if `end` had no resolvable coordinates,
because in that case the pair is skipped and `end` is never used as the new reference.
Actually, examining the Java code carefully: `start = end` is always executed at the end
of the loop body after the check (including the skip path for missing coordinates). This
means when a stop has no coordinates, the pair is skipped but `start` still advances to
`end`. Consecutive-stop pairs are always (i, i+1); the `start = end` assignment drives
that sliding window.

### 3.5 Far-stop speed check (`validateFarStops`)

This check accumulates distances along the route using an inner/outer loop and fires
when the total accumulated distance between any two stops (not just adjacent) exceeds
10 km AND the implied speed is too high.

For each trip group:

1. Pre-compute `distancesKm[i]` = straight-line distance between consecutive stops `i`
   and `i+1` in the trip's stop sequence (0.0 if either stop lacks coordinates).
2. For each `endIdx` from 0 to `n-1`:
   a. If `stop_times[endIdx]` lacks `arrival_time`, skip (continue outer loop).
   b. If `stop_times[endIdx].stop_id` is not found in `stops.txt`, abort entirely
      (return from `validateFarStops`). This short-circuit is per-trip-group.
   c. Initialize `distanceToEndIdx = 0`.
   d. For each `startIdx` from `endIdx - 1` down to 0:
      - Accumulate: `distanceToEndIdx += distancesKm[startIdx]`.
      - If `stop_times[startIdx]` lacks `departure_time`, skip (continue inner loop).
      - Compute `speed_kph` = `getSpeedKphBetweenStops(distanceToEndIdx, stopTime[startIdx], stopTime[endIdx])`.
      - If `speed_kph <= max_speed_kph`, skip (continue inner loop).
      - If `distanceToEndIdx <= 10.0 km`, skip (this pair is not "far"; the consecutive
        check handles near pairs).
      - If `stop_times[startIdx].stop_id` is not found in `stops.txt`, abort the entire
        far-stop validation for this trip group (return).
      - Emit one `fast_travel_between_far_stops` notice per trip in the group, with
        `startIdx` and `endIdx` as the offending pair.
      - **Return immediately** (report at most one far-stop notice per trip group).

Key behavioral subtlety: the inner loop scans from high `startIdx` to 0, but exits after
the first qualifying far-stop violation. Because it goes from `endIdx-1` downward, the
first violation found for a given `endIdx` is the pair that is closest in stop sequence
to `endIdx` but still over 10 km away and too fast. The outer loop also exits (returns)
after the first emission, so only one far-stop notice per trip group is ever emitted.

### 3.6 Speed computation (`getSpeedKphBetweenStops`)

```
speed_kph = distance_km * 3600 / effective_time_seconds
```

Where `effective_time_seconds` is computed by `getTimeBetweenStops`:

1. `raw_time = end.arrival_time_secs - start.departure_time_secs`
2. If `raw_time <= 0`:
   - Use 60 seconds (1 minute). This handles backward-in-time data and same-time stops
     (zero time would cause division by zero).
3. Else if both `end.arrival_time_secs % 60 == 0` and `start.departure_time_secs % 60 == 0`
   (i.e., both times are at exact minute boundaries, indicating minute-resolution data):
   - Add 60 seconds as an error buffer: `effective_time = raw_time + 60`.
4. Otherwise: `effective_time = raw_time`.

The minute-resolution buffer accounts for scheduling systems that only output times at
1-minute precision, which introduces up to 30 seconds of error per endpoint (60 seconds
total potential error).

## 4. Notices emitted

### `fast_travel_between_consecutive_stops` (WARNING)

Emitted when the implied travel speed between two adjacent stops in a trip exceeds the
maximum speed for the route type.

| Field | Type | Source | Description |
|---|---|---|---|
| `trip_csv_row_number` | long | `trips.csv_row_number` | CSV row number of the offending trip |
| `trip_id` | string | `trips.trip_id` | Trip identifier |
| `route_id` | string | `trips.route_id` | Route identifier |
| `speed_kph` | float | computed | Implied travel speed in km/h |
| `distance_km` | float | computed | Straight-line distance between the two stops in km |
| `csv_row_number1` | int | `stop_times.csv_row_number` | CSV row of the first (start) stop time |
| `stop_sequence1` | int | `stop_times.stop_sequence` | Stop sequence of the first stop |
| `stop_id1` | string | `stop_times.stop_id` | Stop ID of the first stop |
| `stop_name1` | string | `stops.stop_name` | Stop name of the first stop |
| `departure_time1` | GtfsTime | `stop_times.departure_time` | Departure time from the first stop |
| `csv_row_number2` | int | `stop_times.csv_row_number` | CSV row of the second (end) stop time |
| `stop_sequence2` | int | `stop_times.stop_sequence` | Stop sequence of the second stop |
| `stop_id2` | string | `stop_times.stop_id` | Stop ID of the second stop |
| `stop_name2` | string | `stops.stop_name` | Stop name of the second stop |
| `arrival_time2` | GtfsTime | `stop_times.arrival_time` | Arrival time at the second stop |

Condition: `speed_kph > max_speed_kph` for the route type, both stops have resolvable
coordinates, and both `departure_time` (start) and `arrival_time` (end) are present.

### `fast_travel_between_far_stops` (WARNING)

Emitted when the implied travel speed between any two stops in a trip (using summed
consecutive distances) exceeds the max speed AND the total distance is greater than 10 km.

Fields are identical to `fast_travel_between_consecutive_stops`. The `distance_km` field
holds the accumulated sum of consecutive straight-line distances between the start and end
stops (not a direct geodesic from start to end).

Condition: `speed_kph > max_speed_kph`, `distance_km > 10.0`, both stops exist in
`stops.txt`, the end stop has `arrival_time`, the start stop has `departure_time`. At most
one such notice is emitted per trip group per call to `validateFarStops`.

### Notice code mapping

| Java class | Python notice code |
|---|---|
| `FastTravelBetweenConsecutiveStopsNotice` | `fast_travel_between_consecutive_stops` |
| `FastTravelBetweenFarStopsNotice` | `fast_travel_between_far_stops` |

Both notices are WARNING severity. Both reference `routes.txt`, `stops.txt`,
`stop_times.txt`, and `trips.txt`.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `routes.txt` absent | No trip-route join is possible; no notices (validator requires all four tables). |
| `trips.txt` absent | No stop time grouping possible; no notices. |
| `stop_times.txt` absent or empty | No iteration; return `[]`. |
| `stops.txt` absent or empty | All coordinate lookups fail; consecutive-stop pairs are skipped; far-stop check aborts early for every trip. No notices. |
| Trip has only one stop time | No pairs to evaluate; no notices. |
| `trip_id` in `stop_times` not found in `trips` | That trip's stop times are silently skipped (the Java `.map(...).ifPresent(...)` pattern). |
| `route_id` from trip not found in `routes` | Skip that trip group entirely (broken FK reported by a separate validator). |
| Stop time pair where either stop has no coordinates | Consecutive-stop pair skipped; distance set to 0.0 in the far-stop distance array. |
| Stop time with missing `departure_time` | Consecutive-stop pair skipped; far-stop inner loop skips that `startIdx` but still accumulates distance for it. |
| Stop time with missing `arrival_time` | Far-stop outer loop skips that `endIdx`; consecutive-stop pair skipped if end stop lacks `arrival_time`. |
| Backward-in-time stop times (arrival < departure) | `getTimeBetweenStops` returns 60 seconds; speed = `distance_km * 60`. |
| Both times at exact minute boundaries (minute resolution) | 60-second buffer added to effective travel time, reducing computed speed. |
| Same arrival and departure time (teleport / same-second) | `raw_time = 0`, which is `<= 0`; use 60 seconds. Speed = `distance_km * 60`. |
| Stop with no coordinates and no parent station | `getOptionalStopOrParentLatLng` returns `Optional.empty`; treated as missing. |
| Parent chain cycle in stops table | Loop depth limit of 3 prevents infinite recursion; falls back to `Optional.empty` if not found within 3 hops. |
| Duplicate trips with same route/stops/times fingerprint | All checks computed once; one notice emitted per trip in the group. |
| Multiple trips NOT sharing a fingerprint | Each trip group validated independently. |
| `stop_id` in a stop time references a GeoJSON location (no lat/lon) | Coordinate lookup returns `Optional.empty`; consecutive-stop pair is skipped; far-stop distance is 0.0. |
| Far-stop check finds a violation: emits one notice per trip then stops | Only one `fast_travel_between_far_stops` notice per trip group is ever emitted per validation run. |
| Stop not found in stops table during far-stop check | Entire `validateFarStops` call aborts (returns immediately) — not just that pair. |

## 7. Implementation notes

### Algorithm strategy

This validator has two distinct algorithmic components, both involving ordered per-trip
traversal with accumulated state. Per AGENTS.md, plain Python is appropriate for
graph/geometry/interval logic. The recommended approach:

1. Join `stop_times` to `trips` to `routes` using Polars joins to resolve `route_type`
   per trip. This join is vectorized.
2. Sort globally by `["trip_id", "stop_sequence"]`.
3. Group by `trip_id` using `partition_by("trip_id", maintain_order=True)`.
4. For each trip group, run both checks in Python with `iter_rows(named=True)`.

The deduplication-by-fingerprint optimization from Java (avoiding redundant geometry
computation for identical trip patterns) can be omitted in Python for simplicity, since
the correctness contract is to emit one notice per actual trip. If performance is a
concern, implement the fingerprint grouping as a dictionary keyed on a tuple
`(route_id, tuple(stop_ids), tuple(arrival_secs), tuple(departure_secs))`.

### Geodesic distance calculation

Java uses the S2 geometry library (`S2Earth.getDistanceKm`). Python must use an
equivalent haversine or geodesic calculation. Options:

- `math`-based haversine (pure Python, no dependency).
- `geopy.distance.geodesic` or `geopy.distance.great_circle`.
- A Polars `map_elements` call over lat/lon pairs.

Because the calculation is per-stop-pair and called in a loop, a plain Python haversine
function is the cleanest approach. The result should be in km.

### Coordinate resolution

Implement `resolve_stop_latlng(stop_id, stops_df)` as a pure Python helper that:

1. Looks up the stop row by `stop_id` (using a pre-built dict or index).
2. Returns `(lat, lon)` if present.
3. If the stop has `parent_station` and no coordinates, recurse on `parent_station`.
4. Limit recursion to 3 hops.
5. Return `None` if no coordinates found.

Build the stops lookup dict once before the trip loop, not per stop time.

### Time computation

Implement `get_time_between_stops_secs(departure_secs, arrival_secs) -> int`:

```python
def get_time_between_stops_secs(departure_secs: int, arrival_secs: int) -> int:
    raw = arrival_secs - departure_secs
    if raw <= 0:
        return 60
    if arrival_secs % 60 == 0 and departure_secs % 60 == 0:
        return raw + 60
    return raw
```

And `get_speed_kph(distance_km, departure_secs, arrival_secs) -> float`:

```python
def get_speed_kph(distance_km: float, departure_secs: int, arrival_secs: int) -> float:
    return distance_km * 3600 / get_time_between_stops_secs(departure_secs, arrival_secs)
```

### Consecutive-stop check: sliding window

In the consecutive check, `start` only advances to `end` when `end` has resolvable
coordinates. When `getDistanceKm` returns `None` (either stop has no coordinates),
`continue` is executed without updating `start`. This means the next iteration still
uses the original `start`, effectively bridging over the unresolvable stop.

### Far-stop check: early exit

The far-stop check must emit at most one notice per trip group and then return. Implement
with explicit `return` (or `break` from a loop with a flag) after the first emission.

### Guard clauses (ordering)

1. `"stop_times"` not in feed → return `[]`.
2. `"trips"` not in feed → return `[]`.
3. `"routes"` not in feed → return `[]`.
4. `"stops"` not in feed → return `[]`.
5. Any required table is empty → return `[]`.
6. Build stop lookup dict from `stops`.
7. Join `stop_times` with `trips` (on `trip_id`) then with `routes` (on `route_id`) to
   get `route_type` per stop time. Use a left join; unmatched trips produce null `route_type`
   and should be filtered out before the per-trip loop.
8. Sort by `["trip_id", "stop_sequence"]`.
9. Partition by `trip_id` and iterate.

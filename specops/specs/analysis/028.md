# Analysis: LocationIdForeignKeyValidator

## 1. Purpose

Validates that every `location_id` referenced in `stop_times.txt` exists as a feature `id` in `locations.geojson`.

## 2. Input tables

| Table | Columns used |
|---|---|
| `stop_times.txt` | `location_id`, `csvRowNumber` |
| `locations.geojson` | `id` (feature ID) |

### Key relationships

- `stop_times.location_id` is a foreign key referencing `locations.geojson` feature `id`.
- The `location_id` column in `stop_times.txt` is optional (conditionally required). The validator only runs if the column is present in the feed.

## 3. Validation logic

1. **Skip check**: Do not run if either table is missing or if `stop_times.txt` does not contain the `location_id` column (`shouldCallValidate` guard).

2. **For each row in `stop_times.txt`**:
   a. Read the `location_id` value.
   b. If empty/blank, skip (no FK to check).
   c. Look up the value in the `locations.geojson` feature ID map.
   d. If not found, emit `foreign_key_violation` (ERROR).

## 4. Notices emitted

### `foreign_key_violation` (ERROR)

| Field | Value |
|---|---|
| `childFilename` | `"stop_times.txt"` |
| `childFieldName` | `"location_id"` |
| `parentFilename` | `"locations.geojson"` |
| `parentFieldName` | `"id"` |
| `fieldValue` | The unmatched `location_id` value |
| `csvRowNumber` | Row number in `stop_times.txt` |

This is the shared `ForeignKeyViolationNotice` class used by all FK checks, not a custom notice.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `stop_times.txt` missing | Validator does not run (`shouldCallValidate` returns false) |
| `locations.geojson` missing | Validator does not run (`shouldCallValidate` returns false) |
| `location_id` column not present in `stop_times.txt` | Validator does not run (`shouldCallValidate` returns false) |
| `location_id` is empty string | Row is skipped, no notice emitted |
| `location_id` is null | Treated as empty by Java (field defaults to `""`), no notice emitted |
| All `location_id` values match | No notices emitted |
| Multiple rows reference same missing ID | One notice per row |

## 6. Test contracts

### `missingGeoJSONId_yieldsNotice`

- **Setup**: One GeoJSON feature with `id = "locationId"`. One stop time row (csvRowNumber=1) with `location_id = "locationId2"`.
- **Expected**: Exactly one `ForeignKeyViolationNotice` with `childFilename="stop_times.txt"`, `childFieldName="location_id"`, `parentFilename="locations.geojson"`, `parentFieldName="id"`, `fieldValue="locationId2"`, `csvRowNumber=1`.

### `existingGeoJSONId_yieldsNoNotice`

- **Setup**: One GeoJSON feature with `id = "locationId"`. One stop time row (csvRowNumber=1) with `location_id = "locationId"`.
- **Expected**: No notices.

## 7. Implementation notes

### Polars approach

This is a straightforward FK check that is well-suited to a Polars anti-join:

1. Filter `stop_times` to rows where `location_id` is non-null and non-empty.
2. Perform an anti-join against the GeoJSON features table on `location_id == id`.
3. Each unmatched row produces a `foreign_key_violation` notice.

### Considerations

- **GeoJSON representation**: The `locations.geojson` file is not a CSV table. In the Python implementation, it needs to be loaded as a DataFrame (or at minimum a set of feature IDs) so it can participate in joins. The current Python `schemas.py` does not yet define a schema for `locations.geojson` -- this may need to be handled as a special case or added.
- **Reuse of `foreign_key_violation`**: This notice code is already used by the load-time FK validation system. If `locations.geojson` FK relationships can be expressed in the schema registry, this check could potentially be handled by `load_validators.py` rather than as a standalone cross-table validator. However, because `locations.geojson` is not a CSV file and has a different loading path, a dedicated validator is likely the cleaner approach.
- **Column existence guard**: The `shouldCallValidate` check for column presence maps to checking whether `"location_id"` is in the DataFrame columns in Python. This matters because `location_id` is an optional/conditionally-required column.
- **Performance**: A single anti-join is O(n) and efficient. No row-by-row iteration needed.

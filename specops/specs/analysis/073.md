# Analysis: TransferStopIdsConditionalValidator

## 1. Purpose

Validates that `from_stop_id` and `to_stop_id` are present on every
`transfers.txt` row whose `transfer_type` is not an in-seat transfer type
(i.e., not type 4 or 5).

## 2. Input tables

| Table | Columns used |
|---|---|
| `transfers.txt` | `transfer_type`, `from_stop_id`, `to_stop_id`, `csv_row_number` |

No other tables are read. The validator is a single-table file validator.

### Column semantics

- `transfer_type` — integer enum; required. Values 0–3 are non-in-seat;
  values 4 (`IN_SEAT_TRANSFER_ALLOWED`) and 5 (`IN_SEAT_TRANSFER_NOT_ALLOWED`)
  are in-seat. The validator only processes a row when `transfer_type` is
  present (non-null).
- `from_stop_id` — conditionally required string (ID type); must be non-null
  for non-in-seat transfer types.
- `to_stop_id` — conditionally required string (ID type); must be non-null
  for non-in-seat transfer types.
- `csv_row_number` — row number from `transfers.txt`; carried into notices.

### Transfer type enum

| Integer value | Constant | In-seat? |
|---|---|---|
| 0 | `RECOMMENDED` | No |
| 1 | `TIMED` | No |
| 2 | `MINIMUM_TIME` | No |
| 3 | `IMPOSSIBLE` | No |
| 4 | `IN_SEAT_TRANSFER_ALLOWED` | Yes |
| 5 | `IN_SEAT_TRANSFER_NOT_ALLOWED` | Yes |

## 3. Validation logic

The validator iterates every row of `transfers.txt`. For each row:

```
for each transfer in transfers:
    if transfer.transfer_type IS NULL:
        skip row

    if transfer.transfer_type IN {4, 5}:   # in-seat types
        skip row                            # stop IDs are not required

    # non-in-seat transfer type — both stop IDs are required
    if transfer.from_stop_id IS NULL:
        emit MissingRequiredFieldNotice(filename="transfers.txt",
                                        csv_row_number=transfer.csv_row_number,
                                        field_name="from_stop_id")

    if transfer.to_stop_id IS NULL:
        emit MissingRequiredFieldNotice(filename="transfers.txt",
                                        csv_row_number=transfer.csv_row_number,
                                        field_name="to_stop_id")
```

Key behaviors:

- The two field checks are independent. A row with both `from_stop_id` and
  `to_stop_id` missing emits **two** notices (one per field).
- A row with only one of the two fields missing emits exactly one notice.
- Rows where `transfer_type` is null are skipped entirely (no notice
  emitted). This is the `hasTransferType()` guard in Java.
- In-seat rows (type 4 or 5) are unconditionally skipped regardless of
  whether `from_stop_id` or `to_stop_id` is present or absent.

## 4. Notices emitted

### `missing_required_field` (ERROR)

Emitted once per missing conditionally-required stop ID field on a
non-in-seat transfer row.

| Field | Type | Source | Description |
|---|---|---|---|
| `filename` | string | literal `"transfers.txt"` | File containing the offending row |
| `csv_row_number` | int | `transfers.csv_row_number` | Row number of the offending transfer |
| `field_name` | string | `"from_stop_id"` or `"to_stop_id"` | Name of the missing field |

Severity: ERROR.

Conditions:
- `transfer_type` IS NOT NULL, AND
- `transfer_type` NOT IN {4, 5}, AND
- `from_stop_id` IS NULL → one notice with `field_name="from_stop_id"`
- `to_stop_id` IS NULL → one notice with `field_name="to_stop_id"`

Both conditions are checked independently; a single row may produce zero,
one, or two notices.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `transfers.txt` absent from feed | Return `[]` immediately (guard). |
| `transfers.txt` present but empty (zero rows) | Return `[]` (loop body never executes). |
| `transfer_type` column absent from `transfers.txt` | All rows have `transfer_type` null; all rows are skipped; return `[]`. |
| Row has `transfer_type` null | Row is skipped; no notice. |
| Row has `transfer_type` 4 or 5 (in-seat) | Row is skipped; stop ID absence is not an error. |
| Row has `transfer_type` in {0,1,2,3} with both stop IDs present | No notice. |
| Row has `transfer_type` in {0,1,2,3} with `from_stop_id` null only | One `missing_required_field` notice for `from_stop_id`. |
| Row has `transfer_type` in {0,1,2,3} with `to_stop_id` null only | One `missing_required_field` notice for `to_stop_id`. |
| Row has `transfer_type` in {0,1,2,3} with both stop IDs null | Two `missing_required_field` notices (one per field). |
| Multiple rows, some passing and some failing | Each failing row produces its own independent notice(s). |

## 6. Test contracts

The Java test file contains three test methods.

### `testTransferFromStopIdNoInSeatTransferNoNotice`

- Iterates `transfer_type` values 4 and 5 (in-seat types).
- For each: builds a transfer with no `from_stop_id` or `to_stop_id` set.
- Expected: no validation notices.
- Confirms: in-seat transfer rows are fully exempt from the stop ID
  requirement, even when both IDs are absent.

### `testTransferMissingFromStopIdNoInSeatTransfer`

- Iterates `transfer_type` values 0, 1, 2, 3 (non-in-seat types).
- For each: builds a transfer with no `from_stop_id` or `to_stop_id` set.
- Expected: exactly two `MissingRequiredFieldNotice` instances:
  one for `from_stop_id` and one for `to_stop_id`.
- Confirms: both fields are independently checked and each absence produces
  its own notice.

### `testTransferFromStopIdNoInSeatTransfer`

- Iterates all `transfer_type` values 0 through 5.
- For each: builds a transfer with `from_stop_id="stop1"` and
  `to_stop_id="stop2"` both set.
- Expected: no validation notices.
- Confirms: when both stop IDs are present the validator is silent for all
  transfer types, including non-in-seat ones.

### What is NOT covered by the Java test suite

- Transfer row with `transfer_type` null (the `hasTransferType()` guard).
- Single-field missing (only `from_stop_id` null, or only `to_stop_id`
  null) for a non-in-seat type.
- `transfers.txt` entirely absent from the feed.
- `transfers.txt` present but empty (zero rows).
- Feed with multiple rows producing a mix of notices and clean rows.

## 7. Implementation notes

### Algorithm strategy

This is a straightforward single-table validator. All logic can be
expressed as a vectorized Polars filter followed by per-field null checks,
avoiding row-by-row Python iteration.

Recommended Polars approach:

```python
def validate_transfer_stop_ids_conditional(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "transfers" not in feed:
        return []

    transfers = feed["transfers"]

    if transfers.is_empty():
        return []

    required_cols = {"transfer_type", "from_stop_id", "to_stop_id", "csv_row_number"}
    if not required_cols.issubset(transfers.columns):
        return []

    # Only process rows with a non-null, non-in-seat transfer_type
    non_in_seat = transfers.filter(
        pl.col("transfer_type").is_not_null()
        & ~pl.col("transfer_type").is_in([4, 5])
    )

    notices: list[Notice] = []

    for field_name in ("from_stop_id", "to_stop_id"):
        missing = non_in_seat.filter(pl.col(field_name).is_null())
        for row in missing.select(["csv_row_number"]).iter_rows(named=True):
            notices.append(
                MissingRequiredFieldNotice(
                    filename="transfers.txt",
                    csv_row_number=row["csv_row_number"],
                    field_name=field_name,
                )
            )

    return notices
```

Alternatively, collect into Python lists in two separate Polars
`.filter(...).select(["csv_row_number"])` passes; both approaches are
equivalent and correct.

### Null semantics for `transfer_type`

In the Python implementation `transfer_type` will be cast to an integer
(nullable `Int64` or `Int32`). A null value means the column value was
absent or unparseable, and such rows must be skipped. The Polars expression
`pl.col("transfer_type").is_not_null()` handles this correctly.

### Notice dataclass

Reuse the existing `MissingRequiredFieldNotice` (already defined in
`notices.py` per the project memory). No new notice class is needed.

```python
@dataclass
class MissingRequiredFieldNotice:
    code: ClassVar[str] = "missing_required_field"
    severity: ClassVar[Severity] = Severity.ERROR
    filename: str
    csv_row_number: int
    field_name: str
```

Verify the field names match the existing implementation before coding.

### Feed dict keys

- `"transfers"` — `transfers.txt`

No other tables are required.

### Validator registration

Required tables: `["transfers"]`. No feature flag required.

### Ordering of notices

The Java implementation checks `from_stop_id` before `to_stop_id` on each
row (the `if (!transfer.hasFromStopId())` block precedes the
`if (!transfer.hasToStopId())` block). Preserve this ordering in the Python
output to remain behaviorally equivalent. Emitting `from_stop_id` notices
before `to_stop_id` notices across all rows is acceptable since the Java
validator processes one row at a time.

### Polars vs plain Python

Given the small table size typical of `transfers.txt` and the simple
null-check logic, a fully Polars-based approach (two `filter` + `iter_rows`
passes) is preferred over a row-by-row Python loop. Both are correct; the
Polars approach is more idiomatic per the project coding rules.

# Analysis: PickupBookingRuleIdValidator

## 1. Purpose

Warns when a `stop_times.txt` row has `pickup_type=2` (MUST_PHONE) with a `start_pickup_drop_off_window` but no `pickup_booking_rule_id`, or has `drop_off_type=2` (MUST_PHONE) with an `end_pickup_drop_off_window` but no `drop_off_booking_rule_id`.

## 2. Input tables

| Table | Columns used |
|---|---|
| `stop_times.txt` | `csv_row_number`, `pickup_type`, `drop_off_type`, `start_pickup_drop_off_window`, `end_pickup_drop_off_window`, `pickup_booking_rule_id`, `drop_off_booking_rule_id` |
| `booking_rules.txt` | (presence only — no columns read) |

The validator reads entity-level data from `stop_times.txt` and emits notices per row. It does not read any columns from `booking_rules.txt`; that table is referenced only in the guard to confirm it is present in the feed.

## 3. Validation logic

### Step 1: Guard — skip unless both tables are present and relevant columns exist

`shouldCallValidate()` returns `false` (skip entirely) unless:

1. `booking_rules.txt` is present and not missing.
2. `stop_times.txt` is present and not missing.
3. `stop_times.txt` has at least one of `pickup_type` or `drop_off_type` columns in its header.

In Python: if `"booking_rules"` is not in the feed dict, or `"stop_times"` is not in the feed dict, or neither `"pickup_type"` nor `"drop_off_type"` appear as columns in `feed["stop_times"]`, return `[]` immediately.

### Step 2: For each row in `stop_times.txt`, perform two independent sub-checks

#### Sub-check A — missing `pickup_booking_rule_id`

Trigger condition (all must be true):
- `pickup_type` is non-null AND equals `2` (MUST_PHONE)
- `start_pickup_drop_off_window` is non-null (i.e., the field is present and has a value)
- `pickup_booking_rule_id` is null or absent

If triggered, emit `missing_pickup_drop_off_booking_rule_id` with:
- `csv_row_number`: the row number of this `stop_times` record
- `pickup_type`: value `2` (MUST_PHONE)
- `drop_off_type`: the row's `drop_off_type` if present, else null

#### Sub-check B — missing `drop_off_booking_rule_id`

Trigger condition (all must be true):
- `drop_off_type` is non-null AND equals `2` (MUST_PHONE)
- `end_pickup_drop_off_window` is non-null (i.e., the field is present and has a value)
- `drop_off_booking_rule_id` is null or absent

If triggered, emit `missing_pickup_drop_off_booking_rule_id` with:
- `csv_row_number`: the row number of this `stop_times` record
- `pickup_type`: the row's `pickup_type` if present, else null
- `drop_off_type`: value `2` (MUST_PHONE)

Note: Both sub-checks are independent — a single row can trigger two notices if it violates both conditions simultaneously.

## 4. Notices emitted

### `missing_pickup_drop_off_booking_rule_id` (WARNING)

Emitted when a GTFS-Flex stop time uses `pickup_type=2` or `drop_off_type=2` (MUST_PHONE) within a pickup/drop-off window but does not reference a booking rule.

| Field | Type | Source | Description |
|---|---|---|---|
| `csvRowNumber` | integer | `stop_times.csv_row_number` | Row number of the offending record |
| `pickupType` | integer or null | `stop_times.pickup_type` | The pickup type value; null if `pickup_type` is absent from the row |
| `dropOffType` | integer or null | `stop_times.drop_off_type` | The drop-off type value; null if `drop_off_type` is absent from the row |

Severity: WARNING.

Java class: `MissingPickupDropOffBookingRuleIdNotice`.

Referenced files: `stop_times.txt`.

The notice code in Python should be `missing_pickup_drop_off_booking_rule_id`.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `booking_rules.txt` absent from feed | Guard returns false; no notices emitted. |
| `stop_times.txt` absent from feed | Guard returns false; no notices emitted. |
| `stop_times.txt` present but has neither `pickup_type` nor `drop_off_type` columns | Guard returns false; no notices emitted. |
| `stop_times.txt` has `pickup_type` but not `drop_off_type` | Guard passes (pickup_type column present); sub-check A runs; sub-check B never fires because `drop_off_type` is always null. |
| `pickup_type` is null for a row | Sub-check A skipped for that row (null fails the `hasPickupType()` guard). |
| `drop_off_type` is null for a row | Sub-check B skipped for that row (null fails the `hasDropOffType()` guard). |
| `pickup_type=2` but `start_pickup_drop_off_window` is null | Sub-check A does not fire — window field must be present. |
| `drop_off_type=2` but `end_pickup_drop_off_window` is null | Sub-check B does not fire — window field must be present. |
| `pickup_type=2`, window present, `pickup_booking_rule_id` present | Sub-check A does not fire — booking rule ID satisfies the requirement. |
| `pickup_type=1` (NOT_AVAILABLE) | Sub-check A does not fire — type is not MUST_PHONE. |
| `pickup_type=0` (REGULAR) | Sub-check A does not fire. |
| `pickup_type=3` (ON_REQUEST_TO_DRIVER) | Sub-check A does not fire. |
| Both sub-checks trigger on the same row | Two notices emitted for that row (each notice carries the other type's value in the sibling field). |
| `stop_times.txt` empty | No rows to iterate; no notices. |

## 6. Test contracts

### `missingBookingRuleIdShouldGenerateNotice`

Setup:
- Stop time row: `csv_row_number=1`, `pickup_type=2` (MUST_PHONE), `start_pickup_drop_off_window=18614s` (present), no `pickup_booking_rule_id`.

Expected: exactly 1 notice of type `MissingPickupDropOffBookingRuleIdNotice` with `csvRowNumber=1`, `pickupType=MUST_PHONE` (2), `dropOffType=null`.

Explanation: Condition A fires because pickup_type is MUST_PHONE, window is set, and no booking rule ID is present. `drop_off_type` was never set so it is null in the notice.

### `existingBookingRuleIdShouldNotGenerateNotice`

Setup:
- Stop time row: `csv_row_number=2`, `pickup_type=2` (MUST_PHONE), `start_pickup_drop_off_window=18614s`, `pickup_booking_rule_id="booking_rule_id"` (present).

Expected: no notices.

Explanation: Sub-check A does not fire because `pickup_booking_rule_id` is set.

### `pickUpTypeNotMustPhoneShouldNotGenerateNotice`

Setup:
- Stop time row: `csv_row_number=3`, `pickup_type=1` (NOT_AVAILABLE), no window fields.

Expected: no notices.

Explanation: `pickup_type` is not MUST_PHONE (2); sub-check A does not apply. `drop_off_type` is unset; sub-check B does not apply.

## 7. Implementation notes

### Algorithm choice

The logic is per-row and does not require cross-row joins. Each row is evaluated independently with two filter conditions. Polars filter expressions are well-suited for both sub-checks.

### Recommended Polars approach

Perform each sub-check as a filtered scan of `stop_times`:

```python
# Sub-check A: missing pickup_booking_rule_id
pickup_violations = feed["stop_times"].filter(
    pl.col("pickup_type").eq(2)
    & pl.col("start_pickup_drop_off_window").is_not_null()
    & pl.col("pickup_booking_rule_id").is_null()
)

# Sub-check B: missing drop_off_booking_rule_id
dropoff_violations = feed["stop_times"].filter(
    pl.col("drop_off_type").eq(2)
    & pl.col("end_pickup_drop_off_window").is_not_null()
    & pl.col("drop_off_booking_rule_id").is_null()
)
```

Iterate over rows of each violation DataFrame using `.iter_rows(named=True)` and construct a notice per row. The notice fields `pickup_type` and `drop_off_type` carry the sibling column's value (or null if the column is absent or null in that row).

### Column presence guard

The `pickup_type` and `drop_off_type` columns are optional in `stop_times.txt`. Before filtering, check whether each column is present in the DataFrame:

- If `pickup_type` column is absent, skip sub-check A entirely (or treat it as always null).
- If `drop_off_type` column is absent, skip sub-check B entirely.
- If neither column is present, return early (matches `shouldCallValidate()` behavior).

The window columns `start_pickup_drop_off_window` and `end_pickup_drop_off_window` are also optional; treat absent columns as all-null (no filter matches).

### Null semantics

- `pickup_type` null → treated as absent; sub-check A does not fire.
- `drop_off_type` null → treated as absent; sub-check B does not fire.
- `start_pickup_drop_off_window` null → sub-check A does not fire for that row.
- `end_pickup_drop_off_window` null → sub-check B does not fire for that row.
- When constructing a notice for sub-check A violation: `drop_off_type` in the notice = the row's `drop_off_type` value (which may be null).
- When constructing a notice for sub-check B violation: `pickup_type` in the notice = the row's `pickup_type` value (which may be null).

### `pickup_type` / `drop_off_type` enum values

| Name | Integer |
|---|---|
| REGULAR | 0 |
| NOT_AVAILABLE | 1 |
| MUST_PHONE | 2 |
| ON_REQUEST_TO_DRIVER | 3 |

Only integer value `2` triggers either sub-check.

### Feed dict keys

- `"stop_times"` — `stop_times.txt`
- `"booking_rules"` — `booking_rules.txt`

### Required columns

From `stop_times.txt` (all optional; guard appropriately):
- `csv_row_number`
- `pickup_type`
- `drop_off_type`
- `start_pickup_drop_off_window`
- `end_pickup_drop_off_window`
- `pickup_booking_rule_id`
- `drop_off_booking_rule_id`

### Notice code mapping

| Java class | Python notice code |
|---|---|
| `MissingPickupDropOffBookingRuleIdNotice` | `missing_pickup_drop_off_booking_rule_id` |

### Validator registration

Requires tables: `["stop_times", "booking_rules"]`.

Guard: skip if `"booking_rules"` absent, `"stop_times"` absent, or `stop_times` DataFrame has neither `pickup_type` nor `drop_off_type` columns.

### GTFS-Flex context

This validator is scoped to GTFS-Flex feeds. The window fields (`start_pickup_drop_off_window`, `end_pickup_drop_off_window`) are Flex-specific. The spec comment in the Java source notes: this recommendation was added for feeds with GTFS-Flex, which is why the window field is a required co-condition rather than checking `pickup_type=2` alone.

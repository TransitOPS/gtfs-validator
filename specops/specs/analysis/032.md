# Analysis: MissingFeedInfoValidator

## 1. Purpose

Validates that `feed_info.txt` is present in the GTFS feed; emits a WARNING if it is missing without `translations.txt`, or an ERROR if it is missing while `translations.txt` is present.

## 2. Input tables

| Table | Columns used |
|---|---|
| `feed_info.txt` | None (only file presence is checked) |
| `translations.txt` | None (only file presence is checked) |

No column values are read. The validator only inspects whether each file was found in the feed.

## 3. Validation logic

1. **Check feed_info.txt presence**: Determine whether `feed_info.txt` is absent from the feed (i.e., its table status is `MISSING_FILE`).
2. **If feed_info.txt is present**: No notices. Validation is done.
3. **If feed_info.txt is absent, check translations.txt presence**:
   - If `translations.txt` is also absent: emit `missing_recommended_file` (WARNING) for `feed_info.txt`.
   - If `translations.txt` is present: emit `missing_required_file` (ERROR) for `feed_info.txt`.

The rationale behind this escalation: `feed_info.txt` is recommended but not strictly required in a plain feed. However, `translations.txt` references `feed_info.txt` (specifically the `feed_lang` field), so if translations are present, `feed_info.txt` becomes required.

### Critical distinction: missing vs. empty

`isMissingFile()` in the Java framework checks strictly for `TableStatus.MISSING_FILE`. A file that is present but has zero data rows or is completely empty does NOT count as missing. Only total absence of the file from the feed triggers this check.

In the Python implementation, the equivalent is checking whether the key is absent from the `feed` dict. An empty DataFrame for a key that is present does not trigger either notice.

## 4. Notices emitted

### `missing_recommended_file` (WARNING)

`feed_info.txt` is absent and `translations.txt` is also absent. `feed_info.txt` is recommended but not strictly required.

| Field | Type | Description |
|---|---|---|
| `filename` | string | The name of the missing file — always `"feed_info.txt"`. |

Conditions: Fires when `feed_info.txt` is missing AND `translations.txt` is missing.

### `missing_required_file` (ERROR)

`feed_info.txt` is absent but `translations.txt` is present. Because `translations.txt` depends on fields in `feed_info.txt`, the latter becomes required.

| Field | Type | Description |
|---|---|---|
| `filename` | string | The name of the missing file — always `"feed_info.txt"`. |

Conditions: Fires when `feed_info.txt` is missing AND `translations.txt` is present.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `feed_info.txt` present, `translations.txt` present | No notice |
| `feed_info.txt` present, `translations.txt` absent | No notice |
| `feed_info.txt` absent, `translations.txt` absent | WARNING (`missing_recommended_file`) for `feed_info.txt` |
| `feed_info.txt` absent, `translations.txt` present | ERROR (`missing_required_file`) for `feed_info.txt` |
| `feed_info.txt` present but empty (zero rows) | No notice — file is present, not missing |
| `feed_info.txt` present with headers but zero data rows | No notice — file is present, not missing |
| `translations.txt` present but empty | No notice when `feed_info.txt` is also present; ERROR when `feed_info.txt` is absent (the file is present regardless of row count) |

The guard is purely about file presence. Content, row count, and parse validity are irrelevant to this validator.

## 6. Test contracts

### `missingFeedInfoTranslationTableNotPresent`

- **Setup**: `feed_info.txt` has status `MISSING_FILE`. `translations.txt` has status `MISSING_FILE`.
- **Expected**: Exactly one `MissingRecommendedFileNotice` with `filename = "feed_info.txt"`.

### `missingFeedInfoWhenTranslationTableIsPresent`

- **Setup**: `feed_info.txt` has status `MISSING_FILE`. `translations.txt` has status `PARSABLE_HEADERS_AND_ROWS`.
- **Expected**: Contains `MissingRequiredFileNotice` with `filename = "feed_info.txt"`.

### `feedInfoPresentShouldGenerateNoNotice`

- **Setup**: `feed_info.txt` has status `PARSABLE_HEADERS_AND_ROWS`. `translations.txt` has status `PARSABLE_HEADERS_AND_ROWS`.
- **Expected**: No notices.

Note: The test suite does not include a case where `feed_info.txt` is present and `translations.txt` is absent, but by the logic this would also produce no notices.

## 7. Implementation notes

### Approach

This validator requires no Polars operations. It is a pure presence check on the `feed` dict keys.

```python
def validate_missing_feed_info(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "feed_info" in feed:
        return []
    if "translations" not in feed:
        return [Notice(
            code="missing_recommended_file",
            severity="WARNING",
            filename="feed_info.txt",
        )]
    return [Notice(
        code="missing_required_file",
        severity="ERROR",
        filename="feed_info.txt",
    )]
```

### Key implementation considerations

- **Key naming**: In the Python feed dict, table keys use the filename stem without `.txt` (e.g., `"feed_info"` and `"translations"`). Confirm this matches the rest of the codebase conventions.
- **Notice `filename` field**: Both notices carry a `filename` field with the value `"feed_info.txt"` (including the `.txt` extension), matching `GtfsFeedInfo.FILENAME` in Java. This is a named string field, not just an implicit property.
- **Two distinct notice codes**: Unlike the similar `MissingCalendarAndCalendarDateValidator` which emits a single notice type, this validator emits one of two different notice types depending on a second table's presence. Ensure both `missing_recommended_file` and `missing_required_file` are registered notice codes in the Python notice registry.
- **No column access**: Do not read any column values from either table.
- **Plain Python, no Polars**: No tabular operations are needed. Do not use Polars expressions for this validator.
- **Severity escalation pattern**: The logic mirrors how the Java `FileValidator` subclass uses two different notice constructors. The Python equivalent is two different return values conditioned on a second presence check.
- **Shared notice codes**: `missing_recommended_file` and `missing_required_file` are general-purpose notice codes that accept a `filename` field. They are shared across multiple validators (e.g., `MissingCalendarAndCalendarDateValidator` uses its own dedicated code). Confirm that the Python implementation uses the general shared codes here, not a dedicated one.

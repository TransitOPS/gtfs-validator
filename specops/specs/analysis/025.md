# Analysis: InconsistentRouteTypeForBlockIdValidator

## 1. Purpose

Warns when trips sharing the same `block_id` are associated with routes that have different `route_type` values, indicating mixed modes within a single vehicle block.

## 2. Input tables

| Table | Columns used |
|---|---|
| `trips.txt` | `block_id`, `route_id` |
| `routes.txt` | `route_id`, `route_type` |

### Key relationships

- `trips.route_id` is a foreign key to `routes.route_id`.
- Trips are grouped by `block_id`; each group is checked for consistent `route_type` across its associated routes.

## 3. Validation logic

1. **Guard clause**: Skip validation entirely if:
   - `trips.txt` is missing or empty.
   - `routes.txt` is missing or empty.
   - `trips.txt` does not contain a `block_id` column.
2. Group all trips by `block_id`.
3. For each group where `block_id` is non-null and non-empty:
   a. Look up each trip's `route_id` in `routes.txt` to get its `route_type`.
   b. Skip any trip whose `route_id` does not resolve to a route (filter out unmatched).
   c. Collect the **distinct** set of `route_type` values for the block.
   d. If there are **more than one** distinct `route_type`, emit a notice.
4. The notice includes:
   - The `block_id`.
   - The distinct `route_id` values in the block (comma-separated).
   - The distinct `route_type` values in the block (comma-separated).

## 4. Notices emitted

| Code | Severity | Fields | Condition |
|---|---|---|---|
| `inconsistent_route_type_for_block_id` | WARNING | `blockId` (str), `routeIds` (str, comma-separated), `routeTypes` (str, comma-separated) | A block_id has trips whose routes have more than one distinct route_type |

### Notice field details

- `blockId`: The `block_id` value of the affected group.
- `routeIds`: Comma-separated list of distinct `route_id` values for trips in the block.
- `routeTypes`: Comma-separated list of distinct `route_type` values (as their integer/enum string representation).

In the Python implementation, field names should follow snake_case convention:
- `block_id`, `route_ids`, `route_types`.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `trips.txt` missing | Skip validation, no notices |
| `routes.txt` missing | Skip validation, no notices |
| `block_id` column absent from trips | Skip validation, no notices |
| `block_id` is null or empty string | Skip that group, no notice |
| Trip's `route_id` not found in `routes.txt` | Trip is excluded from the route_type set for the block (FK violation is handled elsewhere) |
| All trips in a block map to the same route_type | No notice |
| Block has only one trip | Only one route_type possible, no notice |
| Multiple blocks, some consistent, some not | Emit one notice per inconsistent block |
| Multiple trips share the same route_id within a block | That route_id and route_type appear only once in the distinct sets |

## 6. Test contracts

### Test: `sameRouteTypeForBlockIdDoesNotGenerateNotice`

- **Setup**: Two routes (`r0`, `r1`) both with type `BUS`. Two trips (`t0`, `t1`) both in block `b0`, referencing `r0` and `r1` respectively.
- **Expected**: No notices emitted.

### Test: `differentRouteTypeForBlockIdGeneratesNotice`

- **Setup**: Two routes (`r0` = `BUS`, `r1` = `RAIL`). Two trips (`t0`, `t1`) both in block `b0`, referencing `r0` and `r1` respectively.
- **Expected**: Exactly one notice emitted.

### Additional test cases to implement in Python

- Block with null/empty `block_id` -- no notice.
- Multiple blocks where only some are inconsistent -- only inconsistent blocks produce notices.
- Trip whose `route_id` has no matching route -- excluded from check, no crash.
- Empty trips table -- no notices.
- Single trip in a block -- no notice.

## 7. Implementation notes

### Polars approach (recommended)

This validator is well-suited to a fully vectorized Polars implementation:

1. **Join** `trips` with `routes` on `route_id` to attach `route_type` to each trip.
2. **Filter** to rows where `block_id` is not null and not empty string.
3. **Group by** `block_id` and aggregate:
   - `n_distinct(route_type)` to count distinct route types.
   - Collect distinct `route_id` values into a list.
   - Collect distinct `route_type` values into a list.
4. **Filter** groups where `n_distinct(route_type) > 1`.
5. **Emit** one notice per remaining row.

```python
def validate_inconsistent_route_type_for_block_id(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
    trips = feed.get("trips")
    routes = feed.get("routes")
    if trips is None or routes is None:
        return []
    if "block_id" not in trips.columns:
        return []
    if trips.is_empty() or routes.is_empty():
        return []

    joined = trips.select("block_id", "route_id").join(
        routes.select("route_id", "route_type"),
        on="route_id",
        how="inner",  # drops trips with unmatched route_id
    )

    filtered = joined.filter(
        pl.col("block_id").is_not_null()
        & (pl.col("block_id") != "")
    )

    agg = filtered.group_by("block_id").agg(
        pl.col("route_type").n_unique().alias("n_types"),
        pl.col("route_id").unique().alias("route_ids"),
        pl.col("route_type").unique().alias("route_types"),
    )

    bad = agg.filter(pl.col("n_types") > 1)

    notices = []
    for row in bad.iter_rows(named=True):
        notices.append(Notice(
            code="inconsistent_route_type_for_block_id",
            severity=Severity.WARNING,
            block_id=row["block_id"],
            route_ids=", ".join(str(r) for r in sorted(row["route_ids"])),
            route_types=", ".join(str(t) for t in sorted(row["route_types"])),
        ))
    return notices
```

### Key considerations

- The inner join naturally excludes trips whose `route_id` does not exist in `routes.txt`, matching the Java behavior of filtering out `Optional.empty()`.
- Use `n_unique()` rather than collecting to a Python set for the size check -- only materialize the list values for the notice fields.
- Sort the comma-separated values in notice fields for deterministic output.
- The `iter_rows` loop over the bad blocks is acceptable since the number of inconsistent blocks is expected to be very small relative to total data size.

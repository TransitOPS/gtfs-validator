# Analysis: TransfersStopTypeValidator

## 1. Purpose

Validates that `transfers.from_stop_id` and `transfers.to_stop_id` reference stops with a `location_type` of 0 (Stop/Platform) or 1 (Station); any other location type is an error.

## 2. Input tables

| Table | Columns used |
|---|---|
| `transfers.txt` | `from_stop_id`, `to_stop_id`, `csv_row_number` |
| `stops.txt` | `stop_id`, `location_type` |

### Column semantics

- `from_stop_id` / `to_stop_id` — string foreign keys into `stops.stop_id`; may be absent/null (FK absence is validated elsewhere).
- `csv_row_number` — row number from `transfers.txt`; carried into notices.
- `stop_id` in `stops.txt` — the identifier used for lookup.
- `location_type` in `stops.txt` — integer enum (0–4); determines whether the stop is a valid transfer endpoint.

### Location type enum

| Integer value | Constant | Valid transfer stop? |
|---|---|---|
| 0 | `STOP` | Yes |
| 1 | `STATION` | Yes |
| 2 | `ENTRANCE` | No |
| 3 | `GENERIC_NODE` | No |
| 4 | `BOARDING_AREA` | No |

## 3. Validation logic

The validator iterates every row of `transfers.txt`. For each row, both directions (`from_stop_id` and `to_stop_id`) are checked independently using the same logic:

```
for each transfer in transfers:
    for direction in [TRANSFER_FROM, TRANSFER_TO]:
        stop_id = transfer.from_stop_id if direction == FROM else transfer.to_stop_id

        if stop_id NOT IN stops:
            # FK validation is handled by a separate FK validator; skip
            continue

        location_type = stops[stop_id].location_type

        if location_type NOT IN {0, 1}:  # not STOP and not STATION
            emit TransferWithInvalidStopLocationTypeNotice(
                csv_row_number=transfer.csv_row_number,
                stop_id_field_name="from_stop_id" if direction == FROM else "to_stop_id",
                stop_id=stop_id,
                location_type_value=location_type,
                location_type_name=name_of(location_type))
```

### Important ordering details

- Both directions are always checked for every transfer row, regardless of the result for the other direction.
- The FROM direction is checked before the TO direction for each row.
- No filtering on `transfer_type` — this validator applies to all rows in `transfers.txt` (contrast with `TransfersInSeatTransferTypeValidator` which restricts to types 4 and 5).
- The stop lookup is a pure existence check: if the stop ID is not found in `stops.txt`, the check is silently skipped.

## 4. Notices emitted

### `transfer_with_invalid_stop_location_type` (ERROR)

Emitted when a stop referenced by `from_stop_id` or `to_stop_id` in `transfers.txt` has a `location_type` other than 0 (STOP) or 1 (STATION).

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | int | `transfers.csv_row_number` | Row number of the offending transfer |
| `stop_id_field_name` | string | `"from_stop_id"` or `"to_stop_id"` | Name of the stop ID field with the invalid reference |
| `stop_id` | string | `transfers.from_stop_id` or `to_stop_id` | The referenced stop ID |
| `location_type_value` | int | `stops.location_type` | Numeric value of the invalid location type |
| `location_type_name` | string | `stops.location_type` name | String name of the invalid location type (e.g., `"ENTRANCE"`, `"GENERIC_NODE"`, `"BOARDING_AREA"`) |

Severity: ERROR.

Conditions:
- Stop ID is found in `stops.txt`, AND
- `location_type` is NOT 0 (STOP) and NOT 1 (STATION).

A single transfer row may produce zero, one, or two notices of this type (one per direction).

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `transfers.txt` absent from feed | Return `[]` immediately (guard in runner). |
| `transfers.txt` present but empty | Return `[]` (loop body never executes). |
| `stops.txt` absent from feed | All stop lookups produce no result; all rows are silently skipped. |
| `from_stop_id` or `to_stop_id` is null/absent | Stop lookup returns nothing; that direction is silently skipped. FK absence validated elsewhere. |
| Stop ID not found in `stops.txt` | Silently skipped for that direction; FK validation handles the missing reference. |
| `location_type` is 0 (STOP) | Valid; no notice emitted. |
| `location_type` is 1 (STATION) | Valid; no notice emitted. |
| `location_type` is 2 (ENTRANCE) | Invalid; `TransferWithInvalidStopLocationTypeNotice` with `location_type_value=2`, `location_type_name="ENTRANCE"`. |
| `location_type` is 3 (GENERIC_NODE) | Invalid; `TransferWithInvalidStopLocationTypeNotice` with `location_type_value=3`, `location_type_name="GENERIC_NODE"`. |
| `location_type` is 4 (BOARDING_AREA) | Invalid; `TransferWithInvalidStopLocationTypeNotice` with `location_type_value=4`, `location_type_name="BOARDING_AREA"`. |
| Both `from_stop_id` and `to_stop_id` are invalid | Two notices emitted (one for each direction), FROM direction first. |
| Same stop ID used in multiple transfers | Each transfer row is validated independently; a bad stop produces a notice for each transfer referencing it. |
| `transfer_type` is 4 or 5 (in-seat) | This validator still checks both stop IDs, with the same rule (STOP and STATION are valid). The in-seat-specific stricter rule (STATION also forbidden) is applied only by `TransfersInSeatTransferTypeValidator`. |

## 6. Test contracts

The Java test file contains two test methods.

### `testStopToStationTransfer`

- Builds two stops: `s0` with `location_type=STOP` (0), `s1` with `location_type=STATION` (1).
- Builds one transfer: `from_stop_id=s0`, `to_stop_id=s1`, `transfer_type=RECOMMENDED`.
- Expected: zero notices.
- Confirms: both STOP and STATION are valid transfer stop types; a transfer between them produces no errors.

### `testEntranceToGenericNodeTransfer`

- Builds two stops: `s0` with `location_type=ENTRANCE` (2), `s1` with `location_type=GENERIC_NODE` (3).
- Builds one transfer with `csv_row_number=2`: `from_stop_id=s0`, `to_stop_id=s1`, `transfer_type=RECOMMENDED`.
- Expected: exactly two `TransferWithInvalidStopLocationTypeNotice` instances:
  1. Direction `TRANSFER_FROM`: `stop_id_field_name="from_stop_id"`, `stop_id="s0"`, `location_type=ENTRANCE`.
  2. Direction `TRANSFER_TO`: `stop_id_field_name="to_stop_id"`, `stop_id="s1"`, `location_type=GENERIC_NODE`.
- Confirms: ENTRANCE and GENERIC_NODE are both invalid; both directions fail independently and both notices are emitted for the same row.

### What is NOT covered by the Java test suite

- `transfers.txt` absent (guard clause).
- `stops.txt` absent.
- Null/absent `from_stop_id` or `to_stop_id`.
- Stop ID not found in `stops.txt` (FK-miss skip).
- `location_type=4` (BOARDING_AREA).
- Transfers with `transfer_type` 4 or 5 (in-seat); the interaction with `TransfersInSeatTransferTypeValidator` is not exercised here.
- Multiple transfer rows where some pass and some fail.

## 7. Implementation notes

### Algorithm strategy

The validator performs two left-joins: one from `transfers.from_stop_id` to `stops.stop_id`, and one from `transfers.to_stop_id` to `stops.stop_id`. Since `transfers.txt` is typically small, a plain Python row-by-row approach over a pre-built stops dict is equally acceptable and easier to read.

Recommended approach:

1. Guard-return if `"transfers"` or `"stops"` is not in `feed`.
2. Build a Python dict `stops_by_id: dict[str, int]` mapping `stop_id -> location_type` from `stops.txt`.
3. Iterate each transfer row in Python, checking both `from_stop_id` and `to_stop_id` against the dict.

Alternative Polars approach using joins:

```python
# Left join on from_stop_id, then on to_stop_id; filter for invalid location types
from_joined = transfers.join(
    stops.select(["stop_id", "location_type"]),
    left_on="from_stop_id", right_on="stop_id", how="left"
).filter(
    pl.col("location_type").is_not_null() & ~pl.col("location_type").is_in([0, 1])
)
```

The join approach is clean but produces two separate filtered DataFrames that must then be iterated to build notices with the correct `stop_id_field_name` per direction. The row-by-row approach is simpler given the small size of `transfers.txt` in practice.

### Lookup dict construction

```python
stops_df = feed.get("stops")
stops_by_id: dict[str, int] = {}
if stops_df is not None and "stop_id" in stops_df.columns and "location_type" in stops_df.columns:
    for row in stops_df.select(["stop_id", "location_type"]).iter_rows(named=True):
        if row["stop_id"] is not None:
            stops_by_id[row["stop_id"]] = row["location_type"]
```

### Valid location types

```python
VALID_TRANSFER_LOCATION_TYPES = {0, 1}  # STOP, STATION
```

### Location type name mapping

```python
LOCATION_TYPE_NAMES = {
    0: "STOP",
    1: "STATION",
    2: "ENTRANCE",
    3: "GENERIC_NODE",
    4: "BOARDING_AREA",

```

### Notice dataclass

```python
@dataclass
class TransferWithInvalidStopLocationTypeNotice:
    code: ClassVar[str] = "transfer_with_invalid_stop_location_type"
    severity: ClassVar[Severity] = Severity.ERROR
    csv_row_number: int
    stop_id_field_name: str   # "from_stop_id" or "to_stop_id"
    stop_id: str
    location_type_value: int
    location_type_name: str
```

Note: This same notice class is used by `TransfersInSeatTransferTypeValidator` (074). Define it once in `notices.py` and import from both validators.

### Guard clauses

```python
def validate_transfers_stop_type(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "transfers" not in feed:
        return []
    transfers = feed["transfers"]
    if transfers.is_empty():
        return []
```

### Direction iteration

Process directions in order: FROM (field `"from_stop_id"`) then TO (field `"to_stop_id"`) for each row, matching Java behavior.

### Feed dict keys

- `"transfers"` — `transfers.txt`
- `"stops"` — `stops.txt`

### Validator registration

Required tables: `["transfers", "stops"]`. No feature flag required. This validator runs on any feed that includes both `transfers.txt` and `stops.txt`.

### Relationship to other validators

- `TransfersInSeatTransferTypeValidator` (074): uses the same `TransferWithInvalidStopLocationTypeNotice` but with a stricter rule for in-seat transfers — it forbids STATION (1) in addition to all non-STOP/STATION types. The current validator (075) permits STATION for all transfer types.
- FK validators for `transfers.from_stop_id` / `transfers.to_stop_id`: handle the case where the stop ID does not exist in `stops.txt` at all. This validator defers to them by silently skipping any unresolvable stop ID.

### Polars vs plain Python

The validator is naturally row-by-row (two lookups per row, two possible notice objects per row). Per project conventions, plain Python iteration is acceptable here because `transfers.txt` is small and the logic is not a vectorized operation. Polars is used for loading and for building the stops lookup dict efficiently.

# Analysis: FareTransferRuleTransferCountValidator

## 1. Purpose

Validates that `transfer_count` in `fare_transfer_rules.txt` is present when required and absent when forbidden, and that its value is valid when it is present.

The GTFS spec ties the requirement and legality of `transfer_count` to whether `from_leg_group_id` and `to_leg_group_id` are equal:

- When `from_leg_group_id` equals `to_leg_group_id` (a "self-loop" fare transfer rule): `transfer_count` is **required** and must be a valid value.
- When `from_leg_group_id` does not equal `to_leg_group_id` (or either is absent): `transfer_count` is **forbidden**.

Three distinct error conditions are detected:

1. Both leg group IDs are equal, `transfer_count` is present, but its value is invalid (not ≥ 1 and not equal to -1).
2. Both leg group IDs are equal, but `transfer_count` is absent.
3. The two leg group IDs are not equal (or at least one is absent), but `transfer_count` is present.

The validator processes each row independently with no cross-row or cross-table state.

## 2. Input tables

| Table | Columns used |
|---|---|
| `fare_transfer_rules.txt` | `from_leg_group_id`, `to_leg_group_id`, `transfer_count`, `csv_row_number` |

### Schema reference

`fare_transfer_rules.txt` (`GtfsFareTransferRuleSchema`):

| Column | Type | Constraint |
|---|---|---|
| `from_leg_group_id` | ID (string) | Optional, FK → `fare_leg_rules.leg_group_id`, part of composite PK |
| `to_leg_group_id` | ID (string) | Optional, FK → `fare_leg_rules.leg_group_id`, part of composite PK |
| `duration_limit` | positive integer | Optional (conditionally required), part of composite PK |
| `duration_limit_type` | enum (`GtfsDurationLimitType`) | Conditionally required |
| `fare_transfer_type` | enum (`GtfsFareTransferType`) | Required |
| `transfer_count` | integer | Conditionally required, part of composite PK |
| `fare_product_id` | ID (string) | Optional, FK → `fare_products.fare_product_id`, part of composite PK |

## 3. Validation logic

### Skip condition

None. The validator runs for every row in `fare_transfer_rules.txt`. If the table is absent or empty, no rows are processed and no notices are emitted.

### Algorithm

The validator is a `SingleEntityValidator`, meaning it operates on each row independently. For each row in `fare_transfer_rules.txt`:

**Branch A — both leg group IDs are present and equal (`from_leg_group_id` is set AND `to_leg_group_id` is set AND `from_leg_group_id == to_leg_group_id`):**

1. If `transfer_count` is present:
   - If `transfer_count < -1` OR `transfer_count == 0`: emit `fare_transfer_rule_invalid_transfer_count` with `csv_row_number` and `transfer_count`.
   - Otherwise (`transfer_count == -1` or `transfer_count >= 1`): valid, no notice.
2. If `transfer_count` is absent: emit `fare_transfer_rule_without_transfer_count` with `csv_row_number`.

**Branch B — the leg group IDs are not equal, or at least one is absent (all other cases):**

1. If `transfer_count` is present: emit `fare_transfer_rule_with_forbidden_transfer_count` with `csv_row_number`.
2. If `transfer_count` is absent: valid, no notice.

### Valid `transfer_count` values

The only valid values under Branch A are:
- `-1` (unlimited transfers)
- Any positive integer ≥ 1

Invalid values are:
- `0` (explicitly excluded)
- Any integer less than `-1` (e.g., -2, -3, …)

### Pseudocode

```
for each row in fare_transfer_rules:
    if row.from_leg_group_id is not null
    AND row.to_leg_group_id is not null
    AND row.from_leg_group_id == row.to_leg_group_id:
        if row.transfer_count is not null:
            if row.transfer_count < -1 OR row.transfer_count == 0:
                emit fare_transfer_rule_invalid_transfer_count(
                    csv_row_number=row.csv_row_number,
                    transfer_count=row.transfer_count,
                )
        else:
            emit fare_transfer_rule_without_transfer_count(
                csv_row_number=row.csv_row_number,
            )
    else:
        if row.transfer_count is not null:
            emit fare_transfer_rule_with_forbidden_transfer_count(
                csv_row_number=row.csv_row_number,
            )
```

### What is NOT checked here

- Whether `from_leg_group_id` or `to_leg_group_id` reference valid entries in `fare_leg_rules.leg_group_id` (FK check, handled at load time).
- Whether `fare_transfer_type` is present and a valid enum value (handled at load time).
- Whether `duration_limit` and `duration_limit_type` are mutually consistent (handled by `FareTransferRuleDurationLimitTypeValidator`).
- Composite PK uniqueness for `(from_leg_group_id, to_leg_group_id, fare_product_id, transfer_count, duration_limit)` (handled at load time).
- Cross-table relationships beyond the field-level checks described above.

## 4. Notices emitted

### `fare_transfer_rule_invalid_transfer_count`

Severity: **ERROR**

Emitted when both leg group IDs are equal and `transfer_count` is present but its value is invalid (i.e., `transfer_count < -1` or `transfer_count == 0`).

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending row |
| `transfer_count` | int | The invalid `transfer_count` value from the offending row |

### `fare_transfer_rule_without_transfer_count`

Severity: **ERROR**

Emitted when both leg group IDs are equal but `transfer_count` is absent. The spec requires `transfer_count` when `from_leg_group_id == to_leg_group_id`.

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending row |

### `fare_transfer_rule_with_forbidden_transfer_count`

Severity: **ERROR**

Emitted when the two leg group IDs are not equal (or at least one is absent) but `transfer_count` is present. The spec forbids `transfer_count` in that case.

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending row |

## 5. Edge cases

- **`transfer_count == 1`** (minimum valid positive value): No notice when leg IDs are equal.
- **`transfer_count == -1`** (unlimited, sentinel value): No notice when leg IDs are equal.
- **`transfer_count == 0`**: Invalid; emits `fare_transfer_rule_invalid_transfer_count` when leg IDs are equal.
- **`transfer_count == -2`** (or any value < -1): Invalid; emits `fare_transfer_rule_invalid_transfer_count` when leg IDs are equal.
- **`from_leg_group_id == to_leg_group_id`, `transfer_count` absent**: Emits `fare_transfer_rule_without_transfer_count`.
- **`from_leg_group_id != to_leg_group_id`, `transfer_count` present**: Emits `fare_transfer_rule_with_forbidden_transfer_count`.
- **`from_leg_group_id != to_leg_group_id`, `transfer_count` absent**: Valid, no notice.
- **`from_leg_group_id` absent, `to_leg_group_id` present, `transfer_count` present**: Falls into Branch B (IDs are not both present and equal); emits `fare_transfer_rule_with_forbidden_transfer_count`.
- **`from_leg_group_id` absent, `to_leg_group_id` absent, `transfer_count` present**: Falls into Branch B; emits `fare_transfer_rule_with_forbidden_transfer_count`.
- **Both leg group IDs absent, `transfer_count` absent**: Valid, no notice.
- **`fare_transfer_rules.txt` absent or empty**: No rows; no notices.
- **Multiple violating rows**: Each violating row emits its own notice independently. Multiple notices of the same or different codes may appear with different `csv_row_number` values.
- **Equality check is value equality**, not identity. The Java implementation uses `Objects.equals(rule.fromLegGroupId(), rule.toLegGroupId())`, which is a string equality check on the ID values, not reference equality.

## 7. Implementation notes

### Validator type

Single-table, row-level validator. No joins or cross-row or cross-table state required. Each row is checked independently.

### Validator signature

```python
def validate_fare_transfer_rule_transfer_count(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

### Skip logic

```python
if "fare_transfer_rules" not in feed or feed["fare_transfer_rules"].is_empty():
    return []
```

### Polars implementation strategy

The logic branches on a row-level condition (whether the two ID columns are equal and both non-null) and then applies further checks within each branch. This is best expressed as two separate filtered subsets.

```python
df = feed["fare_transfer_rules"]
notices: list[Notice] = []

# Branch A: both leg group IDs present and equal
self_loop = df.filter(
    pl.col("from_leg_group_id").is_not_null()
    & pl.col("to_leg_group_id").is_not_null()
    & (pl.col("from_leg_group_id") == pl.col("to_leg_group_id"))
)

# Branch A, sub-case 1: transfer_count present but invalid
invalid_count = self_loop.filter(
    pl.col("transfer_count").is_not_null()
    & ((pl.col("transfer_count") < -1) | (pl.col("transfer_count") == 0))
)
for row in invalid_count.iter_rows(named=True):
    notices.append(Notice(
        code="fare_transfer_rule_invalid_transfer_count",
        severity=Severity.ERROR,
        fields={"csv_row_number": row["csv_row_number"], "transfer_count": row["transfer_count"]},
    ))

# Branch A, sub-case 2: transfer_count absent
missing_count = self_loop.filter(pl.col("transfer_count").is_null())
for row in missing_count.iter_rows(named=True):
    notices.append(Notice(
        code="fare_transfer_rule_without_transfer_count",
        severity=Severity.ERROR,
        fields={"csv_row_number": row["csv_row_number"]},
    ))

# Branch B: leg group IDs not equal or at least one absent
not_self_loop = df.filter(
    pl.col("from_leg_group_id").is_null()
    | pl.col("to_leg_group_id").is_null()
    | (pl.col("from_leg_group_id") != pl.col("to_leg_group_id"))
)

# Branch B: transfer_count present (forbidden)
forbidden_count = not_self_loop.filter(pl.col("transfer_count").is_not_null())
for row in forbidden_count.iter_rows(named=True):
    notices.append(Notice(
        code="fare_transfer_rule_with_forbidden_transfer_count",
        severity=Severity.ERROR,
        fields={"csv_row_number": row["csv_row_number"]},
    ))

return notices
```

Since violations are expected to be rare, iterating over the small filtered result sets with `iter_rows` is acceptable. The Polars filter expressions run efficiently over full columns before any Python-level iteration.

### Null semantics in Python/Polars

In the Java implementation, `hasFromLegGroupId()`, `hasToLegGroupId()`, and `hasTransferCount()` return false for any field that was not set (empty or absent CSV cell). In Python/Polars, after the two-phase load (raw string → typed cast), a missing or empty cell for an optional column is represented as `null`. The `is_null()` / `is_not_null()` Polars predicates map directly to the Java `has*()` methods.

The Java equality check uses `Objects.equals(rule.fromLegGroupId(), rule.toLegGroupId())`, which returns `false` if either argument is `null`. The Polars equivalent `pl.col("from_leg_group_id") == pl.col("to_leg_group_id")` returns `null` (not `false`) when either operand is `null`. Wrapping the equality in the `is_not_null()` guards (as shown in Branch A above) replicates the Java behavior faithfully.

### Relationship to load-time validation

The following are handled at load time and must not be duplicated here:

- `fare_transfer_type` required and non-null.
- `duration_limit` must be a positive integer when present (`@Positive` constraint).
- `duration_limit_type` must be a valid enum value when present.
- `from_leg_group_id` and `to_leg_group_id` FK checks into `fare_leg_rules.leg_group_id`.
- `fare_product_id` FK check into `fare_products.fare_product_id`.
- Composite PK uniqueness for `(from_leg_group_id, to_leg_group_id, fare_product_id, transfer_count, duration_limit)`.

This validator adds only the conditional-presence and value-range business rules for `transfer_count`.

# Analysis: ExpiredCalendarValidator

## 1. Purpose

Detects service calendars that have fully expired (all active service dates are in the past relative to the validation date). This is a best-practice warning indicating the feed contains stale data. The validator considers both `calendar.txt` and `calendar_dates.txt` together, computing the effective set of active service dates per service ID before checking expiration.

## 2. Input tables

| Table | Columns used |
|---|---|
| `calendar.txt` | `service_id`, `start_date`, `end_date`, `monday`, `tuesday`, `wednesday`, `thursday`, `friday`, `saturday`, `sunday` |
| `calendar_dates.txt` | `service_id`, `date`, `exception_type` |

### Additional context inputs

| Input | Description |
|---|---|
| Validation date | The current date (or configured date) against which expiration is checked |

### Schema reference

| Column | Table | Type | Constraints |
|---|---|---|---|
| `service_id` | `calendar.txt` | ID (string) | Primary key, required |
| `start_date` | `calendar.txt` | date | Required |
| `end_date` | `calendar.txt` | date | Required |
| `monday`..`sunday` | `calendar.txt` | enum (0/1) | Required |
| `service_id` | `calendar_dates.txt` | ID (string) | Required (FK to `calendar.txt`, but may be standalone) |
| `date` | `calendar_dates.txt` | date | Required |
| `exception_type` | `calendar_dates.txt` | enum (1=added, 2=removed) | Required |

## 3. Validation logic

The validator computes the effective active dates for each service ID, then checks whether all those dates fall before the validation date.

### Step 1: Build service period map

For each service ID, combine data from `calendar.txt` and `calendar_dates.txt`:

- **If the service ID exists in `calendar.txt`**: Use `start_date`/`end_date` range plus the weekly day-of-week pattern (monday..sunday fields) to generate the set of regular service dates. Then apply `calendar_dates.txt` entries: add dates with `exception_type=1` (SERVICE_ADDED), remove dates with `exception_type=2` (SERVICE_REMOVED).
- **If the service ID exists only in `calendar_dates.txt`** (no corresponding `calendar.txt` row): The active dates are only those `calendar_dates.txt` entries with `exception_type=1`. Removed entries without a base calendar have no effect on the active date set (there is nothing to remove from).

### Step 2: Check expiration per service ID

For each service ID in the merged map:

1. Compute the sorted set of all active service dates.
2. If the set is empty, skip (no notice).
3. If the latest (maximum) active date is strictly before the validation date, the service is expired.

### Step 3: Determine which notices to emit

There are two distinct branches depending on whether `calendar.txt` has rows:

- **calendar.txt is non-empty**: For each expired service ID that has a row in `calendar.txt`, emit an `expired_calendar` notice immediately, using the `csv_row_number` from the `calendar.txt` row.
- **calendar.txt is empty** (all services defined only via `calendar_dates.txt`): Collect candidate notices for each expired service ID, but only emit them if ALL service IDs are expired. If even one service ID has a non-expired date, no notices are emitted for any of them. When emitting, use the minimum `csv_row_number` among `calendar_dates.txt` rows for that service ID.

### Step 4: Sort output

Sort all emitted notices by `csv_row_number` ascending before returning.

### Key semantics

- "Expired" means the latest active date is strictly before (`<`) the validation date. A service whose latest date equals today is NOT expired.
- The weekly pattern with all days set to 0 produces zero dates within the start/end range, resulting in an empty date set (skipped, no notice).
- `calendar_dates.txt` entries with `exception_type=SERVICE_ADDED` can extend service beyond the `calendar.txt` end date.
- `calendar_dates.txt` entries with `exception_type=SERVICE_REMOVED` can shorten service by removing dates that would otherwise be active.
- Removed days take precedence over added days (if a date appears in both added and removed sets, it is removed).

## 4. Notices emitted

All notices have severity **WARNING**.

| Notice code | Fields | Description |
|---|---|---|
| `expired_calendar` | `csv_row_number`, `service_id` | A service's entire date range has expired (all active dates are in the past) |

### Notice field details

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | Row number of the relevant record (from `calendar.txt` if present, otherwise the minimum row number from `calendar_dates.txt` for that service) |
| `service_id` | string | The expired service ID |

Referenced files: `calendar.txt`, `calendar_dates.txt`.

## 5. Edge cases

- **Both tables empty**: No service IDs to check, no notices emitted.
- **calendar.txt present, calendar_dates.txt empty**: Expiration based solely on the weekly pattern within start/end range.
- **calendar.txt empty, calendar_dates.txt present**: Only emit notices if ALL service IDs (across all calendar_dates entries) are expired. If any one service ID has a future date, suppress all notices.
- **Service with no active days (weekly pattern all zeros, no added dates)**: The active date set is empty. The service is skipped (no notice), even though it has no future service.
- **calendar end_date is today**: The service includes today as a potential date (if the day-of-week matches). Since today is not before today, the service is not expired. No notice.
- **calendar end_date is yesterday**: If yesterday was the latest active date, the service is expired. Notice emitted.
- **calendar_dates extends past end_date**: An added date in the future makes the service non-expired, even if the calendar.txt end_date is in the past.
- **calendar_dates removes the last active date**: If the only remaining date (e.g., today) is removed via exception_type=2, the latest remaining date may be in the past, causing the service to be expired.
- **Foreign key violation in calendar_dates** (service ID not in calendar.txt, but calendar.txt is non-empty): The orphan calendar_dates service ID is still included in the service period map. However, since `calendar.txt` is non-empty (`isCalendarTableEmpty` is false), and `calendarTable.byServiceId()` returns empty for this orphan, it falls into neither emission branch -- no notice is generated for the orphan. The test `calendarDateWithForeignKeyViolationShouldNotGenerateNotice` confirms this.
- **Multiple service IDs, mix of expired and non-expired (calendar_dates only)**: If calendar.txt is empty and at least one service has a future date, ALL expired-service notices are suppressed.
- **start_date after end_date**: CalendarUtil clamps end_date to equal start_date (protection against invalid data).

## 7. Implementation notes

### Validator type

File-level (cross-table) validator. Consumes `calendar.txt`, `calendar_dates.txt`, and the validation date from `ValidationContext`.

### Service date computation

The core of this validator is computing the effective active dates per service ID. This requires:

1. For each service in `calendar.txt`: expand the `start_date`..`end_date` range, filtering by the weekly day-of-week bitmask (monday..sunday columns), to get regular dates.
2. Merge with `calendar_dates.txt`: union in SERVICE_ADDED dates, subtract SERVICE_REMOVED dates.
3. For service IDs only in `calendar_dates.txt`: active dates are just the SERVICE_ADDED dates.

### Polars implementation strategy

The date expansion and merging logic involves per-service-ID set operations that are not naturally vectorizable in Polars. Two approaches:

**Option A: Python-side computation** -- Iterate over service IDs, compute active date sets using plain Python (date ranges + set operations). This is clearer and matches the Java logic directly. Service count is typically small (tens to hundreds), so performance is fine.

**Option B: Polars date range expansion** -- Use `pl.date_range` to expand calendar rows, filter by day-of-week, then join with calendar_dates. More complex but avoids Python loops. Worth considering only if the service count is very large.

Recommendation: Use Option A (Python-side) for clarity. The service period computation is a utility that other validators also need (it appears in CalendarUtil, shared across validators), so implement it as a shared helper in the Python codebase.

### Shared utility: service period computation

The `CalendarUtil.buildServicePeriodMap` and `servicePeriodToServiceDatesMap` functions are used by multiple Java validators. Implement an equivalent Python utility (e.g., `service_dates.py` or add to an existing utils module) that:

- Takes `calendar` and `calendar_dates` DataFrames
- Returns `dict[str, SortedSet[date]]` mapping service_id to its active dates

### Two-branch emission logic

The validator has distinct behavior depending on whether `calendar.txt` has rows:

- **calendar.txt non-empty**: Emit notices per expired service that has a calendar.txt row. Use the calendar.txt csv_row_number.
- **calendar.txt empty**: Only emit if ALL services are expired. Use the minimum csv_row_number from calendar_dates.txt per service.

This branching must be preserved exactly in the Python implementation.

### Notice field naming

Java uses `csvRowNumber` and `serviceId`. Python equivalents: `csv_row_number`, `service_id`.

### Validation date access

The Java validator receives `DateForValidation` via DI. In the Python implementation, the validation date is available from `ValidationContext.date_for_validation` (a `datetime.date`).

# Analysis: BikesAllowanceValidator

## 1. Purpose

Validates that ferry trips include explicit bike allowance information. Every trip associated with a ferry route (`route_type=4`) should have a valid, recognized value in the `bikes_allowed` field in `trips.txt`. If the value is missing (0/UNKNOWN) or unrecognized, a warning is emitted.

## 2. Input tables

| Table | Columns used |
|---|---|
| `routes.txt` | `route_id`, `route_type` |
| `trips.txt` | `trip_id`, `route_id`, `bikes_allowed` |

This is a cross-table validator. Routes are filtered by `route_type`, then trips are looked up by `route_id`.

## 3. Validation logic

This is a cross-table validator that joins routes and trips:

1. Find all routes where `route_type == 4` (FERRY).
2. For each ferry route, find all trips with a matching `route_id`.
3. For each such trip, check whether `bikes_allowed` has a valid, explicit value:
   - If `bikes_allowed` is `ALLOWED` (1) or `NOT_ALLOWED` (2), the trip is valid — skip it.
   - If `bikes_allowed` is `UNKNOWN` (0, the default when the field is empty/missing) or `UNRECOGNIZED` (an invalid integer that doesn't map to the enum), emit a `MissingBikeAllowanceNotice`.

The key condition in Java is:
```java
if (trip.bikesAllowed() != GtfsBikesAllowed.UNRECOGNIZED
    && trip.bikesAllowed() != GtfsBikesAllowed.UNKNOWN) {
  continue; // valid, skip
}
```
So a notice fires when `bikes_allowed` IS `UNRECOGNIZED` or IS `UNKNOWN`.

### Relevant enums

**`bikes_allowed`**:
| Value | Name | Description |
|---|---|---|
| 0 | UNKNOWN | No bike information (default when field is empty) |
| 1 | ALLOWED | Bikes are permitted |
| 2 | NOT_ALLOWED | Bikes are not permitted |

`UNRECOGNIZED` is a framework-level sentinel for values that don't map to any defined enum value (e.g., an integer like 5 that is not in the enum).

**`route_type`** (relevant value):
| Value | Name |
|---|---|
| 4 | FERRY |

## 4. Notices emitted

### `missing_bike_allowance`

- **Severity**: WARNING
- **Condition**: A trip on a ferry route (`route_type == 4`) where `bikes_allowed` is 0 (UNKNOWN/empty) or an unrecognized value.
- **Fields**:
  | Field | Type | Description |
  |---|---|---|
  | `csv_row_number` | int | The 1-based row number of the trip record |
  | `route_id` | str | The route_id of the ferry route |
  | `trip_id` | str | The trip_id of the faulty trip |

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `routes.txt` or `trips.txt` is missing from feed | Validator is never called (tables not available); no notices |
| No routes with `route_type == 4` exist | No ferry routes to check; no notices |
| Ferry route exists but has no associated trips | No trips to check; no notices |
| Ferry trip has `bikes_allowed == 1` (ALLOWED) | Valid; no notice |
| Ferry trip has `bikes_allowed == 2` (NOT_ALLOWED) | Valid; no notice |
| Ferry trip has `bikes_allowed == 0` or empty/null (UNKNOWN) | Notice emitted |
| Ferry trip has `bikes_allowed` set to an unrecognized integer (e.g., 5) | Notice emitted |
| Non-ferry route with `bikes_allowed` missing/unknown | No notice (validator only checks ferry routes) |
| Multiple ferry trips on same route, some valid some not | Notices emitted only for the invalid trips |

## 7. Implementation notes

### Polars vs plain Python

This is a natural join-and-filter operation. The recommended approach:

1. Filter `routes` for `route_type == 4` to get ferry route IDs.
2. Join (or semi-join) `trips` against those ferry route IDs.
3. Filter the joined result for rows where `bikes_allowed` is null, 0, or not in `{1, 2}`.
4. Emit a notice for each matching row.

```python
ferry_route_ids = routes.filter(pl.col("route_type") == 4).select("route_id")
ferry_trips = trips.join(ferry_route_ids, on="route_id", how="semi")
violations = ferry_trips.filter(
    ~pl.col("bikes_allowed").is_in([1, 2])
)
```

The `~is_in([1, 2])` pattern handles null, 0, and any unrecognized value uniformly since `null.is_in(...)` returns null which negates to true in a Polars filter context.

### Null / enum mapping

In the Java validator, the framework maps empty/missing `bikes_allowed` to `UNKNOWN` (0) and invalid integers to `UNRECOGNIZED`. In the Python/Polars migration, the loading layer handles enum parsing. The validator should treat null and 0 the same way (both mean "no information provided"). The simplest approach is to check that the value is NOT in the set of valid explicit values `{1, 2}`.

### Utility dependencies

None. This validator uses no shared utility classes beyond the standard notice and context types. It relies on the route and trip tables being loaded and typed by the orchestrator.

### Notice code derivation

The Java class `MissingBikeAllowanceNotice` maps to snake_case notice code `missing_bike_allowance`.

# Analysis: ServiceGapValidator

## 1. Purpose

Validates that no service has a gap of more than 13 consecutive inactive days between two active service dates, where a gap is defined as a span of inactivity between two consecutive active intervals (dates before the first active day or after the last are not counted as gaps).

## 2. Input tables

| Table | Columns used |
|---|---|
| `calendar.txt` | `service_id`, `start_date`, `end_date`, `monday`, `tuesday`, `wednesday`, `thursday`, `friday`, `saturday`, `sunday` |
| `calendar_dates.txt` | `service_id`, `date`, `exception_type` |

The validator iterates over all `service_id` values found in `calendar.txt`. For each such `service_id`, it computes the full set of active intervals by combining `calendar.txt` weekly-pattern data with `calendar_dates.txt` exceptions. Services that exist only in `calendar_dates.txt` (with no `calendar.txt` row) are NOT checked — the outer loop is driven by `calendar.txt` entities only.

## 3. Validation logic

### Phase 1: Build active-interval set per service_id

For each `service_id` found in `calendar.txt`, compute a sorted, normalized, non-overlapping collection of active date intervals using the following two-phase construction:

**Step 1a — Apply `calendar.txt` weekly pattern**

For each calendar row with this `service_id`:
1. Build a bitmask `weekly_pattern` from the seven day columns (monday–sunday), where bit 0 = Monday, bit 1 = Tuesday, ..., bit 6 = Sunday. A value of 1 sets the bit; 0 leaves it unset.
2. Walk the date range `[start_date, end_date]` day by day.
3. For each date, check if its day-of-week bit is set in `weekly_pattern`.
4. Emit contiguous runs of active days as intervals `[run_start, run_end]`.
5. Merge these intervals into the existing sorted set, absorbing any overlapping or adjacent entries to maintain the normalization invariant (no overlapping intervals, no adjacent intervals).

If `weekly_pattern == 0` (no day is active), skip this calendar row — nothing is added.

**Step 1b — Apply `calendar_dates.txt` exceptions**

For each `calendar_dates.txt` row with this `service_id`:
- `exception_type == 1` (SERVICE_ADDED): add the single date as a one-day interval and merge it into the set (potentially extending an adjacent interval).
- `exception_type == 2` (SERVICE_REMOVED): remove the single date from the set. If the date falls in the middle of an interval, split that interval into two. If at a boundary, trim the interval. If not contained in any interval, this is a no-op.

**Normalization invariant (maintained at all times):**
- No two intervals overlap.
- No two intervals are adjacent (they would have been merged).
- All intervals are non-empty (`start <= end`).

### Phase 2: Compute gaps between active intervals

After building the normalized interval set for the `service_id`:
1. If the set contains fewer than 2 intervals, there are no gaps — skip.
2. For each consecutive pair of intervals `(prev_end, next_start)`:
   - The gap is the span `[prev_end + 1 day, next_start - 1 day]` (inclusive).
   - Compute `gap_length_in_days = (next_start - 1 day) - (prev_end + 1 day) + 1`, equivalently `ChronoUnit.DAYS.between(prev_end, next_start) - 1`.

### Phase 3: Emit notice if gap exceeds threshold

For each gap:
- If `gap_length_in_days > 13` (i.e., 14 or more days), emit `big_gap_in_service`.
- The notice fields are:
  - `service_id`: the service being checked
  - `gap_start_date`: the last active day **before** the gap = `gap.start - 1 day` (i.e., `prev_end`)
  - `gap_end_date`: the first active day **after** the gap = `gap.end + 1 day` (i.e., `next_start`)
  - `gap_duration_days`: `gap_length_in_days`

Note: the gap interval itself (internal inactive span) runs from `prev_end + 1 day` to `next_start - 1 day`. The notice reports the **bounding active dates** around that span (`prev_end` and `next_start`), not the interior gap dates.

## 4. Notices emitted

### `big_gap_in_service` (INFO)

Emitted when a service has a gap of more than 13 days between consecutive active service dates.

| Field | Type | Source | Description |
|---|---|---|---|
| `service_id` | string | `calendar.service_id` | The service that has the gap |
| `gap_start_date` | string (YYYY-MM-DD) | computed | Last active day before the gap (= `gap_internal_start - 1 day`) |
| `gap_end_date` | string (YYYY-MM-DD) | computed | First active day after the gap (= `gap_internal_end + 1 day`) |
| `gap_duration_days` | integer | computed | Length of the inactive span in days (strictly greater than 13) |

Java class: `BigGapInServiceNotice`.

Python notice code: `big_gap_in_service`.

Severity: INFO.

Referenced files (for notice metadata): `calendar.txt`, `calendar_dates.txt`.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `calendar.txt` absent or empty | No `service_id` values to iterate over; return no notices immediately. |
| `calendar_dates.txt` absent | Phase 1b is skipped; only `calendar.txt` weekly patterns contribute to intervals. |
| Service defined only in `calendar_dates.txt` (no `calendar.txt` row) | Not checked — outer loop is driven by `calendar.txt` entities only. No notice emitted. |
| `ServiceInterval` is null / empty after building (e.g., all days removed) | `getIntervals()` returns null or empty; skip that service. |
| Service with a single active day | Only one interval; `getGaps()` returns empty; no notice. |
| Service with continuous coverage (no gaps) | Only one merged interval; `getGaps()` returns empty; no notice. |
| Gap exactly 13 days (= MAX_GAP_DAYS) | `gap_length > 13` is false; no notice. Threshold is strict greater-than. |
| Gap exactly 14 days (= MAX_GAP_DAYS + 1) | Notice is emitted. |
| Multiple gaps in one service, each > 13 days | One notice per gap. |
| Multiple services, only some with large gaps | Only the gappy services emit notices. |
| `calendar.txt` row with `weekly_pattern == 0` (all days off) | The interval is not added; that row contributes nothing. |
| SERVICE_REMOVED date not contained in any existing interval | No-op; no error. |
| SERVICE_ADDED date adjacent to an existing interval | The interval is extended and merged; normalization maintained. |

## 7. Implementation notes

### Algorithm choice: plain Python interval logic

The core algorithm — maintaining a sorted, normalized, non-overlapping set of date intervals with merge-on-insert and split-on-remove operations — is a classical interval-set data structure. It is much clearer and safer to implement in plain Python using a sorted list or `sortedcontainers.SortedList` than to force it into Polars expressions.

The AGENTS.md guidance explicitly permits plain Python for "graph/geometry/interval logic when clearer and safer than forcing Polars."

### Recommended Python data structures

```python
from datetime import date, timedelta
from dataclasses import dataclass

@dataclass
class DateInterval:
    start: date
    end: date  # inclusive

    def length_in_days(self) -> int:
        return (self.end - self.start).days + 1
```

Use a `list[DateInterval]` kept in sorted order. For the relatively small number of intervals expected per service (at most a few hundred), a linear scan on insert/remove is acceptable. If performance requires it, use `sortedcontainers.SortedList` for O(log n) operations.

### Service interval construction (Python translation of Java)

```python
def build_service_intervals(
    calendar: pl.DataFrame,
    calendar_dates: pl.DataFrame,
) -> dict[str, list[DateInterval]]:
    intervals: dict[str, ServiceIntervalSet] = {}

    # Phase 1: calendar.txt
    for row in calendar.iter_rows(named=True):
        sid = row["service_id"]
        if sid not in intervals:
            intervals[sid] = ServiceIntervalSet()
        pattern = weekly_pattern(row["monday"], row["tuesday"], row["wednesday"],
                                  row["thursday"], row["friday"], row["saturday"], row["sunday"])
        intervals[sid].add_interval(row["start_date"], row["end_date"], pattern)

    # Phase 2: calendar_dates.txt
    if calendar_dates is not None:
        for row in calendar_dates.iter_rows(named=True):
            sid = row["service_id"]
            if sid not in intervals:
                intervals[sid] = ServiceIntervalSet()
            if row["exception_type"] == 1:  # SERVICE_ADDED
                intervals[sid].add_date(row["date"])
            elif row["exception_type"] == 2:  # SERVICE_REMOVED
                intervals[sid].remove_date(row["date"])

    return intervals
```

### Weekly pattern bitmask

```python
def weekly_pattern(mon: int, tue: int, wed: int, thu: int, fri: int, sat: int, sun: int) -> int:
    days = [mon, tue, wed, thu, fri, sat, sun]
    pattern = 0
    for i, d in enumerate(days):
        pattern |= (d & 1) << i
    return pattern

def is_active_day(d: date, pattern: int) -> bool:
    # DayOfWeek: Monday=0 in Python's weekday()
    return bool((pattern >> d.weekday()) & 1)
```

### Gap detection

```python
def get_gaps(active_intervals: list[DateInterval]) -> list[DateInterval]:
    if len(active_intervals) < 2:
        return []
    gaps = []
    for i in range(1, len(active_intervals)):
        prev_end = active_intervals[i - 1].end
        next_start = active_intervals[i].start
        gap_start = prev_end + timedelta(days=1)
        gap_end = next_start - timedelta(days=1)
        if gap_start <= gap_end:
            gaps.append(DateInterval(gap_start, gap_end))
    return gaps
```

### Notice field computation

The Java code adjusts the gap's internal boundaries outward by 1 day to get the bounding active dates:
- `gap_start_date` in notice = `gap.start - 1 day` = `prev_end` (last active day before gap)
- `gap_end_date` in notice = `gap.end + 1 day` = `next_start` (first active day after gap)

This is equivalent to: report the two active endpoints, not the internal gap boundaries.

### Polars usage

Polars is appropriate for the initial data extraction step:
- Select only the required columns from `calendar` and `calendar_dates` DataFrames before iterating.
- Use `iter_rows(named=True)` for the row-by-row interval construction phase.
- Do not attempt to vectorize the interval merge/split logic in Polars — it is inherently sequential and stateful.

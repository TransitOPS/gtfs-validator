# Analysis: PathwayEndpointTypeValidator

## 1. Purpose

Validates that pathway endpoints in `pathways.txt` reference only legal stop types — specifically that no endpoint is a station (`location_type == 1`), and that no endpoint is a platform (`location_type == 0`) that has boarding areas as children (because such platforms must delegate pathways to their boarding areas instead).

## 2. Input tables

| Table | Columns used |
|---|---|
| `pathways.txt` | `pathway_id`, `from_stop_id`, `to_stop_id`, `csv_row_number` |
| `stops.txt` | `stop_id`, `location_type`, `parent_station` |

This is a cross-table validator. For every pathway row, both `from_stop_id` and `to_stop_id` are each looked up in `stops.txt` by `stop_id`. For each resolved stop, the validator checks `location_type` and, for stops of type STOP (0), also checks whether any other stop has `parent_station` equal to that `stop_id` (i.e., it has boarding-area children).

## 3. Validation logic

### Overview

For each row in `pathways.txt`, the validator checks both `from_stop_id` and `to_stop_id` independently using the same sub-rule (`checkEndpoint`):

### Rule: checkEndpoint(pathway, field_name, stop_id)

1. Look up `stop_id` in `stops.txt`.
   - If the stop is not found (broken FK reference), **skip silently** — broken references are handled by a separate FK validator.
2. Inspect `location_type` of the resolved stop:
   - **STOP (0):** Check if any stop in `stops.txt` has `parent_station == stop_id` (i.e., the stop has at least one child boarding area).
     - If **yes** (the platform has boarding areas): emit `pathway_to_platform_with_boarding_areas`.
     - If **no** (the platform has no boarding areas): no notice.
   - **STATION (1):** Emit `pathway_to_wrong_location_type`.
   - **ENTRANCE (2), GENERIC_NODE (3), BOARDING_AREA (4):** No notice; these are all valid endpoint types.

### Key invariant: per-endpoint check

Each of `from_stop_id` and `to_stop_id` is checked independently. A single pathway row can produce 0, 1, or 2 notices — one per endpoint.

### Key invariant: field name passed into notice

The validator passes the field name string (`"from_stop_id"` or `"to_stop_id"`) directly into the notice, so the emitted notice identifies which endpoint column caused the violation.

### Key invariant: boarding-area detection via parent_station index

The check for "platform has boarding areas" is implemented via the stop table's `byParentStation` index — checking whether any stop has `parent_station == stop_id`. This means a STOP endpoint is flagged only if at least one row in `stops.txt` has `parent_station` pointing back to it. A platform with no children is valid.

## 4. Notices emitted

### `pathway_to_wrong_location_type` (ERROR)

Emitted when a pathway endpoint resolves to a stop with `location_type == 1` (STATION).

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | integer | `pathways.txt` row | Row number of the offending pathway |
| `pathway_id` | string | `pathways.pathway_id` | ID of the offending pathway |
| `field_name` | string | literal `"from_stop_id"` or `"to_stop_id"` | Which endpoint column references the station |
| `stop_id` | string | `pathways.from_stop_id` or `pathways.to_stop_id` | ID of the station that is incorrectly referenced |

Severity: ERROR.

Java class: `PathwayToWrongLocationTypeNotice`.

### `pathway_to_platform_with_boarding_areas` (ERROR)

Emitted when a pathway endpoint resolves to a stop with `location_type == 0` (STOP/platform) that has at least one child with `location_type == 4` (BOARDING_AREA) — i.e., any stop whose `parent_station` equals this stop's `stop_id`.

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | integer | `pathways.txt` row | Row number of the offending pathway |
| `pathway_id` | string | `pathways.pathway_id` | ID of the offending pathway |
| `field_name` | string | literal `"from_stop_id"` or `"to_stop_id"` | Which endpoint column references the platform |
| `stop_id` | string | `pathways.from_stop_id` or `pathways.to_stop_id` | ID of the platform that has boarding areas |

Severity: ERROR.

Java class: `PathwayToPlatformWithBoardingAreasNotice`.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `pathways.txt` absent from feed | Return immediately, no notices. |
| `stops.txt` absent from feed | All stop lookups return "not found"; all endpoints are skipped silently; no notices. |
| `pathways.txt` present but empty | No pathway rows to iterate; no notices. |
| `stops.txt` present but empty | All stop lookups return "not found"; all endpoints are skipped silently; no notices. |
| Endpoint `stop_id` references a `stop_id` not in `stops.txt` (broken FK) | Skip silently; FK violations are reported separately. |
| Endpoint is ENTRANCE (location_type == 2) | No notice; valid endpoint type. |
| Endpoint is GENERIC_NODE (location_type == 3) | No notice; valid endpoint type. |
| Endpoint is BOARDING_AREA (location_type == 4) | No notice; valid endpoint type. |
| Endpoint is STOP (location_type == 0) with no boarding-area children | No notice; valid endpoint. |
| Endpoint is STOP (location_type == 0) with at least one boarding-area child | Emit `pathway_to_platform_with_boarding_areas`. |
| Endpoint is STATION (location_type == 1) | Emit `pathway_to_wrong_location_type` regardless of children. |
| Both `from_stop_id` and `to_stop_id` are stations | Two notices emitted for the same pathway row (one per endpoint). |
| Both `from_stop_id` and `to_stop_id` are platforms with boarding areas | Two notices emitted for the same pathway row. |
| One endpoint is a station and the other is a platform with boarding areas | One notice of each type emitted. |
| `parent_station` column is null for all stops | No stop is a child of any other; STOP endpoints are never flagged as having boarding areas. |
| A stop has `parent_station` pointing to a STOP endpoint but the child itself is not a BOARDING_AREA | The Java code checks only whether `byParentStation(stopId)` is non-empty, not whether the children have a specific `location_type`. Any child (regardless of type) causes the notice to fire. |

## 7. Implementation notes

### Algorithm choice

The Java implementation:
1. Iterates over all `pathways.txt` rows.
2. For each row, performs two independent checks via `checkEndpoint`.
3. For each endpoint, looks up the stop in `stops.txt` by `stop_id`.
4. For STOP endpoints, checks whether `byParentStation(stop_id)` is non-empty (any child exists).

The Python equivalent has two sub-problems:

**Sub-problem A (station check):** Pure Polars join — join `pathways` to `stops` on `from_stop_id`/`to_stop_id`, filter where `location_type == 1`.

**Sub-problem B (platform-with-boarding-areas check):** Requires knowing which STOP endpoints have children. This needs a set of "stop IDs that appear as `parent_station` in stops.txt" — i.e., the set of all non-null `parent_station` values. This can be computed once as a Polars or Python set and reused for both endpoint checks.

### Recommended Python implementation sketch

```python
import polars as pl
from gtfs_validator.notices import Notice

def validate_pathway_endpoint_type(
    feed: dict[str, pl.DataFrame], ctx
) -> list[Notice]:
    pathways = feed.get("pathways")
    stops = feed.get("stops")
    if pathways is None or pathways.is_empty():
        return []
    if stops is None or stops.is_empty():
        return []

    STATION = 1
    STOP = 0

    # Build a lookup: stop_id -> location_type
    stop_type: dict[str, int] = dict(
        zip(
            stops["stop_id"].to_list(),
            stops["location_type"].to_list(),
        )
    )

    # Build set of stop_ids that are parents of any stop (have any child)
    parents_with_children: set[str] = set(
        stops.filter(pl.col("parent_station").is_not_null())["parent_station"].to_list()
    )

    notices: list[Notice] = []

    for row in pathways.select(
        ["csv_row_number", "pathway_id", "from_stop_id", "to_stop_id"]
    ).iter_rows(named=True):
        for field_name, stop_id in [
            ("from_stop_id", row["from_stop_id"]),
            ("to_stop_id", row["to_stop_id"]),
        ]:
            loc_type = stop_type.get(stop_id)
            if loc_type is None:
                # Broken FK reference; skip silently.
                continue
            if loc_type == STATION:
                notices.append(Notice(
                    code="pathway_to_wrong_location_type",
                    severity="ERROR",
                    fields={
                        "csvRowNumber": row["csv_row_number"],
                        "pathwayId": row["pathway_id"],
                        "fieldName": field_name,
                        "stopId": stop_id,
                    },
                ))
            elif loc_type == STOP and stop_id in parents_with_children:
                notices.append(Notice(
                    code="pathway_to_platform_with_boarding_areas",
                    severity="ERROR",
                    fields={
                        "csvRowNumber": row["csv_row_number"],
                        "pathwayId": row["pathway_id"],
                        "fieldName": field_name,
                        "stopId": stop_id,
                    },
                ))
    return notices
```

### Alternative: pure Polars approach

A fully vectorized approach is feasible via two separate joins:

**Station check:**
1. Melt `pathways` to produce `(csv_row_number, pathway_id, field_name, stop_id)` rows (one per endpoint).
2. Join to `stops` on `stop_id`.
3. Filter where `location_type == 1`.
4. Emit one notice per resulting row.

**Platform-with-boarding-areas check:**
1. Compute the set of `stop_id` values that appear as `parent_station` in `stops.txt` (a simple `filter + unique` on `parent_station`).
2. In the melted endpoint table, filter where `location_type == 0` and `stop_id` is in that set.
3. Emit one notice per resulting row.

This is also correct, but the row-iteration approach is simpler here because the per-row logic involves two independent conditions evaluated in a specific order with early exits. AGENTS.md permits plain Python for this kind of logic.

### Notice field name convention

Follow camelCase field keys in the notice `fields` dict:
- `csvRowNumber`
- `pathwayId`
- `fieldName`
- `stopId`

### Feed dict keys

- `"pathways"` — `pathways.txt`
- `"stops"` — `stops.txt`

### Required columns

From `pathways.txt`: `csv_row_number`, `pathway_id`, `from_stop_id`, `to_stop_id`.

From `stops.txt`: `stop_id`, `location_type`, `parent_station` (nullable).

### Note on child detection

The Java implementation uses `byParentStation(stopId).isEmpty()` — it returns **any** stop that has `parent_station == stopId`, regardless of whether that child is a BOARDING_AREA or another type. The Python implementation must mirror this: a STOP endpoint is flagged if any stop (of any type) has `parent_station` pointing to it. Do not add an additional filter for `location_type == 4` on the children.

### Validator registration

Requires: `["pathways", "stops"]`.

### Determinism

Emit notices in pathway row order (`csv_row_number` ascending), with `from_stop_id` check before `to_stop_id` for each pathway row. This matches Java iteration order.

# Analysis: TimeframeStartAndEndTimeValidator

## 1. Purpose

Validates each row in `timeframes.txt` to ensure that `start_time` and
`end_time` are either both present or both absent, and that neither value
exceeds `24:00:00`.

## 2. Input tables

| Table | Columns used |
|---|---|
| `timeframes.txt` | `start_time`, `end_time`, `csv_row_number` |

### Column semantics

- `start_time` — conditionally required `GtfsTime` (stored as a Utf8 string
  in the Python implementation); the inclusive lower bound of the timeframe
  interval.
- `end_time` — conditionally required `GtfsTime`; the exclusive upper bound
  of the timeframe interval.
- `csv_row_number` — integer; identifies the offending row in notices.

Both fields are `@ConditionallyRequired` in the Java schema. The `@EndRange`
annotation on `start_time` (`allowEqual = false`) enforces `start_time <
end_time` at load time, not in this validator. This validator only checks the
presence pairing and the 24-hour ceiling.

## 3. Validation logic

The Java implementation is a `SingleEntityValidator` — it processes one row at
a time. All three checks are independent; multiple notices can be emitted for
the same row.

### Check 1 — Exactly one of start_time / end_time is present (XOR)

```
if entity.hasStartTime() XOR entity.hasEndTime():
    emit TimeframeOnlyStartOrEndTimeSpecifiedNotice(csvRowNumber)
```

The condition triggers when exactly one of the two fields is non-null. If
both are present or both are absent, no notice is emitted for this check.

### Check 2 — start_time exceeds 24:00:00

```
if entity.hasStartTime() AND entity.startTime() > 24:00:00:
    emit TimeframeStartOrEndTimeGreaterThanTwentyFourHoursNotice(
        csvRowNumber, field_name="start_time", time=entity.startTime()
    )
```

The threshold is exactly `24:00:00` (`86400` seconds since midnight).
`isAfter` is a strict greater-than: `secondsSinceMidnight > 86400`. A value
of exactly `24:00:00` does NOT trigger this notice.

### Check 3 — end_time exceeds 24:00:00

```
if entity.hasEndTime() AND entity.endTime() > 24:00:00:
    emit TimeframeStartOrEndTimeGreaterThanTwentyFourHoursNotice(
        csvRowNumber, field_name="end_time", time=entity.endTime()
    )
```

Same threshold and strict-greater-than semantics as Check 2. This check is
independent of Check 1 and independent of Check 2.

### Independence of checks

All three checks run unconditionally for every row. A single row can
produce up to three notices:

- If `start_time` is set and `end_time` is absent: Check 1 fires (only one
  specified).
- If `start_time` is present and `> 24:00:00`: Check 2 fires.
- If `end_time` is present and `> 24:00:00`: Check 3 fires.

The order of emission per row is: Check 1, Check 2, Check 3.

## 4. Notices emitted

### `timeframe_only_start_or_end_time_specified` (ERROR)

Emitted when exactly one of `start_time` or `end_time` is present on a row.

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | int | `timeframes.csv_row_number` | Row number of the offending entry |

Severity: ERROR.

Condition: `start_time IS NOT NULL XOR end_time IS NOT NULL`.

### `timeframe_start_or_end_time_greater_than_twenty_four_hours` (ERROR)

Emitted when `start_time` or `end_time` is strictly greater than `24:00:00`
(i.e., `> 86400` seconds since midnight). One notice is emitted per
offending field per row (up to two per row if both fields exceed the limit).

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | int | `timeframes.csv_row_number` | Row number of the offending entry |
| `field_name` | string | literal `"start_time"` or `"end_time"` | Which field has the invalid value |
| `time` | string (HH:MM:SS) | `timeframes.start_time` or `timeframes.end_time` | The actual value that exceeded the limit |

Severity: ERROR.

Condition: the field is non-null AND its value in seconds since midnight is
strictly greater than `86400` (`24 * 3600`).

Boundary: `24:00:00` exactly (86400 s) is valid and does NOT trigger this
notice. `24:00:01` (86401 s) does trigger it.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `timeframes.txt` absent from feed | Return `[]` immediately. |
| `timeframes.txt` present but empty (zero rows) | Return `[]` immediately. |
| Both `start_time` and `end_time` are null (absent) | No notice from any of the three checks; both-absent is the valid "implicit full-day" case. |
| Both `start_time` and `end_time` are present and both within bounds | No notices. |
| `start_time` is present, `end_time` is null | Check 1 fires (XOR = true); Checks 2 and 3 are skipped for the null field. |
| `end_time` is present, `start_time` is null | Check 1 fires (XOR = true); Checks 2 and 3 are skipped for the null field. |
| `start_time = 00:00:00`, `end_time = 24:00:00` | Explicit full-day interval; all checks pass, no notices. |
| `end_time = 24:00:01` | Check 3 fires (`24:00:01 > 24:00:00`). |
| `start_time > 24:00:00` | Check 2 fires. |
| Both `start_time` and `end_time` exceed `24:00:00` | Checks 2 and 3 both fire; two notices for the row. |
| `start_time` present, `end_time` absent, and `start_time > 24:00:00` | Check 1 fires (XOR) AND Check 2 fires; two notices. |
| Null values reaching the validator | `_TIME` columns are validated at load time for format but stay as Utf8. Nulls (absent values) are explicitly tested in Java; `hasStartTime()` / `hasEndTime()` return false for nulls, and no comparison is performed on null fields. Python must guard accordingly: check for null before parsing to seconds. |
| Multiple rows with violations | Each row is checked independently; no deduplication across rows. |

## 6. Test contracts

The Java test file (`TimeframeStartAndEndTimeValidatorTest.java`) contains
four test methods.

### `testExplicitFullDayInterval`

- One row: `start_time="00:00:00"`, `end_time="24:00:00"`.
- Expected: no notices.
- Rationale: both fields are present; `24:00:00` is exactly at the boundary
  and is NOT greater than `24:00:00`, so Check 2/3 do not fire.

### `testImplicitFullDayInterval`

- One row: no `start_time`, no `end_time` (default-built entity).
- Expected: no notices.
- Rationale: both fields absent; XOR is false (both absent = false XOR false
  = false), and neither presence check fires.

### `testBeyondTwentyFourHours`

- One row: `csv_row_number=2`, `start_time="00:00:00"`,
  `end_time="24:00:01"`.
- Expected: exactly one `TimeframeStartOrEndTimeGreaterThanTwentyFourHoursNotice`
  with `csv_row_number=2`, `field_name="end_time"`, `time="24:00:01"`.
- Rationale: `start_time` is present and within bounds (no Check 2 notice);
  `end_time` is `24:00:01 > 24:00:00` so Check 3 fires.

### `testOnlyStartTimeSpecified`

- One row: `csv_row_number=2`, `start_time="00:00:00"`, no `end_time`.
- Expected: exactly one `TimeframeOnlyStartOrEndTimeSpecifiedNotice` with
  `csv_row_number=2`.
- Rationale: XOR is true (start present, end absent); Check 1 fires.
  Check 2 does not fire (`00:00:00` is within bounds). Check 3 does not fire
  (`end_time` is absent).

### `testOnlyEndTimeSpecified`

- One row: `csv_row_number=2`, `end_time="10:00:00"`, no `start_time`.
- Expected: exactly one `TimeframeOnlyStartOrEndTimeSpecifiedNotice` with
  `csv_row_number=2`.
- Rationale: XOR is true (start absent, end present); Check 1 fires.
  Check 3 does not fire (`10:00:00` is within bounds). Check 2 does not fire
  (`start_time` is absent).

### What is NOT covered by the Java test suite

- `timeframes.txt` absent from the feed entirely.
- Empty `timeframes.txt`.
- Both `start_time` and `end_time` exceed `24:00:00` simultaneously (two
  notices from one row).
- `start_time` missing AND `end_time > 24:00:00` (Check 1 + Check 3 on same
  row).
- Multiple rows, some valid and some invalid (batch behavior).
- `start_time` exceeds `24:00:00` while `end_time` is valid.

## 7. Implementation notes

### Algorithm strategy

The Java validator is a row-level `SingleEntityValidator`. The Python
equivalent processes the `timeframes` DataFrame with Polars vectorized
expressions, emitting notices for each violating row.

Per the AGENTS.md guidance: "Use Polars expressions for tabular checks."
This validator is well-suited to vectorized filtering — no interval
arithmetic or graph logic is needed.

### Time representation in the Python implementation

`_TIME` columns remain as Utf8 strings after loading (see `loading.py`
line 386–387: `FieldType.TIME` goes through format validation only, no
numeric cast). The `_TIME_RE` pattern (`^\d{1,2}:\d{2}:\d{2}$`) accepts
only 1–2 digit hours, so values like `24:00:01` (two-digit hour) pass
format validation, but `100:00:00` (three-digit) would be rejected.

To compare against the `24:00:00` threshold, strings must be parsed to
seconds since midnight. A helper function is required:

```python
def _time_str_to_seconds(t: str) -> int:
    h, m, s = t.split(":")
    return int(h) * 3600 + int(m) * 60 + int(s)
```

In Polars this can be vectorized using `str.split_exact` or string slicing
with `cast(Int32)`:

```python
def _time_col_to_seconds(col_name: str) -> pl.Expr:
    # Parses "HH:MM:SS" Utf8 column to total seconds as Int32.
    return (
        pl.col(col_name).str.slice(0, 2).cast(pl.Int32) * 3600
        + pl.col(col_name).str.slice(3, 2).cast(pl.Int32) * 60
        + pl.col(col_name).str.slice(6, 2).cast(pl.Int32)
    )
```

Note: this approach works for zero-padded two-digit hours only. GTFS allows
H:MM:SS (one-digit hour) per `_TIME_RE`. Use `str.splitn(":", 3)` or
`str.split(":")` and index into the resulting list for robustness.

The threshold constant is `TWENTY_FOUR_HOURS_SECONDS = 24 * 3600 = 86400`.

### Recommended Polars approach

```python
TWENTY_FOUR_HOURS_SECONDS = 24 * 3600  # 86400

def _parse_time_seconds(col_name: str) -> pl.Expr:
    """Parse a GTFS HH:MM:SS or H:MM:SS Utf8 column to seconds since midnight."""
    parts = pl.col(col_name).str.split(":")
    return (
        parts.list.get(0).cast(pl.Int32) * 3600
        + parts.list.get(1).cast(pl.Int32) * 60
        + parts.list.get(2).cast(pl.Int32)
    )


def validate_timeframe_start_and_end_time(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "timeframes" not in feed or feed["timeframes"].is_empty():
        return []

    tf = feed["timeframes"].select(
        "start_time", "end_time", "csv_row_number"
    )

    has_start = pl.col("start_time").is_not_null()
    has_end = pl.col("end_time").is_not_null()

    # Check 1: exactly one of start_time / end_time is present (XOR)
    xor_violations = tf.filter(has_start != has_end)

    # Check 2: start_time > 24:00:00
    start_violations = tf.filter(
        has_start & (_parse_time_seconds("start_time") > TWENTY_FOUR_HOURS_SECONDS)
    )

    # Check 3: end_time > 24:00:00
    end_violations = tf.filter(
        has_end & (_parse_time_seconds("end_time") > TWENTY_FOUR_HOURS_SECONDS)
    )

    notices: list[Notice] = []

    for row in xor_violations.iter_rows(named=True):
        notices.append(
            TimeframeOnlyStartOrEndTimeSpecifiedNotice(
                csv_row_number=row["csv_row_number"],
            )
        )

    for row in start_violations.iter_rows(named=True):
        notices.append(
            TimeframeStartOrEndTimeGreaterThanTwentyFourHoursNotice(
                csv_row_number=row["csv_row_number"],
                field_name="start_time",
                time=row["start_time"],
            )
        )

    for row in end_violations.iter_rows(named=True):
        notices.append(
            TimeframeStartOrEndTimeGreaterThanTwentyFourHoursNotice(
                csv_row_number=row["csv_row_number"],
                field_name="end_time",
                time=row["end_time"],
            )
        )

    return notices
```

### Emission order

The Java validator emits notices in the order: Check 1, Check 2, Check 3
within a single row. The Python implementation above processes each check
as a separate batch filter and appends in the same order, which is
behaviorally equivalent for the notice stream.

### Notice dataclasses

```python
@dataclass
class TimeframeOnlyStartOrEndTimeSpecifiedNotice:
    code: ClassVar[str] = "timeframe_only_start_or_end_time_specified"
    severity: ClassVar[str] = "ERROR"
    csv_row_number: int


@dataclass
class TimeframeStartOrEndTimeGreaterThanTwentyFourHoursNotice:
    code: ClassVar[str] = "timeframe_start_or_end_time_greater_than_twenty_four_hours"
    severity: ClassVar[str] = "ERROR"
    csv_row_number: int
    field_name: str  # "start_time" or "end_time"
    time: str        # original HH:MM:SS string value
```

### Boundary semantics

The Java threshold is `GtfsTime.fromHourMinuteSecond(24, 0, 0)` (86400 s)
and the comparison is `isAfter`, which is a strict greater-than
(`secondsSinceMidnight > 86400`). Therefore `24:00:00` is valid; `24:00:01`
is not. The Python implementation must use strict `>`, not `>=`.

### Null handling

`start_time` and `end_time` are `@ConditionallyRequired`. They may be null.
The Polars filters explicitly gate on `is_not_null()` before converting to
seconds, so null fields never reach the integer comparison. The XOR check
uses null-awareness directly (`is_not_null() != is_not_null()`).

### Feed dict key

- `"timeframes"` — `timeframes.txt`

### Validator registration

Required tables: `["timeframes"]`. The validator self-guards on the presence
and emptiness of `timeframes.txt`.

Feature flag: none.

### No cross-row or cross-table logic

This validator is entirely within a single table and makes no reference to
any other GTFS table. No joins or FK lookups are required.

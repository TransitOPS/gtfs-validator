# Analysis: GtfsTripServiceIdForeignKeyValidator

## 1. Purpose

Validates that every `service_id` in `trips.txt` references a valid `service_id` that exists in either `calendar.txt` or `calendar_dates.txt`.

## 2. Input tables

| Table | Columns used |
|---|---|
| `trips.txt` | `service_id`, `csvRowNumber` (row tracking) |
| `calendar.txt` | `service_id` |
| `calendar_dates.txt` | `service_id` |

### Key relationships

This is a **multi-parent foreign key** check. The `service_id` in `trips.txt` is valid if it appears in the `service_id` column of **either** `calendar.txt` **or** `calendar_dates.txt` (logical OR). It does not need to appear in both.

## 3. Validation logic

1. Iterate over every row in `trips.txt`.
2. For each row, read the `service_id` value.
3. Check whether the `service_id` value exists in `calendar.txt` (via `service_id` column, which is the primary key) OR in `calendar_dates.txt` (via `service_id` column, which is part of the composite key).
4. If the value is **not found in either table**, emit a `foreign_key_violation` notice.
5. If found in at least one of the two tables, the row passes.

### Guard clauses

- The Java validator does not explicitly guard against null/empty `service_id` -- it relies on the framework having already parsed the field. In the Python implementation, rows with null or empty `service_id` should be skipped (no notice emitted), since `service_id` is a required field and would already be flagged by load-time validation.
- The check is purely a set-membership lookup: the `service_id` value must appear as at least one `service_id` value in calendar or calendar_dates.

## 4. Notices emitted

### `foreign_key_violation`

Severity: **ERROR**

Emitted when a `trips.txt` row has a `service_id` that does not exist in either `calendar.txt` or `calendar_dates.txt`.

| Field | Type | Description |
|---|---|---|
| `childFilename` | string | Always `"trips.txt"` |
| `childFieldName` | string | Always `"service_id"` |
| `parentFilename` | string | Always `"calendar.txt or calendar_dates.txt"` |
| `parentFieldName` | string | Always `"service_id"` |
| `fieldValue` | string | The unresolved `service_id` value |
| `csvRowNumber` | int | The 1-based row number in `trips.txt` |

## 5. Edge cases

- **`trips.txt` absent**: The validator will not be invoked (no child table to iterate). No notices.
- **`calendar.txt` absent but `calendar_dates.txt` present**: The lookup in calendar yields no matches; the check falls through to calendar_dates. If found in calendar_dates, no notice. If not found, notice emitted.
- **`calendar_dates.txt` absent but `calendar.txt` present**: Same logic in reverse -- if found in calendar, no notice.
- **Both parent tables absent**: Every `service_id` in trips will produce a notice.
- **`service_id` is null/empty in trips**: Should be skipped (would already be caught by load-time required-field validation).
- **All trip rows have valid `service_id`**: No notices emitted.
- **Duplicate `service_id` values in calendar or calendar_dates**: Does not matter; the check is set-membership ("does at least one row with this service_id exist?").
- **`service_id` exists in both calendar and calendar_dates**: Valid -- no notice. The OR condition is satisfied.
- **Multiple trips reference the same invalid `service_id`**: Each trip row produces its own notice (one per row, not deduplicated).

## 7. Implementation notes

### Validator type

This is a **cross-table validator** (post-load). It checks foreign key references across three tables.

### Implementation strategy: Polars expressions

This is a straightforward set-membership / anti-join check, well-suited to Polars.

### Suggested approach

1. Extract the set of all `service_id` values from `calendar.txt` (non-null, non-empty).
2. Extract the set of all `service_id` values from `calendar_dates.txt` (non-null, non-empty).
3. Compute the union of these two sets.
4. Filter `trips.txt` to rows where `service_id` is non-null and non-empty.
5. For each such row where `service_id` is NOT in the union set, emit a `foreign_key_violation` notice.

### Handling missing tables

- If `trips.txt` is absent from the feed, return early with an empty list.
- If `calendar.txt` is absent, treat its service_id set as empty.
- If `calendar_dates.txt` is absent, treat its service_id set as empty.

### Existing infrastructure

The `foreign_key_violation` notice code is a standard FK notice already used by the load-time FK checking infrastructure in `load_validators.py`. This validator is a special case because it checks a **multi-parent** FK (the value can resolve to either of two tables), which the standard single-parent FK loader cannot handle. That is why it exists as a separate cross-table validator.

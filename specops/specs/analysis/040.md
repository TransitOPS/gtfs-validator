# Analysis: PathwayDanglingGenericNodeValidator

## 1. Purpose

Validates that every `GENERIC_NODE` stop (`location_type == 3`) in `stops.txt` is connected to at least two distinct locations in the pathway graph — i.e., it is not "dangling" (connected to only one other location).

## 2. Input tables

| Table | Columns used |
|---|---|
| `stops.txt` | `stop_id`, `stop_name`, `parent_station`, `location_type`, `csv_row_number` |
| `pathways.txt` | `from_stop_id`, `to_stop_id` |

This is a cross-table validator. It joins the stop table (filtered to generic nodes) against the pathway table (both directions).

### Location type integer values (relevant subset)

| Integer | Enum name | Meaning |
|---|---|---|
| 0 | `STOP` | Stop / platform |
| 1 | `STATION` | Station |
| 2 | `ENTRANCE` | Entrance / exit |
| 3 | `GENERIC_NODE` | Generic pathway node |
| 4 | `BOARDING_AREA` | Boarding area |

## 3. Validation logic

### Algorithm overview

For each stop with `location_type == 3` (GENERIC_NODE):

1. Collect the set of **distinct neighbor stop IDs** reachable through any pathway edge incident to this node, treating edges as undirected:
   - For every pathway where `from_stop_id == stop_id`, add `to_stop_id` to the neighbor set.
   - For every pathway where `to_stop_id == stop_id`, add `from_stop_id` to the neighbor set.
2. If the neighbor set has **exactly one** element, the generic node is dangling — emit `pathway_dangling_generic_node`.
3. If the neighbor set has **zero elements** (isolated node) or **two or more elements** (pass-through or hub), emit nothing.

### Key invariant: direction is ignored

Pathway directionality (`is_bidirectional`, `pathway_mode`) plays no role. Both `from_stop_id` and `to_stop_id` endpoints are treated as undirected neighbors regardless of the original direction.

### Key invariant: set deduplication

Multiple pathway edges connecting the same pair of nodes do not increase the neighbor count. The neighbor **set** counts distinct neighbor IDs, not pathway edges. Two pathways `(A → B)` and `(B → A)` both add the same neighbor `B` to A's set, so A still has only one distinct neighbor.

## 4. Notices emitted

### `pathway_dangling_generic_node` (WARNING)

Emitted when a `GENERIC_NODE` stop has exactly one distinct neighbor in the pathway graph.

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | integer | `stops.txt` row | Row number of the dangling generic node |
| `stop_id` | string | `stops.stop_id` | ID of the dangling generic node |
| `stop_name` | string | `stops.stop_name` | Name of the dangling generic node (may be null) |
| `parent_station` | string | `stops.parent_station` | Parent station ID of the dangling node (may be null) |

Severity: WARNING.

Java class: `PathwayDanglingGenericNodeNotice`.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `stops.txt` absent from feed | Return immediately, no notices. |
| `pathways.txt` absent from feed | No pathways exist; all generic nodes have zero neighbors; isolated nodes do not trigger the notice (size == 0, not == 1); return no notices. |
| `stops.txt` has no `GENERIC_NODE` rows | No notices; skip immediately after filtering. |
| `stops.txt` present but empty | No notices. |
| `pathways.txt` present but empty | All generic nodes are isolated (neighbor set size == 0); no notices. |
| Generic node is isolated (no pathway edges reference it) | Neighbor set is empty (size == 0); no notice emitted. |
| Generic node has exactly one distinct neighbor via multiple edges | E.g., pathways `(G → A)` and `(A → G)`: set = `{A}`, size = 1; notice is emitted. |
| Generic node has two or more distinct neighbors | Pass-through or hub; no notice. |
| Stop has `location_type != 3` (STOP, STATION, ENTRANCE, BOARDING_AREA) | Skipped entirely; the check only applies to `GENERIC_NODE`. |
| `stop_name` or `parent_station` is null | Null values are passed through to notice fields as-is. |
| `from_stop_id` or `to_stop_id` in a pathway references a `stop_id` that is not in `stops.txt` | That pathway still contributes its opposite endpoint as a neighbor of any generic node it references; dangling FK references are handled by separate FK validators. |

## 6. Test contracts

### `danglingGenericNode_yieldsNotice`

Setup:
- Stops: STATION (row 10), STOP (row 11, parent=10), GENERIC_NODE (row 12, parent=10), ENTRANCE (row 13, parent=10).
- Pathways: `(11 → 13)`, `(11 → 12)`.

Expected: exactly one `pathway_dangling_generic_node` notice for the GENERIC_NODE at row 12.

Reasoning: The GENERIC_NODE (stop12) appears only as `to_stop_id` in pathway `(11 → 12)`. Its neighbor set is `{stop11}`, size = 1 → dangling.

### `danglingGenericNodeWithTwoPathways_yieldsNotice`

Setup:
- Same stops as above.
- Pathways: `(11 → 13)`, `(11 → 12)`, `(12 → 11)`.

Expected: exactly one `pathway_dangling_generic_node` notice for row 12.

Reasoning: GENERIC_NODE (stop12) appears as `to_stop_id` in `(11 → 12)` and as `from_stop_id` in `(12 → 11)`. Both edges point to the same neighbor `stop11`. Neighbor set = `{stop11}`, size = 1 → still dangling despite two pathway edges.

This test confirms that multi-edge connections to the same neighbor do not prevent the notice.

### `isolatedGenericNode_yieldsNoNotice`

Setup:
- Same stops as above.
- Pathways: `(11 → 13)` only (no pathway references stop12).

Expected: no notices.

Reasoning: GENERIC_NODE (stop12) has zero pathway edges; neighbor set is empty, size = 0 → not dangling; no notice.

### `passThroughGenericNode_yieldsNoNotice`

Setup:
- Same stops as above.
- Pathways: `(11 → 12)`, `(12 → 13)`.

Expected: no notices.

Reasoning: GENERIC_NODE (stop12) has neighbors `{stop11, stop13}`, size = 2 → not dangling; no notice.

### `danglingPlatformAndEntrance_yieldsNoNotice`

Setup:
- Stops: STATION (row 10), STOP (row 11, parent=10), ENTRANCE (row 12, parent=10). No GENERIC_NODE.
- Pathways: `(11 → 12)`.

Expected: no notices.

Reasoning: Neither stop11 (STOP) nor stop12 (ENTRANCE) is a GENERIC_NODE; the validator skips all non-GENERIC_NODE stops.

## 7. Implementation notes

### Algorithm choice

The Java implementation uses a row loop with per-node `HashSet` construction using index lookups (`byFromStopId`, `byToStopId`). In Python, the equivalent can be done with Polars joins or, as AGENTS.md explicitly permits for graph logic, plain Python sets.

**Recommended approach: plain Python with prebuilt adjacency sets.**

The graph-neighborhood computation involves per-node set unions, which is cleaner in Python than forcing Polars expressions. This aligns with the AGENTS.md guideline: "Use plain Python algorithms for graph/geometry/interval logic when clearer and safer than forcing Polars."

### Recommended Python implementation sketch

```python
import polars as pl
from gtfs_validator.notices import Notice

def validate_pathway_dangling_generic_node(
    feed: dict[str, pl.DataFrame], ctx
) -> list[Notice]:
    stops = feed.get("stops")
    pathways = feed.get("pathways")
    if stops is None or stops.is_empty():
        return []

    GENERIC_NODE = 3

    generic_nodes = stops.filter(pl.col("location_type") == GENERIC_NODE)
    if generic_nodes.is_empty():
        return []

    # Build neighbor sets: stop_id -> set of neighbor stop_ids (undirected)
    neighbors: dict[str, set[str]] = {
        row["stop_id"]: set()
        for row in generic_nodes.iter_rows(named=True)
    }

    if pathways is not None and not pathways.is_empty():
        for row in pathways.select(["from_stop_id", "to_stop_id"]).iter_rows(named=True):
            from_id = row["from_stop_id"]
            to_id = row["to_stop_id"]
            if from_id in neighbors:
                neighbors[from_id].add(to_id)
            if to_id in neighbors:
                neighbors[to_id].add(from_id)

    notices: list[Notice] = []
    for row in generic_nodes.iter_rows(named=True):
        if len(neighbors[row["stop_id"]]) == 1:
            notices.append(Notice(
                code="pathway_dangling_generic_node",
                severity="WARNING",
                fields={
                    "csvRowNumber": row["csv_row_number"],
                    "stopId": row["stop_id"],
                    "stopName": row.get("stop_name"),
                    "parentStation": row.get("parent_station"),
                },
            ))
    return notices
```

### Alternative: Polars-only approach

A pure Polars approach is possible but more verbose:

1. Filter `pathways` to rows where `from_stop_id` or `to_stop_id` is a GENERIC_NODE.
2. Union both directions into a single `(generic_node_id, neighbor_id)` edge table.
3. Group by `generic_node_id`, count distinct `neighbor_id` values.
4. Filter where `n_distinct == 1`.
5. Join back to `stops` for notice fields.

This is correct but harder to read for a graph problem. Prefer the plain-Python approach per AGENTS.md guidance.

### Notice code

The Java class is `PathwayDanglingGenericNodeNotice`. The Python notice code should be:

```
"pathway_dangling_generic_node"
```

### Feed dict keys

- `"stops"` — `stops.txt`
- `"pathways"` — `pathways.txt`

### Required columns

From `stops.txt`: `stop_id`, `location_type`, `csv_row_number`, `stop_name` (optional/nullable), `parent_station` (optional/nullable).

From `pathways.txt`: `from_stop_id`, `to_stop_id`.

### Guard for missing `pathways` table

If `pathways` is `None` or empty, all generic nodes have empty neighbor sets (size = 0), so no notices are emitted. The implementation must handle this case without error.

### Validator registration

Requires: `["stops", "pathways"]`.

Both tables must be listed; the validator should not run if either is absent (treat absence as empty for pathways, but also treat absence of stops as the primary early-exit guard).

### Determinism

Emit notices in the order generic nodes appear in `stops.txt` (by `csv_row_number`). The Java implementation iterates over all stops in table order, so the Python implementation should produce the same ordering by iterating over the already-ordered `generic_nodes` DataFrame.

### Notice field name convention

Follow the project convention of camelCase field keys in the notice `fields` dict:
- `csvRowNumber`
- `stopId`
- `stopName`
- `parentStation`

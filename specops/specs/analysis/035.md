# Analysis: MissingTripEdgeValidator

## 1. Purpose

Validates that the first and last stop times of every trip (ordered by `stop_sequence`) each define both `arrival_time` and `departure_time`, unless the stop time uses a continuous pickup/drop-off window (`start_pickup_drop_off_window` / `end_pickup_drop_off_window`).

## 2. Input tables

| Table | Columns used |
|---|---|
| `stop_times.txt` | `trip_id`, `stop_sequence`, `arrival_time`, `departure_time`, `start_pickup_drop_off_window`, `end_pickup_drop_off_window` |

No other tables are read. The validator operates entirely on `stop_times.txt`.

Columns used per row:
- `trip_id` — used to group stop times by trip.
- `stop_sequence` — used to determine sort order within a trip; the row with the minimum `stop_sequence` is the first stop, the row with the maximum is the last stop.
- `arrival_time` — checked for presence on the first and last stop of each trip.
- `departure_time` — checked for presence on the first and last stop of each trip.
- `start_pickup_drop_off_window` — exemption flag; if present on a trip edge row, no time checks are performed on that row.
- `end_pickup_drop_off_window` — exemption flag; if present on a trip edge row, no time checks are performed on that row.

## 3. Validation logic

The Java implementation groups all `stop_times.txt` rows by `trip_id` and processes each group as a list sorted ascending by `stop_sequence`. The `@PrimaryKey(isSequenceUsedForSorting = true)` annotation on `stop_sequence` guarantees this ordering inside `byTripIdMap()`.

Step-by-step rules:

1. **Group by trip**: For each unique `trip_id` in `stop_times.txt`, collect all rows belonging to that trip into an ordered list sorted by `stop_sequence` ascending.

2. **Identify trip edges**: Within each group:
   - `first_stop` = the row with the lowest `stop_sequence`.
   - `last_stop` = the row with the highest `stop_sequence`.

3. **Pickup/drop-off window exemption**: For each edge row (first and last independently), check whether **both** `start_pickup_drop_off_window` and `end_pickup_drop_off_window` are absent (null/not provided). If either field is present on the edge row, **skip all time checks** for that row. This models continuous-zone demand-responsive services, which do not use fixed times.
   - The exemption condition in Java: `!hasStartPickupDropOffWindow() && !hasEndPickupDropOffWindow()` must be true for checks to proceed.
   - Presence of **either** window field (even only one) exempts the row — but the Java code checks that **both** are absent before doing the time checks. If only one is present and the other is absent, the Java condition `!hasStart && !hasEnd` evaluates to false, so checks are skipped. In practice, the spec requires both to be present together, but the validator logic exempts any row where at least one window field is present.

4. **Arrival time check**: If the edge row is not exempted (step 3), and `arrival_time` is null/absent, emit `missing_trip_edge` with `specified_field = "arrival_time"`.

5. **Departure time check**: If the edge row is not exempted (step 3), and `departure_time` is null/absent, emit `missing_trip_edge` with `specified_field = "departure_time"`.

6. Both checks (arrival and departure) are independent: a single edge row can produce zero, one, or two notices.

7. The first and last edges are also checked independently: if `first_stop == last_stop` (a single-stop trip), both the first-edge and last-edge checks apply to the same row, potentially doubling notices. The Java code does not de-duplicate this case.

8. If `stop_times.txt` is absent or empty, the outer loop has nothing to iterate and no notices are emitted.

## 4. Notices emitted

### `missing_trip_edge` (ERROR)

Emitted when the first or last stop time of a trip is missing `arrival_time` or `departure_time` and is not a pickup/drop-off window row.

| Field | Type | Source |
|---|---|---|
| `csv_row_number` | int | Row number (1-based) of the offending `stop_times.txt` row |
| `stop_sequence` | int | `stop_sequence` value of the offending row |
| `trip_id` | string | `trip_id` of the offending row |
| `specified_field` | string | `"arrival_time"` or `"departure_time"` — whichever field is missing |

Severity: ERROR.

One notice is emitted per missing field per trip edge. For a single edge row that is missing both `arrival_time` and `departure_time`, two notices are emitted (one for each field).

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `stop_times.txt` absent from feed | No notices; validator does nothing. |
| `stop_times.txt` is empty (zero rows) | No notices; nothing to iterate. |
| Trip with a single stop time row | That row is both the first and last stop. Both first-edge and last-edge checks fire on it independently. Up to four notices possible (arrival + departure for first, arrival + departure for last — but same row twice). |
| First and last edge are the same row | Same as single-stop trip above. |
| Middle stop times missing times | No notices; only the first and last stops in `stop_sequence` order are checked. |
| Edge row has `start_pickup_drop_off_window` present, `end_pickup_drop_off_window` absent | Exempted (Java condition: `!hasStart && !hasEnd` is false). No time checks for that row. |
| Edge row has `end_pickup_drop_off_window` present, `start_pickup_drop_off_window` absent | Exempted for the same reason. No time checks for that row. |
| Edge row has both window fields present | Exempted. No time checks. |
| Edge row has both times present and no window fields | No notice. |
| Edge row has `arrival_time` present but `departure_time` absent (no windows) | One notice for `"departure_time"`. |
| Edge row has `departure_time` present but `arrival_time` absent (no windows) | One notice for `"arrival_time"`. |
| Edge row has both times absent and no window fields | Two notices: one for `"arrival_time"`, one for `"departure_time"`. |
| Multiple trips in feed, some valid and some invalid | Notices only for trips with edge violations. Valid trips emit nothing. |
| Trip IDs with special characters or spaces | Treated as opaque strings; no special handling. |

- Expected: Exactly one `MissingTripEdgeNotice` with `csvRowNumber=2`, `stopSequence=1`, `tripId="trip id value"`, `specifiedField="arrival_time"`.

- Expected: Exactly one `MissingTripEdgeNotice` with `csvRowNumber=2`, `stopSequence=1`, `tripId="trip id value"`, `specifiedField="departure_time"`.

### `tripWithLastStopMissingArrivalTimeShouldGenerateNotices`

- Setup: Four stop times for `"trip id value"` with `stop_sequence` 1, 2, 3, 5. Stop at sequence 1 (csv row 2) has both times set. Stop at sequence 5 (csv row 10) has `departure_time` set but `arrival_time` null.
- Expected: Exactly one `MissingTripEdgeNotice` with `csvRowNumber=10`, `stopSequence=5`, `tripId="trip id value"`, `specifiedField="arrival_time"`.

### `tripWithLastStopMissingDepartureTimeShouldGenerateNotices`

- Setup: Four stop times for `"trip id value"` with `stop_sequence` 1, 2, 3, 5. Stop at sequence 1 (csv row 2) has both times set. Stop at sequence 5 (csv row 10) has `arrival_time` set but `departure_time` null.
- Expected: Exactly one `MissingTripEdgeNotice` with `csvRowNumber=10`, `stopSequence=5`, `tripId="trip id value"`, `specifiedField="departure_time"`.

### `tripWithValidEdgesShouldNotGenerateNotice`

- Setup: Four stop times for `"trip id value"` with `stop_sequence` 1, 2, 3, 4. Stop at sequence 1 (csv row 2) has both times set. Stop at sequence 4 (csv row 10) has both times set. Middle stops have both times null.
- Expected: No notices.

### `tripWithPickupDropOffWindowShouldNotGenerateNotice`

- Setup: Two single-stop trips (`"trip id value"` and `"trip id value 2"`). Each has one stop time with `arrival_time` and `departure_time` null, but `start_pickup_drop_off_window` and `end_pickup_drop_off_window` both set.
- Expected: No notices. The pickup/drop-off window exempts the rows from the time requirement.
- Note: This also implicitly tests that the two trips are processed independently.

## 7. Implementation notes

### Approach

The core logic groups rows by `trip_id` and finds the first/last row per group by `stop_sequence`. This is a natural Polars group-by operation. Because `stop_sequence` determines ordering, no assumption about input file order should be made.

Two equivalent approaches are viable:

**Option A — Pure Polars (preferred for large feeds):**

1. Filter `stop_times` to keep only rows where `start_pickup_drop_off_window` is null AND `end_pickup_drop_off_window` is null. These are the only rows eligible to generate notices.
2. For each trip, find the min and max `stop_sequence` rows using `group_by("trip_id").agg(pl.min("stop_sequence").alias("min_seq"), pl.max("stop_sequence").alias("max_seq"))`.
3. Join back to identify the actual first and last rows per trip (handling ties in `stop_sequence` is unlikely per GTFS PK constraints, but use `sort + first/last` to be safe).
4. From those first/last rows, check `arrival_time.is_null()` and `departure_time.is_null()`.
5. Emit one notice per null field found.

**Option B — Plain Python with grouped iteration (acceptable for correctness clarity):**

Since this check requires identifying minimum and maximum `stop_sequence` per group and checking nulls, a grouped-Python approach is also clean:

```python
for trip_id, group in stop_times.sort("stop_sequence").group_by("trip_id"):
    first = group.row(0, named=True)
    last = group.row(-1, named=True)
    for edge in _deduplicated_edges(first, last):
        if not _has_window(edge):
            if edge["arrival_time"] is None:
                notices.append(...)
            if edge["departure_time"] is None:
                notices.append(...)
```

AGENTS.md permits plain Python loops for graph/interval logic when clearer. This validator is simple enough that either approach is acceptable, but the Polars approach avoids materializing groups in Python memory for large feeds.

### Exemption logic

The exemption requires that **both** `start_pickup_drop_off_window` AND `end_pickup_drop_off_window` are absent. In Polars: `pl.col("start_pickup_drop_off_window").is_null() & pl.col("end_pickup_drop_off_window").is_null()`. Only rows satisfying this condition are candidates for the time check. Rows with either window column non-null are exempt.

### Single-stop trip behavior

When a trip has exactly one stop time row, that row is both first and last. The Java code processes first and last independently, so in the single-row case the checks run twice. If both `arrival_time` and `departure_time` are absent and there is no window exemption, four notices would be emitted (arrival for first-edge, departure for first-edge, arrival for last-edge, departure for last-edge). The Python implementation must replicate this behavior faithfully. A straightforward approach: after identifying first-row and last-row per trip, process them as a list (possibly containing the same row twice), rather than de-duplicating.

### `csv_row_number` field

The `csv_row_number` corresponds to the 1-based row number in the original `stop_times.txt` file (including the header row as row 1, so data rows start at 2). This is stored by the orchestrator's loading layer in a `_row_number` column on each loaded DataFrame. The validator should use that column value directly.

### Notice code

Notice code: `"missing_trip_edge"` (derived from the Java class name `MissingTripEdgeNotice` following the existing snake_case convention).

### Feed dict key

- `stop_times.txt` → `"stop_times"` key in `feed`.

### Validator registration

Register with `requires=["stop_times"]`. If `stop_times` is absent from `feed`, the runner's `should_skip` logic will bypass the validator automatically.

### Columns required

Only these columns need to be selected from `stop_times`:
- `trip_id`
- `stop_sequence`
- `arrival_time`
- `departure_time`
- `start_pickup_drop_off_window`
- `end_pickup_drop_off_window`
- `_row_number`

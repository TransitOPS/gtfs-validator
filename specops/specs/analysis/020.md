# Analysis: FeedServiceDateValidator

## 1. Purpose

Validates that `feed_info.txt` records do not provide only one of the `feed_start_date` / `feed_end_date` pair. Both fields are optional (recommended), but when either is present the other must also be present — the two fields are conditionally required together.

The validator is a Best Practices check. It emits a WARNING notice identifying the missing field by name so the consumer can pinpoint exactly what to add.

Because `feed_info.txt` is declared a single-row table, at most one notice will ever be generated in practice.

## 2. Input tables

| Table | Columns used |
|---|---|
| `feed_info.txt` | `feed_start_date`, `feed_end_date`, `csv_row_number` |

### Schema reference

`feed_info.txt` (`GtfsFeedInfoSchema`, Python: `FEED_INFO`):

| Column | Type | Constraint |
|---|---|---|
| `feed_publisher_name` | string | Required |
| `feed_publisher_url` | URL (string) | Required |
| `feed_lang` | language code | Required |
| `default_lang` | language code | Optional |
| `feed_start_date` | date | Recommended; end-range anchor for `feed_end_date` |
| `feed_end_date` | date | Recommended |
| `feed_version` | string | Recommended |
| `feed_contact_email` | email (string) | Optional |
| `feed_contact_url` | URL (string) | Optional |

The table is declared `single_row=True` in the Python schema (`FEED_INFO`), so the loader enforces at most one data row.

## 3. Validation logic

### Skip conditions

- If `feed_info.txt` is absent or empty, no rows are processed and no notices are emitted.
- If both `feed_start_date` and `feed_end_date` are absent (null), no notice is emitted — neither field is required.
- If both `feed_start_date` and `feed_end_date` are present, no notice is emitted — the pair is complete.

### Algorithm

For each row in `feed_info.txt`:

**Case 1 — start present, end absent:**

```
if feed_start_date is not null AND feed_end_date is null:
    emit missing_feed_info_date(
        csv_row_number=row.csv_row_number,
        field_name="feed_end_date",
    )
```

**Case 2 — start absent, end present:**

```
if feed_start_date is null AND feed_end_date is not null:
    emit missing_feed_info_date(
        csv_row_number=row.csv_row_number,
        field_name="feed_start_date",
    )
```

The two cases are mutually exclusive. At most one notice is emitted per row. No arithmetic or date comparison is performed; the check is purely about field presence.

### Pseudocode

```
for each row in feed_info:
    has_start = row.feed_start_date is not null
    has_end   = row.feed_end_date   is not null

    if has_start and not has_end:
        emit missing_feed_info_date(
            csv_row_number=row.csv_row_number,
            field_name="feed_end_date",
        )
    elif not has_start and has_end:
        emit missing_feed_info_date(
            csv_row_number=row.csv_row_number,
            field_name="feed_start_date",
        )
```

### What is NOT checked here

- Whether `feed_start_date` or `feed_end_date` are valid date values (handled at load time via type casting).
- Whether `feed_start_date` precedes or equals `feed_end_date` (handled by the load-time `@EndRange` check in `load_validators.py`).
- Whether either date field is recommended but absent when both are absent (a recommendation hint; absence of both simply generates no notice from this validator).
- Required field presence for `feed_publisher_name`, `feed_publisher_url`, `feed_lang` (load-time checks).

## 4. Notices emitted

### `missing_feed_info_date`

Severity: **WARNING**

Emitted when exactly one of `feed_start_date` / `feed_end_date` is provided. The notice identifies the specific missing field by name.

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending `feed_info.txt` row |
| `field_name` | string | The name of the missing field: either `"feed_end_date"` or `"feed_start_date"` |

The `field_name` values are fixed string literals. Only two values are ever emitted:

- `"feed_end_date"` — when `feed_start_date` is present but `feed_end_date` is absent.
- `"feed_start_date"` — when `feed_end_date` is present but `feed_start_date` is absent.

## 5. Edge cases

- **Both dates absent (null)**: No notice. Both fields are optional; the pair is trivially consistent.
- **Both dates present**: No notice. The pair is complete.
- **Only `feed_start_date` present**: Emits `missing_feed_info_date` with `field_name="feed_end_date"`.
- **Only `feed_end_date` present**: Emits `missing_feed_info_date` with `field_name="feed_start_date"`.
- **`feed_info.txt` absent from the feed**: No rows; no notices.
- **`feed_info.txt` empty (header only)**: No rows; no notices.
- **Multiple rows** (spec violation, but possible before loader enforcement): Each row is checked independently; a notice is emitted per violating row.
- **Date values that fail type casting**: Handled at load time; by the time this validator runs, invalid date strings have already been flagged separately and the column value is null. If a date field is null due to a parse failure, this validator treats it the same as absent.
- **No cross-row or cross-table state**: The check is purely local to each row; no join, aggregation, or accumulation is needed.

## 7. Implementation notes

### Validator type

Single-table, row-level validator. No joins, no cross-row state, no cross-table lookups, no date arithmetic. Pure field-presence check.

No dependency on `ValidationContext` (no current date needed).

### Validator signature

```python
def validate_feed_service_date(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

### Skip logic

```python
if "feed_info" not in feed or feed["feed_info"].is_empty():
    return []
```

### Polars implementation strategy

`feed_info.txt` is a single-row table, so performance is not a concern. The cleanest implementation iterates over rows and checks field presence directly.

```python
import polars as pl
from gtfs_validator.notices import Notice, Severity
from gtfs_validator.context import ValidationContext

def validate_feed_service_date(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
    if "feed_info" not in feed or feed["feed_info"].is_empty():
        return []

    notices: list[Notice] = []

    for row in feed["feed_info"].iter_rows(named=True):
        has_start = row["feed_start_date"] is not None
        has_end   = row["feed_end_date"]   is not None

        if has_start and not has_end:
            notices.append(Notice(
                code="missing_feed_info_date",
                severity=Severity.WARNING,
                fields={
                    "csv_row_number": row["csv_row_number"],
                    "field_name": "feed_end_date",
                },
            ))
        elif not has_start and has_end:
            notices.append(Notice(
                code="missing_feed_info_date",
                severity=Severity.WARNING,
                fields={
                    "csv_row_number": row["csv_row_number"],
                    "field_name": "feed_start_date",
                },
            ))

    return notices
```

Because `feed_info.txt` is a single-row table, `iter_rows` is appropriate and imposes no performance concern.

### Notice codes (Python)

| Java notice class | Python notice code | Severity |
|---|---|---|
| `MissingFeedInfoDateNotice` | `missing_feed_info_date` | WARNING |

### Relationship to load-time validation

The following are handled at load time and must not be duplicated here:

- `feed_start_date` and `feed_end_date` type validation (valid YYYYMMDD date strings).
- `feed_start_date` end-range check relative to `feed_end_date` (`feed_start_date <= feed_end_date`), enforced via the `@EndRange` annotation on `GtfsFeedInfoSchema.feedStartDate()`.
- Single-row enforcement for `feed_info.txt`.
- Required field presence checks for `feed_publisher_name`, `feed_publisher_url`, `feed_lang`.

This validator adds only the conditional presence check: "if one date field is given, the other must also be given."

### Python schema reference

The `FEED_INFO` table definition in `src/gtfs_validator/schemas.py` includes `feed_start_date` and `feed_end_date` typed as `_DATE` and marked `_REC` (recommended). No schema changes are needed. After the two-phase load, values are `datetime.date` objects or `null` if absent/unparseable.

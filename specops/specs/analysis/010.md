# Analysis: DuplicateRouteNameValidator

## 1. Purpose

Validates that no two routes within the same agency share the same combination of `route_short_name`, `route_long_name`, and `route_type`. Routes with different `route_id` values but identical name+type+agency tuples are flagged as likely duplicates. This is a best-practice warning to catch copy-paste errors or modeling mistakes where different directions are incorrectly split into separate routes.

## 2. Input tables

| Table | Columns used |
|---|---|
| `routes.txt` | `route_id`, `agency_id`, `route_short_name`, `route_long_name`, `route_type` |

No additional context inputs required (no cross-table joins, no validation date).

### Schema reference

| Column | Type | Constraints |
|---|---|---|
| `route_id` | ID (string) | Primary key, required |
| `agency_id` | ID (string) | Optional (FK to `agency.txt`) |
| `route_short_name` | string | Conditionally required (at least one of short/long name) |
| `route_long_name` | string | Conditionally required (at least one of short/long name) |
| `route_type` | enum (int) | Required |

## 3. Validation logic

1. Iterate over all rows in `routes.txt` (only rows that parsed successfully).
2. For each row, form a composite key: `(route_short_name, route_long_name, route_type, agency_id)`.
3. Track the first occurrence of each key in a lookup map.
4. If a row's key matches an already-seen key, emit a `duplicate_route_name` notice referencing both the first occurrence and the current row.
5. If there are more than two rows with the same key, each subsequent row after the first is paired with the first occurrence (not with the previous duplicate). The first row seen is always the "left" side of the notice.

### Key semantics

- The Java implementation hashes the four fields together using FarmHash: `route_long_name`, `route_short_name`, `route_type` (as int), and `agency_id`. Hash collisions are theoretically possible but astronomically unlikely with FarmHash64.
- Null/missing `route_short_name` or `route_long_name` defaults to empty string in the Java getter, so two routes both missing short name (with same long name, type, and agency) will match.
- Two routes with different `route_type` values are considered distinct even if names and agency match.
- Two routes with different `agency_id` values are considered distinct even if names and type match.
- Two routes with different short names but the same long name do NOT trigger a notice (and vice versa).

## 4. Notices emitted

All notices have severity **WARNING**.

| Notice code | Fields | Description |
|---|---|---|
| `duplicate_route_name` | `csv_row_number_1`, `route_id_1`, `csv_row_number_2`, `route_id_2`, `route_short_name`, `route_long_name`, `route_type_value`, `agency_id` | Two distinct routes share the same short name, long name, type, and agency |

### Notice field details

| Field | Type | Description |
|---|---|---|
| `csv_row_number_1` | int | Row number of the first (earlier) route |
| `route_id_1` | string | ID of the first route |
| `csv_row_number_2` | int | Row number of the duplicate route |
| `route_id_2` | string | ID of the duplicate route |
| `route_short_name` | string | The shared short name (from the first route) |
| `route_long_name` | string | The shared long name (from the first route) |
| `route_type_value` | int | The shared route type as integer (from the first route) |
| `agency_id` | string | The shared agency ID (from the first route) |

Referenced file: `routes.txt`.

## 5. Edge cases

- **Empty routes.txt**: No rows to iterate, no notices emitted.
- **routes.txt not present in feed**: Validator does not run (no table to inject). No notices.
- **Single route**: No duplicates possible. No notices.
- **Null/empty route_short_name**: If two routes both have null/empty `route_short_name` and the same `route_long_name`, `route_type`, and `agency_id`, they match and produce a notice. The Java getter returns empty string for missing values.
- **Null/empty route_long_name**: Same behavior — missing long name is treated as empty string for key computation.
- **Both names null/empty**: Two routes with no short name, no long name, same type, and same agency will match. This is an unusual edge case since at least one name is conditionally required, but if both pass load-time checks the validator still applies.
- **Three or more routes with the same key**: The first route becomes the "existing" entry. Each subsequent route produces a separate notice, always paired with the first route. For N routes sharing a key, N-1 notices are emitted.
- **Different route_id, same composite key**: This is exactly the scenario the validator catches.
- **Same agency_id missing/empty**: If `agency_id` defaults to empty string on both routes, they share the same agency for key purposes and will match if names+type also match.
- **Hash collisions**: The Java implementation uses FarmHash64 for the composite key. In theory, two routes with different name/type/agency combos could produce the same hash, yielding a false positive. The Python implementation should use direct tuple comparison to avoid this.

## 7. Implementation notes

### Validator type

File-level (single-table) validator. Consumes only `routes.txt`.

### Polars implementation strategy

This validator detects duplicate composite keys across rows in a single table. A natural Polars approach:

1. Select the relevant columns: `route_id`, `agency_id`, `route_short_name`, `route_long_name`, `route_type`, and the row index (`csv_row_number`).
2. Fill null `route_short_name` and `route_long_name` with empty string to match Java default-getter semantics.
3. Fill null `agency_id` with empty string for the same reason.
4. Group by `(route_short_name, route_long_name, route_type, agency_id)`.
5. Filter groups with count > 1.
6. Within each group, pair the first row with every subsequent row to emit notices.

Since routes tables are typically small (hundreds to low thousands of rows), any approach is fine performance-wise. A self-join on the composite key with a row-number filter (`csv_row_number_1 < csv_row_number_2`) paired with a `first()` aggregation is an alternative.

### Notice field naming

Java uses `csvRowNumber1`, `routeId1`, `csvRowNumber2`, `routeId2`, `routeShortName`, `routeLongName`, `routeTypeValue`, `agencyId`. Python equivalents: `csv_row_number_1`, `route_id_1`, `csv_row_number_2`, `route_id_2`, `route_short_name`, `route_long_name`, `route_type_value`, `agency_id`.

### Difference from Java: avoid hashing

The Java implementation uses FarmHash64 to hash the composite key for efficient map lookup. The Python implementation should use direct tuple comparison (or Polars group-by on the four columns) instead, which is simpler, avoids hash collision false positives, and is idiomatic in Python/Polars.

### Pairing semantics

When multiple duplicates exist for the same key, the first row encountered is always `route_1` (the "existing" entry). Each subsequent duplicate is paired individually with that first row. This means for a group of N rows sharing a key, exactly N-1 notices are emitted, all referencing the same `csv_row_number_1` / `route_id_1`.

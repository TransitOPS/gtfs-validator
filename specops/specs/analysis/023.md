# Analysis: GtfsFareLegRuleNetworkIdForeignKeyValidator

## 1. Purpose

Validates that every non-empty `network_id` in `fare_leg_rules.txt` references a valid `network_id` that exists in either `routes.txt` or `networks.txt`.

## 2. Input tables

| Table | Columns used |
|---|---|
| `fare_leg_rules.txt` | `network_id`, `csvRowNumber` (row tracking) |
| `routes.txt` | `network_id` |
| `networks.txt` | `network_id` |

### Key relationships

This is a **multi-parent foreign key** check. The `network_id` in `fare_leg_rules.txt` is valid if it appears in the `network_id` column of **either** `routes.txt` **or** `networks.txt` (logical OR). It does not need to appear in both.

## 3. Validation logic

1. Iterate over every row in `fare_leg_rules.txt`.
2. For each row, read the `network_id` value.
3. If `network_id` is empty (null or empty string), **skip** the row -- no validation needed.
4. Check whether the `network_id` value exists in `routes.txt` (via the `network_id` column) OR in `networks.txt` (via the `network_id` column).
5. If the value is **not found in either table**, emit a `foreign_key_violation` notice.
6. If found in at least one of the two tables, the row passes.

### Guard clauses

- Rows with empty `network_id` are silently skipped (no notice emitted).
- The check is purely a set-membership lookup: the `network_id` value must appear as at least one `network_id` value in routes or networks.

## 4. Notices emitted

### `foreign_key_violation`

Severity: **ERROR**

Emitted when a `fare_leg_rules.txt` row has a non-empty `network_id` that does not exist in either `routes.txt` or `networks.txt`.

| Field | Type | Description |
|---|---|---|
| `childFilename` | string | Always `"fare_leg_rules.txt"` |
| `childFieldName` | string | Always `"network_id"` |
| `parentFilename` | string | Always `"routes.txt or networks.txt"` |
| `parentFieldName` | string | Always `"network_id"` |
| `fieldValue` | string | The unresolved `network_id` value |
| `csvRowNumber` | int | The 1-based row number in `fare_leg_rules.txt` |

## 5. Edge cases

- **`fare_leg_rules.txt` absent**: The validator will not be invoked (no child table to iterate). No notices.
- **`routes.txt` absent but `networks.txt` present**: The lookup in routes yields no matches; the check falls through to networks. If found in networks, no notice. If not found, notice emitted.
- **`networks.txt` absent but `routes.txt` present**: Same logic in reverse -- if found in routes, no notice.
- **Both parent tables absent**: Every non-empty `network_id` in fare_leg_rules will produce a notice.
- **`network_id` is null/empty in fare_leg_rules**: Silently skipped (empty string check at line 57-59 of the Java source).
- **All fare_leg_rule rows have empty `network_id`**: No notices emitted.
- **Single row in fare_leg_rules**: Normal processing -- one lookup, one possible notice.
- **Duplicate `network_id` values in routes or networks**: Does not matter; the check is set-membership ("does at least one row with this network_id exist?").
- **`network_id` exists in both routes and networks**: Valid -- no notice. The OR condition is satisfied.

## 7. Implementation notes

### Validator type

This is a **cross-table validator** (post-load). It checks foreign key references across three tables.

### Implementation strategy: Polars expressions

This is a straightforward set-membership / anti-join check, well-suited to Polars.

### Suggested approach

1. Extract the set of all `network_id` values from `routes.txt` (non-null, non-empty).
2. Extract the set of all `network_id` values from `networks.txt` (non-null, non-empty).
3. Compute the union of these two sets.
4. Filter `fare_leg_rules.txt` to rows where `network_id` is non-null and non-empty.
5. For each such row where `network_id` is NOT in the union set, emit a `foreign_key_violation` notice.

### Handling missing tables

- If `fare_leg_rules.txt` is absent from the feed, return early with an empty list.
- If `routes.txt` is absent, treat its network_id set as empty.
- If `networks.txt` is absent, treat its network_id set as empty.

### Existing infrastructure

The `foreign_key_violation` notice code is a standard FK notice already used by the load-time FK checking infrastructure in `load_validators.py`. This validator is a special case because it checks a **multi-parent** FK (the value can resolve to either of two tables), which the standard single-parent FK loader cannot handle. That is why it exists as a separate cross-table validator.

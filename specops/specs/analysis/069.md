# Analysis: TimeframeServiceIdForeignKeyValidator

## 1. Purpose

Validates that every `service_id` value in `timeframes.txt` references a valid
`service_id` that exists in either `calendar.txt` or `calendar_dates.txt`.

## 2. Input tables

| Table | Columns used |
|---|---|
| `timeframes.txt` | `service_id`, `csv_row_number` |
| `calendar.txt` | `service_id` (lookup only) |
| `calendar_dates.txt` | `service_id` (lookup only) |

### Column semantics

- `timeframes.service_id` — required string; the foreign key being validated.
  Every row in `timeframes.txt` must have this value present in at least one of
  the two parent tables.
- `calendar.service_id` — primary key of `calendar.txt`; used as one valid
  parent reference target.
- `calendar_dates.service_id` — part of the composite primary key of
  `calendar_dates.txt`; used as the other valid parent reference target.
- `timeframes.csv_row_number` — integer; carried into the notice to identify
  the offending row.

## 3. Validation logic

### Step 1 — Guard: timeframes.txt absent or empty

If `timeframes.txt` is absent from the feed or contains zero rows, there is
nothing to check. Return immediately with no notices.

### Step 2 — Build parent key sets

Collect all distinct `service_id` values from `calendar.txt` into a set.
Collect all distinct `service_id` values from `calendar_dates.txt` into a set.
Either or both parent tables may be absent or empty; treat absent tables as
contributing an empty set.

### Step 3 — Check each timeframes row

For each row in `timeframes.txt`:

1. Read `service_id` from the row.
2. Check whether that value is present in the `calendar` set OR the
   `calendar_dates` set (union lookup).
3. If the value is found in either set, no notice — continue to the next row.
4. If the value is absent from both sets, emit one `foreign_key_violation`
   notice for that row.

The check is a union: the `service_id` only needs to appear in one of the two
parent tables to be considered valid.

### Step 4 — One notice per violating row

Each `timeframes.txt` row with an unresolved `service_id` produces exactly one
notice. There is no deduplication by `service_id` value — if the same invalid
`service_id` appears on multiple rows, each row produces its own notice.

## 4. Notices emitted

### `foreign_key_violation` (ERROR)

Emitted for each row in `timeframes.txt` whose `service_id` cannot be found in
either `calendar.txt` or `calendar_dates.txt`.

| Field | Type | Source | Description |
|---|---|---|---|
| `child_filename` | string | literal `"timeframes.txt"` | The file containing the invalid reference |
| `child_field_name` | string | literal `"service_id"` | The field that holds the bad FK value |
| `parent_filename` | string | literal `"calendar.txt or calendar_dates.txt"` | The combined parent reference target |
| `parent_field_name` | string | literal `"service_id"` | The field in the parent that was looked up |
| `field_value` | string | `timeframes.service_id` | The actual value that was not found |
| `csv_row_number` | int | `timeframes.csv_row_number` | Row number of the offending timeframe entry |

Severity: ERROR.

Condition: `timeframes.service_id` value is not present in `calendar.service_id`
set AND not present in `calendar_dates.service_id` set.

Note: the `parent_filename` field uses the literal string
`"calendar.txt or calendar_dates.txt"` (a composite description of both
possible parent tables), not just one filename. This is the exact value emitted
by the Java validator; the Python implementation must reproduce it verbatim.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `timeframes.txt` absent from feed | Return `[]` immediately. |
| `timeframes.txt` present but empty (zero rows) | Return `[]` immediately. |
| `calendar.txt` absent or empty | Use empty set for calendar lookups; only `calendar_dates` contributes. |
| `calendar_dates.txt` absent or empty | Use empty set for calendar_dates lookups; only `calendar` contributes. |
| Both `calendar.txt` and `calendar_dates.txt` absent | Every `timeframes.service_id` is unresolvable; every row emits a notice. |
| `service_id` in `calendar.txt` only | Valid — no notice emitted. |
| `service_id` in `calendar_dates.txt` only | Valid — no notice emitted. |
| `service_id` in both `calendar.txt` and `calendar_dates.txt` | Valid — no notice emitted. |
| Same invalid `service_id` on multiple `timeframes.txt` rows | One notice per row; no deduplication. |
| Null `service_id` in `timeframes.txt` | `service_id` is required; null values should be caught at load time. Defensively, a null value would not be found in either parent set and would generate a notice, but this should not normally reach the validator. |

## 6. Test contracts

The Java test file contains three test methods.

### `timeframeServiceIdInCalendarTableShouldNotGenerateNotice`

- One timeframe row: `service_id="WEEK"`.
- One calendar row: `service_id="WEEK"`, with dates and weekday flags set.
- Empty `calendar_dates` list.
- Expected: no notices.
- Rationale: `"WEEK"` is found in `calendar.txt`; FK is satisfied.

### `tripServiceIdInCalendarDateTableShouldNotGenerateNotice`

- One timeframe row: `service_id="WEEK"`.
- Empty `calendar` list.
- One `calendar_dates` row: `service_id="WEEK"`, `csv_row_number=2`,
  `exception_type=2`.
- Expected: no notices.
- Rationale: `"WEEK"` is found in `calendar_dates.txt`; FK is satisfied even
  though `calendar.txt` is empty.

### `tripServiceIdNotInDataShouldGenerateNotice`

- One timeframe row: `service_id="WEEK"`, `csv_row_number=1`.
- Empty `calendar` list.
- Empty `calendar_dates` list.
- Expected: exactly one `ForeignKeyViolationNotice` with:
  - `child_filename="timeframes.txt"`
  - `child_field_name="service_id"`
  - `parent_filename="calendar.txt or calendar_dates.txt"`
  - `parent_field_name="service_id"`
  - `field_value="WEEK"`
  - `csv_row_number=1`
- Rationale: `"WEEK"` is absent from both parent tables; FK violation.

### What is NOT covered by the Java test suite

- `timeframes.txt` absent from the feed entirely.
- Empty `timeframes.txt`.
- Multiple timeframe rows with the same invalid `service_id` (per-row notice
  deduplication behavior).
- Multiple timeframe rows with different invalid `service_id` values (multiple
  notices).
- `service_id` present in both `calendar.txt` and `calendar_dates.txt`.
- Null `service_id` in `timeframes.txt`.

## 7. Implementation notes

### Algorithm strategy

The Java implementation iterates over each `GtfsTimeframe` entity and performs
a lookup against two indexed containers. The equivalent Python approach is:

1. Build a set of all `service_id` values from `calendar.txt`.
2. Build a set of all `service_id` values from `calendar_dates.txt`.
3. Compute the union of both sets once (or check membership in either).
4. Use a Polars anti-join (or filter against a literal set) to find timeframe
   rows whose `service_id` is absent from the union.
5. Collect violating rows and emit one notice per row.

This is a straightforward FK check against a union of two parent tables — the
same pattern used by other `*ForeignKeyValidator` implementations already
migrated to Python.

### Recommended Polars approach

```python
def validate_timeframe_service_id_foreign_key(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "timeframes" not in feed or feed["timeframes"].is_empty():
        return []

    tf = feed["timeframes"].select("service_id", "csv_row_number")

    # Build union of valid service_id values from both parent tables
    cal_ids: set[str] = set()
    if "calendar" in feed and not feed["calendar"].is_empty():
        cal_ids = set(feed["calendar"]["service_id"].drop_nulls().to_list())

    cal_date_ids: set[str] = set()
    if "calendar_dates" in feed and not feed["calendar_dates"].is_empty():
        cal_date_ids = set(
            feed["calendar_dates"]["service_id"].drop_nulls().to_list()
        )

    valid_ids = cal_ids | cal_date_ids

    # Find rows whose service_id is not in the union
    violations = tf.filter(
        ~pl.col("service_id").is_in(list(valid_ids))
    )

    notices: list[Notice] = []
    for row in violations.iter_rows(named=True):
        notices.append(
            ForeignKeyViolationNotice(
                child_filename="timeframes.txt",
                child_field_name="service_id",
                parent_filename="calendar.txt or calendar_dates.txt",
                parent_field_name="service_id",
                field_value=row["service_id"],
                csv_row_number=row["csv_row_number"],
            )
        )
    return notices
```

### parent_filename literal

The Java validator constructs the `parent_filename` field as:
`GtfsCalendar.FILENAME + " or " + GtfsCalendarDate.FILENAME`, which evaluates
to `"calendar.txt or calendar_dates.txt"`. The Python implementation must use
this exact string to maintain output compatibility.

### Set-based vs. join-based lookup

For this validator a set-based membership check (`is_in`) is appropriate and
efficient. The parent tables (`calendar.txt`, `calendar_dates.txt`) are small
relative to the number of unique `service_id` values, and the union set is
computed once before scanning `timeframes.txt`. A Polars left-anti-join against
a combined parent DataFrame is an equally valid alternative.

### Notice dataclass

```python
@dataclass
class ForeignKeyViolationNotice:
    code: ClassVar[str] = "foreign_key_violation"
    severity: ClassVar[str] = "ERROR"
    child_filename: str
    child_field_name: str
    parent_filename: str
    parent_field_name: str
    field_value: str
    csv_row_number: int
```

Note: `ForeignKeyViolationNotice` is a shared notice type used by many
validators. Confirm whether it is already defined in `notices.py` before adding
a new definition.

### Feed dict keys

- `"timeframes"` — `timeframes.txt`
- `"calendar"` — `calendar.txt`
- `"calendar_dates"` — `calendar_dates.txt`

### Validator registration

Required tables: `["timeframes"]`. The validator should still run when
`calendar` and/or `calendar_dates` are absent (those absences are treated as
empty parent sets, producing notices for every timeframe row).

Feature flag: none. The validator self-guards on the presence of `timeframes.txt`.

### Null handling

`service_id` is a required field in `timeframes.txt`. Null values should be
caught at load time. Defensively, any null `service_id` should be excluded from
the `is_in` check or treated as a non-matching value. Since a null will not be
found in the valid-IDs set, it would naturally generate a notice, but this case
should not normally reach the validator.

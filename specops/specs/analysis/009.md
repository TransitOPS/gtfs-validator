# Analysis: DuplicateFareMediaValidator

## 1. Purpose

Validates that no two fare media entries in `fare_media.txt` share the same combination of `fare_media_name` and `fare_media_type`. Different fare media IDs that represent the same name+type pair are flagged as duplicates. This is a data quality check to prevent confusing or redundant fare media definitions.

## 2. Input tables

| Table | Columns used |
|---|---|
| `fare_media.txt` | `fare_media_id`, `fare_media_name`, `fare_media_type` |

No additional context inputs required (no validation date, no cross-table joins).

### Schema reference

| Column | Type | Constraints |
|---|---|---|
| `fare_media_id` | ID (string) | Primary key, required |
| `fare_media_name` | string | Optional |
| `fare_media_type` | enum (int) | Required |

`fare_media_type` values:

| Value | Name |
|---|---|
| 0 | NONE |
| 1 | PAPER_TICKET |
| 2 | TRANSIT_CARD |
| 3 | CONTACTLESS_EMV |
| 4 | MOBILE_APP |

## 3. Validation logic

1. Iterate over all rows in `fare_media.txt` (only rows that parsed successfully).
2. For each row, form a composite key: `(fare_media_name, fare_media_type)`.
3. Track the first occurrence of each key in a lookup map.
4. If a row's key matches an already-seen key, emit a `duplicate_fare_media` notice referencing both the first occurrence and the current row.
5. If there are more than two rows with the same key, each subsequent row after the first is paired with the first occurrence (not with the previous duplicate). The first row seen is always the "left" side of the notice.

### Key semantics

- The composite key uses the actual string value of `fare_media_name` and the enum value of `fare_media_type`.
- Two rows with different `fare_media_id` values but the same `(fare_media_name, fare_media_type)` trigger a notice.
- Two rows with the same type but different names do NOT trigger a notice.
- Two rows with the same name but different types do NOT trigger a notice.

## 4. Notices emitted

All notices have severity **WARNING**.

| Notice code | Fields | Description |
|---|---|---|
| `duplicate_fare_media` | `csv_row_number_1`, `fare_media_id_1`, `csv_row_number_2`, `fare_media_id_2` | Two distinct fare media entries share the same name and type |

### Notice field details

| Field | Type | Description |
|---|---|---|
| `csv_row_number_1` | int | Row number of the first (earlier) fare media |
| `fare_media_id_1` | string | ID of the first fare media |
| `csv_row_number_2` | int | Row number of the duplicate fare media |
| `fare_media_id_2` | string | ID of the duplicate fare media |

Referenced file: `fare_media.txt`.

## 5. Edge cases

- **Empty fare_media.txt**: No rows to iterate, no notices emitted.
- **fare_media.txt not present in feed**: Validator does not run (no table to inject). No notices.
- **Single row**: No duplicates possible. No notices.
- **Null/empty fare_media_name**: If two rows both have a null or empty `fare_media_name` and the same `fare_media_type`, they will match on the composite key and produce a notice. The Java `Key` uses `media.fareMediaName()` which returns an empty string when not set, so two rows with missing names and the same type are considered duplicates.
- **Three or more rows with the same key**: The first row becomes the "existing" entry. Each subsequent row produces a separate notice, always paired with the first row. For N rows sharing a key, N-1 notices are emitted.
- **Same fare_media_id on two rows**: This would already be caught by the primary key uniqueness check (a load-time validation). If it somehow passes, this validator would still flag the name+type duplicate independently.
- **Different names, same type**: No notice (keys differ).
- **Same name, different types**: No notice (keys differ).

## 7. Implementation notes

### Validator type

File-level (single-table) validator. Consumes only `fare_media.txt`.

### Polars implementation strategy

This validator groups rows by `(fare_media_name, fare_media_type)` and flags groups with more than one row. A natural Polars approach:

1. Select the relevant columns: `fare_media_id`, `fare_media_name`, `fare_media_type`, and the row index (csv_row_number).
2. Fill null `fare_media_name` with empty string to ensure null-null matches.
3. Group by `(fare_media_name, fare_media_type)`.
4. Filter groups with count > 1.
5. Within each group, pair the first row with every subsequent row to emit notices.

Alternatively, use a `self-join` or `partition_by` approach. Since fare_media tables are typically small (tens of rows), any approach is fine performance-wise.

### Notice field naming

Java uses `csvRowNumber1`, `fareMediaId1`, `csvRowNumber2`, `fareMediaId2`. Python equivalents: `csv_row_number_1`, `fare_media_id_1`, `csv_row_number_2`, `fare_media_id_2`.

### Simplicity

This is one of the simplest cross-row validators -- no joins with other tables, no date logic, no complex algorithms. It is a straightforward duplicate-key detection on a single table with a composite key.

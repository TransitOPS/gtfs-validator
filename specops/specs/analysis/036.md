# Analysis: NetworkIdConsistencyValidator

## 1. Purpose

Detects when `routes.txt` contains a `network_id` column while `route_networks.txt` or `networks.txt` is also present, because route network identifiers must be specified in exactly one place.

## 2. Input tables

| Table | Columns used |
|---|---|
| `routes.txt` | presence of `network_id` column (header-level check only; no row data needed) |
| `route_networks.txt` | file presence only; no column data read |
| `networks.txt` | file presence only; no column data read |

The validator does not read any row values. It only inspects:
- Whether `routes.txt` has a `network_id` column in its header (i.e., the column was declared in the CSV).
- Whether `route_networks.txt` is a missing file vs. present.
- Whether `networks.txt` is a missing file vs. present.

## 3. Validation logic

The validation is a pure file-presence cross-check. No row iteration occurs.

Step-by-step rules:

1. **Check for `network_id` column in `routes.txt`**: Determine whether the parsed `routes.txt` header includes the `network_id` field. If the column is absent, the entire validator exits with no notices.

2. **If `network_id` is present in `routes.txt`, check `route_networks.txt`**: If `route_networks.txt` is present (not a missing file), emit `route_networks_specified_in_more_than_one_file` with `file_name_a = "routes.txt"`, `file_name_b = "route_networks.txt"`, `field_name = "network_id"`.

3. **If `network_id` is present in `routes.txt`, check `networks.txt`**: If `networks.txt` is present (not a missing file), emit `route_networks_specified_in_more_than_one_file` with `file_name_a = "routes.txt"`, `file_name_b = "networks.txt"`, `field_name = "network_id"`.

4. Steps 2 and 3 are independent checks. Both can fire in the same validation run, producing two notices if all three files are present simultaneously.

5. Neither check inspects any row contents; the notices are about structural/file-level redundancy, not individual data values.

## 4. Notices emitted

### `route_networks_specified_in_more_than_one_file` (ERROR)

Emitted when route network identifiers are redundantly defined across multiple files. Specifically, `routes.txt` has a `network_id` column and at least one of `route_networks.txt` or `networks.txt` is also present.

| Field | Type | Value |
|---|---|---|
| `file_name_a` | string | Always `"routes.txt"` |
| `file_name_b` | string | `"route_networks.txt"` or `"networks.txt"` depending on which conflicting file is present |
| `field_name` | string | Always `"network_id"` |

Severity: ERROR.

At most two notices can be emitted per feed (one for `route_networks.txt`, one for `networks.txt`). Notices are emitted independently; zero, one, or two may be emitted in a single run.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `routes.txt` absent from feed | Validator has no route table to inspect; treat as no `network_id` column present — no notices. |
| `routes.txt` present but `network_id` column absent from header | No notices; guard clause exits early. |
| `routes.txt` has `network_id` column, both `route_networks.txt` and `networks.txt` absent | No notices. |
| `routes.txt` has `network_id` column, only `route_networks.txt` present | One notice: `file_name_b = "route_networks.txt"`. |
| `routes.txt` has `network_id` column, only `networks.txt` present | One notice: `file_name_b = "networks.txt"`. |
| `routes.txt` has `network_id` column, both `route_networks.txt` and `networks.txt` present | Two notices, one per conflicting file. |
| `routes.txt` has `network_id` column with all values null/empty | Column presence is what matters; null values in rows do not affect the check. |
| `route_networks.txt` present but `routes.txt` lacks `network_id` column | No notices; the guard on `network_id` column presence exits early. |

## 6. Test contracts

### `validatesConditionalForbiddenFilePresenceNoNotice`

- Setup: `routes.txt` loaded with `network_id` column present (route `"123"` with `network_id = "network1"`). Both `route_networks.txt` and `networks.txt` are set to `MISSING_FILE`.
- Expected: No notices emitted.

### `validatesConditionalForbiddenFilePresence1`

- Setup: `routes.txt` loaded with `network_id` column (same as above). `route_networks.txt` is present with a `GtfsRouteNetwork` entry (`route_id = "123"`, `network_id = "network1"`). `networks.txt` remains `MISSING_FILE`.
- Expected: Exactly one notice of type `RouteNetworksSpecifiedInMoreThanOneFileNotice` with `fileNameA = "routes.txt"`, `fileNameB = "route_networks.txt"`, `fieldName = "network_id"`.

### `validatesConditionalForbiddenFilePresence2`

- Setup: `routes.txt` loaded with `network_id` column (same as above). `route_networks.txt` remains `MISSING_FILE`. `networks.txt` is present with a `GtfsNetwork` entry (`network_id = "network1"`).
- Expected: Exactly one notice of type `RouteNetworksSpecifiedInMoreThanOneFileNotice` with `fileNameA = "routes.txt"`, `fileNameB = "networks.txt"`, `fieldName = "network_id"`.

Note: The test assertions in the Java source use `assertThat(expr)` without chaining a condition method (e.g., `.isTrue()`), which means the assertions are effectively no-ops in the Java test framework (they always pass). The behavioral contracts described above are derived from the validator implementation logic, not from trusting these test assertions to be correct.

## 7. Implementation notes

### Approach

This validator performs no Polars operations on row data. The check is entirely about column and file presence metadata, which the Python orchestrator already tracks.

In the Python implementation, the relevant inputs are:

1. Whether `"routes"` is in `feed` and whether its DataFrame has a column named `"network_id"`.
2. Whether `"route_networks"` is in `feed` (table present).
3. Whether `"networks"` is in `feed` (table present).

The implementation in plain Python (no Polars required):

```python
routes = feed.get("routes")
has_network_id_col = routes is not None and "network_id" in routes.columns

if has_network_id_col:
    if "route_networks" in feed:
        notices.append(RouteNetworksSpecifiedInMoreThanOneFileNotice(
            file_name_a="routes.txt",
            file_name_b="route_networks.txt",
            field_name="network_id",
        ))
    if "networks" in feed:
        notices.append(RouteNetworksSpecifiedInMoreThanOneFileNotice(
            file_name_a="routes.txt",
            file_name_b="networks.txt",
            field_name="network_id",
        ))
```

No joins, no group-by, no row iteration needed.

### Column presence vs. column non-null

The check is purely about the column being declared in the CSV header, not about whether any row has a non-null `network_id` value. A `routes.txt` with `network_id` column present but all values null/empty still triggers the check. In Polars, column presence is `"network_id" in df.columns`, which is correct.

### Notice code

Notice code: `"route_networks_specified_in_more_than_one_file"` (derived from Java class name `RouteNetworksSpecifiedInMoreThanOneFileNotice` following the project's snake_case convention).

### Feed dict keys

- `routes.txt` → `"routes"` key in `feed`
- `route_networks.txt` → `"route_networks"` key in `feed`
- `networks.txt` → `"networks"` key in `feed`

### Validator registration

Register with `requires=["routes"]`. The `route_networks` and `networks` tables are optional; their absence is handled inside the validator by checking `"route_networks" in feed` and `"networks" in feed`.

Alternatively, `requires=[]` with all three table lookups guarded by `feed.get(...)` is equally correct given the guard on `routes` column presence.

### Notice field naming

The Java notice uses `fileNameA`, `fileNameB`, and `fieldName`. The Python Notice dataclass should use `file_name_a`, `file_name_b`, and `field_name` per the project's snake_case notice field convention.

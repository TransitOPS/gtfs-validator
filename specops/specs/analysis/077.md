# Analysis: TranslationFieldAndReferenceValidator

## 1. Purpose

Validates that each row in `translations.txt` uses the correct combination of `field_value`, `record_id`, and `record_sub_id` fields, and that when a row references an entity by record ID it actually exists in the referenced table.

---

## 2. Input tables

| Table | Columns used |
|---|---|
| `translations.txt` | `table_name`, `field_name`, `language`, `record_id`, `record_sub_id`, `field_value`, `csv_row_number` |
| Every other GTFS table that may be referenced by `table_name` | Primary key column(s) — looked up by name at runtime |

### Column semantics

- `table_name` — required string; names the target GTFS table (e.g., `"agency"`, `"stop_times"`). The validator appends `.txt` to form a filename (`"agency.txt"`) and resolves it against the feed container.
- `field_name` — required string; names the translated field in the target table.
- `language` — required BCP-47 language tag.
- `translation` — required string; the translated text (not validated here).
- `record_id` — conditionally required string; first part of the entity key. Required when the referenced table has a single primary key column mapped to `RECORD_ID`. Forbidden when `field_value` is present or when the target table has zero translatable key columns (e.g., `feed_info`).
- `record_sub_id` — conditionally required string; second part of the entity key. Required when the referenced table has a two-column translatable primary key (e.g., `stop_times.trip_id` / `stop_times.stop_sequence`). Forbidden when `field_value` is present.
- `field_value` — conditional alternative to `record_id`/`record_sub_id`. When present, the row is matched by scanning for a row where the named field equals this value; `record_id` and `record_sub_id` must then be empty.

---

## 3. Validation logic

### 3.1 Legacy format guard (first check)

```
if translations.txt header does NOT contain column "table_name":
    # This is the legacy Google translation format
    return  # no validation performed at all
```

The legacy Google format pre-dates the standard GTFS `translations.txt` and omits `table_name`. If detected, the entire validator is skipped gracefully.

### 3.2 Standard required fields check

Before processing individual rows, all rows are scanned to confirm that `table_name`, `field_name`, and `language` are non-null. These are required in the standard format.

```
for each translation row:
    if field_name is null/empty:
        emit MissingRequiredFieldNotice(filename="translations.txt", row, field_name="field_name")
        isValid = false
    if language is null/empty:
        emit MissingRequiredFieldNotice(filename="translations.txt", row, field_name="language")
        isValid = false
    if table_name is null/empty:
        emit MissingRequiredFieldNotice(filename="translations.txt", row, field_name="table_name")
        isValid = false

if isValid == false:
    return  # skip per-row validation entirely
```

If any row is missing any of these three fields, the per-row validation phase is aborted entirely (early return after emitting all MissingRequiredFieldNotice instances).

### 3.3 Per-row validation

For each translation row (only reached when all rows pass the required-fields check):

```
validateTranslation(translation):

    # Step A: field_value mutual exclusion with record_id / record_sub_id
    if field_value is present:
        if record_id is present:
            emit TranslationUnexpectedValueNotice(row, field_name="record_id", value=record_id)
        if record_sub_id is present:
            emit TranslationUnexpectedValueNotice(row, field_name="record_sub_id", value=record_sub_id)
        # No further checks for this row when field_value is present and no conflicts
        # (even if the parent table lookup fails, we do not check reference integrity)

    # Step B: resolve parent table
    parent_table = feed.getTableForFilename(table_name + ".txt")

    if parent_table is absent OR parent_table.isMissingFile():
        emit TranslationUnknownTableNameNotice(row, table_name=table_name)
        return  # no reference integrity check

    # Step C: reference integrity (only when field_value is absent)
    if field_value is absent:
        if parent_table is a GtfsTableContainer (CSV-backed, not JSON):
            validateReferenceIntegrity(translation, parent_table)
        # JSON-backed tables: TODO (skipped in current Java implementation)
```

### 3.4 Reference integrity sub-routine

```
validateReferenceIntegrity(translation, parent_table):
    key_columns = parent_table.getKeyColumnNames()
    # key_columns holds only the columns annotated @PrimaryKey
    # for which translationRecordIdType is NOT UNSUPPORTED.
    # Size is 0, 1, or 2 depending on the table.

    # Check record_id
    record_id_expected = (key_columns.size >= 1)
    mismatch = isMissingOrUnexpectedField(
        hasValue=record_id is present,
        expectedPresent=record_id_expected,
        fieldName="record_id",
        fieldValue=record_id)

    if mismatch:
        return  # abort; notice already emitted inside helper

    # Check record_sub_id
    sub_id_expected = (key_columns.size >= 2)
    mismatch = isMissingOrUnexpectedField(
        hasValue=record_sub_id is present,
        expectedPresent=sub_id_expected,
        fieldName="record_sub_id",
        fieldValue=record_sub_id)

    if mismatch:
        return  # abort; notice already emitted

    # Lookup entity by translation key
    entity = parent_table.byTranslationKey(record_id, record_sub_id)
    if entity is absent:
        emit TranslationForeignKeyViolationNotice(row)
```

### 3.5 `isMissingOrUnexpectedField` helper

```
isMissingOrUnexpectedField(hasValue, expectedPresent, fieldName, fieldValue) -> bool:
    if hasValue == expectedPresent:
        return false  # correct; no notice

    if hasValue and not expectedPresent:
        emit TranslationUnexpectedValueNotice(row, fieldName, fieldValue)
        return true

    if not hasValue and expectedPresent:
        emit MissingRequiredFieldNotice("translations.txt", row, fieldName)
        return true
```

## 4. Notices emitted

### `missing_required_field` (ERROR)

Reused general notice; see the load-time validator for its full definition.

Emitted in two contexts within this validator:

**Context A — standard format required fields missing (section 3.2)**

| Field | Type | Value |
|---|---|---|
| `filename` | string | `"translations.txt"` |
| `csv_row_number` | int | Row of the offending translation |
| `field_name` | string | `"table_name"`, `"field_name"`, or `"language"` |

Conditions: The header contains `"table_name"` (standard format detected), AND the named field is null/empty for that row.

**Context B — reference integrity: `record_id` or `record_sub_id` missing (section 3.4)**

| Field | Type | Value |
|---|---|---|
| `filename` | string | `"translations.txt"` |
| `csv_row_number` | int | Row of the offending translation |
| `field_name` | string | `"record_id"` or `"record_sub_id"` |

Conditions: `field_value` is absent, parent table exists, the referenced table requires the given key field (key column count >= 1 for `record_id`, >= 2 for `record_sub_id`), but the field is absent in the translation row.

---

### `translation_unexpected_value` (ERROR)

A field in a translations row has a value but must be empty.

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | int | `translations.csv_row_number` | Row of the offending translation |
| `field_name` | string | `"record_id"` or `"record_sub_id"` | Name of the field that should be empty |
| `field_value` | string | `translation.record_id` or `translation.record_sub_id` | Actual value found |

Severity: ERROR.

Conditions — two cases:

1. `field_value` is present AND `record_id` is also present → `field_name="record_id"`, `field_value=record_id`.
2. `field_value` is present AND `record_sub_id` is also present → `field_name="record_sub_id"`, `field_value=record_sub_id`.
3. `field_value` is absent AND parent table exists AND the referenced table does NOT use the field (key column count < 1 for `record_id`, or < 2 for `record_sub_id`), but the field is present anyway.

Both cases 1/2 can be emitted for the same row (when both `record_id` and `record_sub_id` are set alongside `field_value`).

---

### `translation_unknown_table_name` (WARNING)

A translation references an unknown or missing GTFS table.

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | int | `translations.csv_row_number` | Row of the offending translation |
| `table_name` | string | `translations.table_name` | The unrecognized table name |

Severity: WARNING.

Conditions: `table_name + ".txt"` does not correspond to any table in the feed, OR the file is marked as missing.

---

### `translation_foreign_key_violation` (ERROR)

An entity with the given `record_id` and `record_sub_id` cannot be found in the referenced table.

| Field | Type | Source | Description |
|---|---|---|---|
| `csv_row_number` | int | `translations.csv_row_number` | Row of the offending translation |
| `table_name` | string | `translations.table_name` | The referenced table name |
| `record_id` | string | `translations.record_id` | The record ID provided |
| `record_sub_id` | string | `translations.record_sub_id` | The record sub-ID provided (may be empty) |

Severity: ERROR.

Conditions: `field_value` is absent, parent table exists, `record_id`/`record_sub_id` presence matches expectations, AND no entity with those key values exists in the parent table. Also emitted when `record_sub_id` is expected to be an integer (for tables like `stop_times` where the sub-ID maps to `stop_sequence`) but the string cannot be parsed as such.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `translations.txt` absent from feed | Validator is not invoked (runner guard). Return `[]`. |
| `translations.txt` present but empty | Legacy check passes; standard required-fields loop iterates zero rows (`isValid` stays `true`); per-row loop iterates zero rows. Return `[]`. |
| Header missing `"table_name"` column | Legacy format detected; return immediately with no notices. |
| Row missing `field_name`, `language`, or `table_name` in standard format | `MissingRequiredFieldNotice` emitted for each missing field across all rows; per-row validation aborted entirely (no reference checks). |
| `table_name` does not map to any known GTFS table | `TranslationUnknownTableNameNotice` (WARNING) emitted; reference integrity skipped. |
| `table_name` maps to a present-but-empty table | Parent table exists (not missing); reference integrity proceeds; entity lookup returns empty; `TranslationForeignKeyViolationNotice` emitted. |
| `field_value` is set, `record_id` absent, `record_sub_id` absent | No notices for mutual exclusion; parent table lookup still done; if table unknown → WARNING; otherwise no reference check (field_value path). |
| `field_value` and `record_id` both set | `TranslationUnexpectedValueNotice` for `record_id`. |
| `field_value` and `record_sub_id` both set | `TranslationUnexpectedValueNotice` for `record_sub_id`. |
| `field_value`, `record_id`, and `record_sub_id` all set | Two `TranslationUnexpectedValueNotice` (one for each). |
| Target table has 0 translatable key columns (e.g., `feed_info`) | `record_id_expected=false`, `sub_id_expected=false`; if `record_id` is absent and `record_sub_id` is absent → proceed to `byTranslationKey(null, null)` which should return the single entity; if `record_id` is present → `TranslationUnexpectedValueNotice`. |
| Target table has 1 translatable key column (e.g., `agency`, `stops`, `routes`, `trips`) | `record_id` required; `record_sub_id` not expected. Missing `record_id` → `MissingRequiredFieldNotice`. Unexpected `record_sub_id` → `TranslationUnexpectedValueNotice` and abort before lookup. |
| Target table has 2 translatable key columns (e.g., `stop_times`) | Both `record_id` and `record_sub_id` required. If `record_sub_id` is not a valid integer for the numeric sub-key → `byTranslationKey` will fail to find the entity → `TranslationForeignKeyViolationNotice`. |
| `record_id` present but does not match any entity | `TranslationForeignKeyViolationNotice`. |
| `record_id` present and matches an entity | No notice from this check. |
| JSON-backed tables referenced | Reference integrity silently skipped (Java TODO; treat as no-op). |
| Multiple rows in one feed have violations | All are processed and all notices emitted (the per-row loop does not short-circuit on errors). |

### What is NOT covered by the Java test suite

- `translations.txt` absent from feed (runner guard).
- `translations.txt` present but empty.
- Legacy format with entities present.
- Both `record_id` and `record_sub_id` present alongside `field_value` (only one at a time is tested).
- Multiple rows with mixed errors.
- A table name that appears in the feed but is JSON-backed (GeoJSON tables).
- A translation row where `record_id` missing AND `record_sub_id` missing for a 2-key table.
- `record_sub_id` present but table only needs `record_id` (unexpected sub-ID for single-key table).

## 7. Implementation notes

### Algorithm strategy

The validator has three sequential phases:

1. **Legacy guard** — inspect whether `"table_name"` appears as a header column in `translations.txt`. In the Python implementation, check whether the column exists and is not entirely null/absent.
2. **Required-fields scan** — iterate all translation rows and confirm `table_name`, `field_name`, `language` are non-null. Emit `missing_required_field` for any violation. Abort phase 3 if any row fails.
3. **Per-row validation** — for each row: check mutual exclusion of `field_value` with `record_id`/`record_sub_id`, resolve the parent table, then validate reference integrity.

### Legacy format detection

In Java, this is done by checking whether the CSV header object contains the `"table_name"` column name. In Python/Polars, after loading `translations.txt`, check if the column `"table_name"` is present in the DataFrame. If the column is absent, return `[]` immediately.

An alternative approach: check whether all rows in `translations.table_name` are null — however, the Java checks the header, not the data, so the correct Python equivalent is to check for column presence.

Since the Python loader enforces required fields at load time, the "legacy" detection needs special handling. The schema marks `table_name` as `_R` (required), which means the load-time validator would already emit errors for missing values. However, the legacy format completely omits the `table_name` column from the CSV header. The correct approach is to treat a fully-null `table_name` column (or absent column) as a signal to skip this validator. This should be guarded using a column-existence check or by inspecting whether the column was present in the raw loaded data.

### Key column count per table

The `record_id` / `record_sub_id` requirement depends on the number of translatable primary key columns in the referenced table. Based on the Java schema annotations:

| Table | Translatable key columns | `record_id` required | `record_sub_id` required |
|---|---|---|---|
| `feed_info` | 0 (no `@PrimaryKey`) | No | No |
| `agency` | 1 (`agency_id`) | Yes | No |
| `stops` | 1 (`stop_id`) | Yes | No |
| `routes` | 1 (`route_id`) | Yes | No |
| `trips` | 1 (`trip_id`) | Yes | No |
| `calendar` | 1 (`service_id`) | Yes | No |
| `fare_attributes` | 1 (`fare_id`) | Yes | No |
| `levels` | 1 (`level_id`) | Yes | No |
| `pathways` | 1 (`pathway_id`) | Yes | No |
| `attributions` | 1 (`attribution_id`) | Yes | No |
| `stop_times` | 2 (`trip_id`, `stop_sequence`) | Yes | Yes |
| `calendar_dates` | 2 (`service_id`, `date`) | Yes | Yes |
| `shapes` | 2 (`shape_id`, `shape_pt_sequence`) | Yes | Yes |
| `frequencies` | 2 (`trip_id`, `headway_secs`) | Yes | Yes |
| `transfers` | 2 (`from_stop_id`, `to_stop_id`) | Yes | Yes |
| `fare_rules` | 0 (all PKs are UNSUPPORTED) | No | No |

In the Python implementation, represent this as a dict mapping filename stem to `(record_id_key, record_sub_id_key)` where each is either a column name (string) or `None`:

```python
TRANSLATION_KEYS: dict[str, tuple[str | None, str | None]] = {
    "agency":          ("agency_id",       None),
    "stops":           ("stop_id",         None),
    "routes":          ("route_id",        None),
    "trips":           ("trip_id",         None),
    "calendar":        ("service_id",      None),
    "fare_attributes": ("fare_id",         None),
    "levels":          ("level_id",        None),
    "pathways":        ("pathway_id",      None),
    "attributions":    ("attribution_id",  None),
    "stop_times":      ("trip_id",         "stop_sequence"),
    "calendar_dates":  ("service_id",      "date"),
    "shapes":          ("shape_id",        "shape_pt_sequence"),
    "frequencies":     ("trip_id",         "headway_secs"),
    "transfers":       ("from_stop_id",    "to_stop_id"),
    "feed_info":       (None,              None),
    "fare_rules":      (None,              None),
}
```

If `table_name` is not in this dict (or the corresponding file is not loaded in the feed), emit `translation_unknown_table_name`.

### Entity lookup

Java's `byTranslationKey(record_id, record_sub_id)` looks up an entity using the translated key columns. In Python/Polars:

- For tables with 0 key columns (e.g., `feed_info`): the table must be non-empty; always succeeds if the table has at least one row.
- For 1-key tables: filter the DataFrame for rows where the key column equals `record_id`. If the result is non-empty, the reference exists.
- For 2-key tables: filter for rows where key column 1 equals `record_id` AND key column 2 equals `record_sub_id`. For numeric sub-key columns (e.g., `stop_sequence`, `shape_pt_sequence`, `headway_secs`), attempt to parse `record_sub_id` as an integer before comparison; if parsing fails, the lookup returns no rows → `translation_foreign_key_violation`.

Use Polars filter expressions for the lookup rather than row-by-row Python iteration, as the parent tables can be large.

### Polars vs plain Python

Recommended approach:

- **Polars eager** for building lookup sets: pre-build a `dict[str, set]` for each potentially-referenced table, mapping `(record_id, record_sub_id)` tuples to a boolean. This avoids repeated Polars filter calls inside the per-row loop.
- **Plain Python** for the per-row validation loop over `translations.txt`, which is typically small.
- **No row-by-row Python iteration** over large tables like `stop_times`; instead build the lookup set once using Polars `.select()` + `.iter_rows()`.

### Guard clauses

```python
def validate_translation_field_and_reference(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "translations" not in feed:
        return []
    translations = feed["translations"]
    if translations.is_empty():
        return []
    # Legacy format check: if table_name column is missing or all-null
    if "table_name" not in translations.columns or translations["table_name"].is_null().all():
        return []
```

```python
    code: ClassVar[str] = "translation_unknown_table_name"
    severity: ClassVar[Severity] = Severity.WARNING

@dataclass

    code: ClassVar[str] = "translation_foreign_key_violation"

```

### Feed dict keys

- `"translations"` — `translations.txt`
- Other table keys as named in `SCHEMA_REGISTRY` (e.g., `"agency"`, `"stop_times"`, `"feed_info"`, etc.)

### Validator registration

Required tables: `["translations"]`. Other tables are accessed via the feed dict with graceful fallback if absent (table not found → `translation_unknown_table_name`). No feature flag required.

### Interaction with load-time validators

The load-time validators already enforce:
- Required field presence for `table_name`, `field_name`, `language`, `translation` (since they are `_R` in the schema).
- PK uniqueness on `(table_name, field_name, language, record_id, record_sub_id, field_value)`.

However, the Java validator performs its own required-field check for `table_name`, `field_name`, `language` and aborts per-row logic if any are missing. This is because in the legacy-format support mode the schema can relax these as optional. In Python, since the legacy path is handled by the guard clause (column absent → return early), the load-time required-field enforcement will apply normally for standard-format feeds. The Python validator can rely on the load-time validator having already emitted `missing_required_field` for these three fields, and can skip phase 2 of the Java logic — OR it can re-implement the phase 2 abort to match Java semantics exactly. Matching Java semantics exactly is the safer choice for behavioral equivalence.

# Analysis: OverlappingPickupDropOffZoneValidator

## 1. Purpose

Detects when two `stop_times.txt` entries in the same trip have overlapping pickup/drop-off time windows AND overlapping geographic zones (as defined by their corresponding `locations.geojson` polygons), which would create an ambiguous or conflicting service area during that time period.

## 2. Input tables

| Table | Columns used |
|---|---|
| `stop_times.txt` | `trip_id`, `stop_sequence`, `location_id`, `pickup_type`, `drop_off_type`, `start_pickup_drop_off_window`, `end_pickup_drop_off_window` |
| `locations.geojson` | Per-feature: `id`, `geometry_type`, `coordinates` (used to build Shapely geometry for overlap testing) |

### Data model notes

`locations_geojson` in the Python feed is a `list[dict]` (not a Polars DataFrame), where each dict has at minimum:
- `"id"` — the feature ID string (matches `location_id` in `stop_times.txt`)
- `"geometry_type"` — `"Polygon"` or `"MultiPolygon"`
- `"coordinates"` — nested coordinate array

Pickup/drop-off type values are integers:
- 0: `REGULAR`
- 1: `NOT_AVAILABLE`
- 2: `MUST_PHONE`
- 3: `ON_REQUEST_TO_DRIVER`
- Any other value: `UNRECOGNIZED`

## 3. Validation logic

The check is an all-pairs comparison of stop times within each trip, filtered by time-window overlap and geographic overlap.

### Step-by-step algorithm

1. **Guard: missing files.** If either `stop_times` or `locations_geojson` is absent from the feed, return immediately with no notices.

2. **Group by `trip_id`.** Partition all rows from `stop_times.txt` into groups, one per distinct `trip_id`.

3. **All-pairs comparison within each trip.** For each trip group, compare every pair `(stopTime1, stopTime2)` where `i < j` in the group (i.e., each unordered pair is examined exactly once). The Java implementation does not sort by `stop_sequence`; it iterates in the order the stop times are stored in the group.

4. **Skip if pickup/drop-off types are incompatible.** For a pair to be flagged, at least one of the following must match between the two entries:
   - `stopTime1.pickup_type == stopTime2.pickup_type`, OR
   - `stopTime1.drop_off_type == stopTime2.drop_off_type`

   More precisely: skip the pair if **both** of the following are true simultaneously:
   - `stopTime1.pickup_type != stopTime2.pickup_type`, AND
   - `stopTime1.drop_off_type != stopTime2.drop_off_type`

   Additionally, skip the pair if **any** of the four pickup/drop-off type values is `UNRECOGNIZED` (i.e., not one of 0, 1, 2, 3).

   Note: the Java condition reads:
   ```
   if ((stopTime1.pickupType() != stopTime2.pickupType()
           && stopTime1.dropOffType() != stopTime2.dropOffType())
       || (stopTime1.pickupType() == UNRECOGNIZED
           || stopTime1.dropOffType() == UNRECOGNIZED
           || stopTime2.pickupType() == UNRECOGNIZED
           || stopTime2.dropOffType() == UNRECOGNIZED))
   ```
   This means: skip if (pickup AND drop-off both differ) OR (any value is UNRECOGNIZED).

5. **Skip if required fields are missing.** Skip the pair if any of the following fields are null/missing in either stop time:
   - `start_pickup_drop_off_window`
   - `end_pickup_drop_off_window`
   - `location_id`

6. **Skip if same location.** If `stopTime1.location_id == stopTime2.location_id`, skip (a zone cannot overlap with itself in a meaningful way for this check).

7. **Skip if time windows do not overlap.** The windows `[start1, end1)` and `[start2, end2)` overlap if and only if:
   - `start1 < end2` AND `start2 < end1`

   The Java uses the equivalent: skip if any of the following hold:
   - `start1 > end2` (stopTime1 starts after stopTime2 ends)
   - `end1 < start2` (stopTime1 ends before stopTime2 starts)
   - `end1 == start2` (touching at endpoint, stopTime1 ends exactly when stopTime2 starts)
   - `start1 == end2` (touching at endpoint, stopTime2 ends exactly when stopTime1 starts)

   Therefore: windows must **strictly overlap** — touching endpoints (abutting) are **not** considered overlapping and do not trigger a notice.

8. **Look up GeoJSON features.** Retrieve the geometry for `stopTime1.location_id` and `stopTime2.location_id` from the `locations_geojson` data. If either location ID has no corresponding GeoJSON feature (lookup returns null/not found), skip the pair.

9. **Check geometric overlap.** Using the JTS/Shapely `overlaps()` predicate, test whether the two geometries overlap. `overlaps()` returns `true` if the geometries share some but not all interior points — specifically it returns `true` when the intersection is non-empty and has the same dimension as the geometries, but the geometries are not identical. If `geometryDefinition` is null for either feature, return false (no overlap). Note: Shapely's `.overlaps()` method is the direct equivalent of JTS `Geometry.overlaps()`.

10. **Emit notice.** If the geometric overlap check passes, emit one `overlapping_zone_and_pickup_drop_off_window` notice per qualifying pair.

### Overlap predicate (formal)

Two time windows `[s1, e1]` and `[s2, e2]` strictly overlap (step 7) if and only if:
```
s1 < e2  AND  s2 < e1
```
(Both start-to-end comparisons are strict; endpoint touching produces false.)

Two geometries geographically overlap (step 9) if:
```
geom1.overlaps(geom2)  # Shapely / JTS DE-9IM predicate
```
This is true when geometries have the same dimension, their intersection has the same dimension, but neither contains the other entirely. Two polygons sharing only a boundary edge or point do NOT return true from `.overlaps()`.

### Pickup/drop-off type: default values

In `stop_times.txt`, `pickup_type` defaults to `0` (REGULAR) and `drop_off_type` defaults to `0` (REGULAR) when not specified. This means that if both fields are absent from both stop times, they both default to REGULAR (0), satisfying the "same pickup_type" condition and NOT being skipped by the type check.

## 4. Notices emitted

### `overlapping_zone_and_pickup_drop_off_window` (ERROR)

Emitted when two stop times within the same trip have overlapping time windows and overlapping geographic zones.

| Field | Type | Source | Description |
|---|---|---|---|
| `trip_id` | string | `stopTime1.trip_id` (same as `stopTime2.trip_id`) | The shared trip identifier |
| `stop_sequence1` | integer | `stopTime1.stop_sequence` | Stop sequence of the first entry |
| `location_id1` | string | `stopTime1.location_id` | Location ID of the first entry |
| `start_pickup_drop_off_window1` | string (HH:MM:SS) | `stopTime1.start_pickup_drop_off_window` | Start of the first entry's pickup/drop-off window |
| `end_pickup_drop_off_window1` | string (HH:MM:SS) | `stopTime1.end_pickup_drop_off_window` | End of the first entry's pickup/drop-off window |
| `stop_sequence2` | integer | `stopTime2.stop_sequence` | Stop sequence of the second entry |
| `location_id2` | string | `stopTime2.location_id` | Location ID of the second entry |
| `start_pickup_drop_off_window2` | string (HH:MM:SS) | `stopTime2.start_pickup_drop_off_window` | Start of the second entry's pickup/drop-off window |
| `end_pickup_drop_off_window2` | string (HH:MM:SS) | `stopTime2.end_pickup_drop_off_window` | End of the second entry's pickup/drop-off window |

Severity: ERROR.

The Java notice class is `OverlappingZoneAndPickupDropOffWindowNotice`. The Python notice code follows snake_case convention: `overlapping_zone_and_pickup_drop_off_window`.

Multiple notices may be emitted per trip if more than two entries form overlapping pairs.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `stop_times.txt` absent | Return immediately, no notices. |
| `locations_geojson` absent | Return immediately, no notices. |
| `stop_times.txt` empty | No trips to iterate; no notices. |
| `locations_geojson` empty list | Geometry lookups return null for all IDs; all pairs are skipped at step 8; no notices. |
| Single stop time in a trip | No pairs to compare; no notices. |
| Both stop times reference the same `location_id` | Skipped at step 6; no notice. |
| Time windows touch at endpoint (`end1 == start2` or `start1 == end2`) | Not overlapping per the strict predicate; no notice. |
| Time windows are identical | Strictly overlapping (each start < the other's end); proceed to geometry check. |
| `start_pickup_drop_off_window` or `end_pickup_drop_off_window` is null | Pair is skipped at step 5; no notice. |
| `location_id` is null on either stop time | Pair is skipped at step 5; no notice. |
| `pickup_type` and `drop_off_type` are both different between the two stop times | Pair is skipped at step 4; no notice. |
| Any pickup/drop-off type value is unrecognized (outside 0–3) | Pair is skipped at step 4; no notice. |
| `location_id` refers to a feature not in `locations_geojson` | Geometry lookup returns null; pair is skipped at step 8; no notice. |
| GeoJSON feature has null/missing geometry (`geometryDefinition == null`) | `geometryOverlaps()` returns false; no notice. |
| Two polygons touch at a single point or share a boundary edge | `overlaps()` returns false (JTS/Shapely DE-9IM semantics); no notice. |
| Two polygons that are identical/contained within each other | `overlaps()` returns false (one would need to use `intersects()` for containment); no notice from this validator. |
| Multiple pairs within a trip all qualify | One notice emitted per qualifying pair; all are independent. |

## 6. Test contracts

### `overlappingPickupDropOffZonesShouldGenerateNotice`

- Setup: Two GeoJSON features:
  - Feature `"1"`: polygon `[(0,0), (4,0), (4,4), (0,4), (0,0)]` (square 0–4)
  - Feature `"2"`: polygon `[(2,2), (6,2), (6,6), (2,6), (2,2)]` (square 2–6, overlapping with feature 1)
- Stop times for trip `"t0"`:
  - Seq 1: `location_id="1"`, `pickup_type=1`, window `05:00–07:00`
  - Seq 2: `location_id="2"`, `pickup_type=1`, window `06:00–08:00`
- Expected: 1 notice of type `OverlappingZoneAndPickupDropOffWindowNotice`. Both conditions met — windows overlap (`06:00 < 07:00`) and geometries overlap (two partially-overlapping squares).

### `nonOverlappingPickupDropOffWindowsShouldNotGenerateNotice`

- Setup: Same two overlapping GeoJSON features as above.
- Stop times for trip `"t0"`:
  - Seq 1: `location_id="1"`, window `05:00–07:00` (no `pickup_type` set, defaults to 0)
  - Seq 2: `location_id="2"`, window `07:00–08:00` (no `pickup_type` set, defaults to 0)
- Expected: 0 notices. Time windows touch at `07:00` but do not strictly overlap (`end1 == start2`); skipped at step 7.

### `nonOverlappingPickupDropOffZonesShouldNotGenerateNotice`

- Setup: Two GeoJSON features that do NOT overlap:
  - Feature `"1"`: small square `[(0,0), (2,0), (2,2), (0,2), (0,0)]`
  - Feature `"2"`: distant square `[(5,5), (7,5), (7,7), (5,7), (5,5)]`
- Stop times for trip `"t0"`:
  - Seq 1: `location_id="1"`, window `05:00–07:00` (no `pickup_type` set, defaults to 0)
  - Seq 2: `location_id="2"`, window `06:00–08:00` (no `pickup_type` set, defaults to 0)
- Expected: 0 notices. Time windows overlap, but geometries do not; skipped at step 9.

## 7. Implementation notes

### Algorithm choice

Per AGENTS.md, plain Python is preferred for graph/geometry/interval logic when clearer and safer than forcing Polars. This validator combines time-interval comparison and geometry overlap testing. The recommended approach:

1. Use Polars to extract the relevant columns from `stop_times` and group by `trip_id`.
2. Build a Python dict mapping `location_id -> Shapely geometry` from the `locations_geojson` list using Shapely at lookup time (or pre-build during validation setup).
3. For each trip group, collect rows to Python dicts and run the all-pairs comparison in plain Python.
4. Use Shapely's `.overlaps()` for geometric testing.

This avoids forcing Polars into O(n²) pair generation and geometry operations, which Polars is not designed for.

### Time comparison

GTFS time strings are in `HH:MM:SS` format. Convert to total seconds for comparison:

```python
def _time_to_secs(t: str) -> int:
    h, m, s = t.split(":")
    return int(h) * 3600 + int(m) * 60 + int(s)
```

The strict overlap predicate becomes: `s1 < e2 and s2 < e1` (where `s1`, `e1`, `s2`, `e2` are integer seconds).

### Geometry lookup and Shapely overlap

The `locations_geojson` feed value is a `list[dict]` where each dict has `"id"`, `"geometry_type"`, and `"coordinates"`. Build a lookup dict from feature ID to Shapely geometry before the pair loop:

```python
from shapely.geometry import Polygon, MultiPolygon, shape

def _build_geometry_index(geojson_features: list[dict]) -> dict[str, object]:
    index = {}
    for f in geojson_features:
        fid = f.get("id")
        geom_type = f.get("geometry_type")
        coords = f.get("coordinates")
        if not fid or not geom_type or coords is None:
            continue
        try:
            geom = shape({"type": geom_type, "coordinates": coords})
        except Exception:
            continue  # invalid geometry handled by geojson_geometry validator
        index[fid] = geom
    return index
```

Then the geometry check is:
```python
geom1 = geom_index.get(location_id1)
geom2 = geom_index.get(location_id2)
if geom1 is None or geom2 is None:
    continue
if geom1.overlaps(geom2):
    # emit notice
```

Shapely's `shape()` function reconstructs a geometry from a GeoJSON-like dict. Alternatively, build Shapely objects at load time and store them in the feature dict under a `"geometry"` key — but that requires coordination with the loading module.

### Pickup/drop-off type: null and default handling

In `stop_times.txt`, `pickup_type` defaults to `0` (REGULAR) when absent. The Python loader should apply this default during loading so the validator can assume non-null integer values for `pickup_type` and `drop_off_type`. If either value is null after loading, treat as `UNRECOGNIZED` (skip the pair).

UNRECOGNIZED values are those outside the range 0–3. The check:
```python
RECOGNIZED = {0, 1, 2, 3}
if (pickup_type1 not in RECOGNIZED or drop_off_type1 not in RECOGNIZED or
    pickup_type2 not in RECOGNIZED or drop_off_type2 not in RECOGNIZED):
    continue
if pickup_type1 != pickup_type2 and drop_off_type1 != drop_off_type2:
    continue
```

### Polars grouping

Use `partition_by("trip_id", maintain_order=False)` or `group_by("trip_id")` to split the stop times DataFrame into per-trip groups. For each group, collect to `iter_rows(named=True)` and apply the all-pairs loop.

### Notice code

`"overlapping_zone_and_pickup_drop_off_window"` (derived from Java class `OverlappingZoneAndPickupDropOffWindowNotice` following the project's snake_case convention).

### Feed dict keys

- `"stop_times"` — `stop_times.txt`
- `"locations_geojson"` — `locations.geojson` parsed features (list of dicts)

### Guard for missing tables

```python
stop_times = feed.get("stop_times")
geojson_features = feed.get("locations_geojson")
if stop_times is None or stop_times.is_empty():
    return []
if not geojson_features:
    return []
```

### Required columns in stop_times

The validator needs: `trip_id`, `stop_sequence`, `location_id`, `pickup_type`, `drop_off_type`, `start_pickup_drop_off_window`, `end_pickup_drop_off_window`. Not all feeds will have `location_id` or the window columns — check for column existence before proceeding.

### Validator registration

Requires: `["stop_times", "locations_geojson"]`.

### Dependency on Shapely

Shapely is already a project dependency (used by `geojson_geometry.py`). No new dependencies needed.

### Performance note

This validator is O(n²) per trip in the number of stop times. For typical flex-service feeds with many demand-responsive zones, the number of stop times per trip using `location_id` is expected to be small (typically 2–10). If the stop times table is large, pre-filter to rows that have non-null `location_id` and non-null window fields before the all-pairs loop.

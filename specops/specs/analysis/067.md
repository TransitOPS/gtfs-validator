# Analysis: StopZoneIdValidator

## 1. Purpose

Checks that every stop/platform (`location_type = 0`) used in a trip whose
route has a zone-dependent fare rule (`origin_id`, `destination_id`, or
`contains_id`) has `stops.zone_id` assigned; emits an INFO notice for each
stop that is missing `zone_id` in that context.

## 2. Input tables

| Table | Columns used |
|---|---|
| `stops.txt` | `stop_id`, `stop_name`, `location_type`, `zone_id`, `csv_row_number` |
| `fare_rules.txt` | `route_id`, `origin_id`, `destination_id`, `contains_id` |
| `stop_times.txt` | `stop_id`, `trip_id` |
| `trips.txt` | `trip_id`, `route_id` |
| `routes.txt` | `route_id` |

### Column semantics

- `stops.location_type` — integer enum; only rows where `location_type = 0`
  (i.e. STOP/platform) are evaluated. All other location types are unconditionally
  skipped.
- `stops.zone_id` — optional string; a null/empty value indicates the stop has
  no zone assigned.
- `fare_rules.origin_id`, `fare_rules.destination_id`, `fare_rules.contains_id`
  — optional strings; any non-null value in any of these three columns means
  that fare rule is "zone-dependent".
- `fare_rules.route_id` — optional string; links the zone-dependent fare rule
  to a specific route. May be null (global rule not tied to a route).
- `stop_times.stop_id` / `stop_times.trip_id` — FK linkage: stop appears in
  trip.
- `trips.trip_id` / `trips.route_id` — FK linkage: trip belongs to route.

## 3. Validation logic

### Step 1 — Guard: fare_rules.txt absent or empty

If `fare_rules.txt` is absent or contains zero rows, return immediately with no
notices.

### Step 2 — Guard: no zone structure in fare_rules.txt

Scan all rows of `fare_rules.txt`. If no row has a non-null value in any of
`origin_id`, `destination_id`, or `contains_id`, return immediately with no
notices.

This "hasFareZoneStructure" check short-circuits the entire validator when the
feed's fare model is purely route-based (no zone columns used anywhere).

### Step 3 — Build the "routes with zone fields" set

From `fare_rules.txt`, collect the set of `route_id` values (which may be null)
where the row has at least one of `origin_id`, `destination_id`, or
`contains_id` non-null.

Call this set `routes_with_zone_fare`. It is the set of route IDs explicitly
linked to zone-dependent fare rules. (Fare rules that have zone fields but no
`route_id` are represented in `fare_rules.txt` but their `route_id` is null;
such rules contribute a null key to the multimap but do not match any real
route.)

### Step 4 — For each stop with location_type = 0 and no zone_id

Iterate stops where:
- `location_type = 0` (STOP)
- `zone_id` is null/empty

For each such stop, determine whether it is "in scope" by tracing:

```
stop_id
  -> stop_times (filter by stop_id) -> trip_id values
  -> trips (look up each trip_id) -> route_id values
  -> check if any route_id is in routes_with_zone_fare
```

If any route reachable from this stop is in `routes_with_zone_fare`, emit one
`StopWithoutZoneIdNotice` for this stop and move on to the next stop (break
after first match).

### Summary of the chain

```
stop (no zone_id, location_type=0)
  -[stop_times.stop_id]-> stop_times rows
  -[stop_times.trip_id]-> trips rows
  -[trips.route_id]-> routes
  -> is any route_id in fare_rules rows with zone columns? -> emit notice
```

One notice per violating stop, regardless of how many routes link it to
zone-dependent fare rules.

## 4. Notices emitted

### `stop_without_zone_id` (INFO)

Emitted when a stop with `location_type = 0` has no `zone_id` and is
reachable via `stop_times -> trips -> routes` from a fare rule with at least
one zone column (`origin_id`, `destination_id`, or `contains_id`).

| Field | Type | Source | Description |
|---|---|---|---|
| `stop_id` | string | `stops.stop_id` | The ID of the stop missing `zone_id` |
| `stop_name` | string | `stops.stop_name` | The name of the stop |
| `csv_row_number` | int | `stops.csv_row_number` | Row number of the stop in stops.txt |

Severity: INFO.

Condition: `location_type == 0` AND `zone_id` is null AND at least one route
serving this stop appears as `route_id` in a `fare_rules` row that has at least
one of `origin_id`, `destination_id`, `contains_id` non-null.

One notice per qualifying stop; at most once per stop regardless of how many
routes link to zone-dependent fare rules.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `fare_rules.txt` absent from feed | Return `[]` immediately (guard step 1). |
| `fare_rules.txt` present but empty (zero rows) | Return `[]` immediately (guard step 1). |
| `fare_rules.txt` has rows but none use zone columns | Return `[]` immediately (guard step 2 — `hasFareZoneStructure` is false). |
| `fare_rules.txt` has zone columns but `route_id` is null for those rows | `routes_with_zone_fare` contains null; null does not match any trip's `route_id`, so no notices are emitted for stops via that path. |
| Stop with `location_type != 0` (station, entrance, node, boarding area) | Unconditionally skipped, even if `zone_id` is missing. |
| Stop with `location_type = 0` and `zone_id` present | Skipped; notice is only for stops missing `zone_id`. |
| Stop with `location_type = 0`, no `zone_id`, but its route is not in any zone-based fare rule | No notice; the route must appear in a zone-dependent fare rule row. |
| Stop not referenced by any `stop_times` row | `getTripsIncludingStop` returns empty set; `getRoutesIncludingStop` returns empty set; no route match possible; no notice. |
| Stop referenced in `stop_times` but its `trip_id` is not in `trips.txt` | `tripTable.byTripId()` returns empty; that stop_time is skipped; effectively the stop is treated as having no route. |
| Stop's trip references a `route_id` not in `routes.txt` | `routeTable.byRouteId()` returns empty; no route added; route match not possible. |
| Multiple routes serving the same stop, only one in zone fare rule | Notice is emitted (first match triggers break). |
| Multiple violating stops | One notice per violating stop. |
| All stops have `zone_id` | No notices emitted. |
| `stops.txt` absent | Return `[]` (no stops to iterate). |
| `stop_times.txt` absent | No linkage possible; no notices emitted. |
| `trips.txt` absent | No route linkage possible; no notices emitted. |

## 6. Test contracts

The Java test file (`StopZoneIdValidatorTest.java`) contains nine test methods.

### `stop_zoneIdNotProvided_routeNotInFareRules_noNotice`

- Stop: `location_type=STOP`, `zone_id=null`.
- Fare rules: four rules, none have a `route_id` (so `fare_rules.route_id` is
  null for all), but three have zone fields. The stop's route is
  `toRouteId(0)`, which does not appear as a `route_id` in any fare rule.
- Expected: no notices.
- Rationale: even though zone fields exist, the stop's route is not mentioned
  in any fare rule row; no match in `routesWithZoneFieldsDefined`.

### `stop_zoneIdNotProvided_routeInFareRulesWithoutZoneFields_noNotice`

- Stop: `location_type=STOP`, `zone_id=null`.
- Fare rules: one rule with `route_id=toRouteId(0)` but no zone fields.
- Expected: no notices.
- Rationale: `hasFareZoneStructure` returns false (no zone columns in any fare
  rule), so the validator exits at guard step 2.

### `stop_zoneIdNotProvided_routeInFareRulesWithOriginId_yieldsNotice`

- Stop: `location_type=STOP`, `zone_id=null`.
- Fare rules: one rule with `route_id=toRouteId(0)` AND `origin_id` set.
- Expected: exactly one `StopWithoutZoneIdNotice(stop)`.
- Rationale: stop has no `zone_id`; its route appears in a zone-dependent fare
  rule (via `origin_id`).

### `stop_zoneIdNotProvided_routeInFareRulesWithDestinationId_yieldsNotice`

- Stop: `location_type=STOP`, `zone_id=null`.
- Fare rules: one rule with `route_id=toRouteId(0)` AND `destination_id` set.
- Expected: exactly one `StopWithoutZoneIdNotice(stop)`.
- Rationale: same as above but trigger column is `destination_id`.

### `stop_zoneIdNotProvided_routeInFareRulesWithContainsId_yieldsNotice`

- Stop: `location_type=STOP`, `zone_id=null`.
- Fare rules: one rule with `route_id=toRouteId(0)` AND `contains_id` set.
- Expected: exactly one `StopWithoutZoneIdNotice(stop)`.
- Rationale: same as above but trigger column is `contains_id`.

### `stop_zoneIdNotProvided_routeInFareRulesWithAndWithoutZoneFields_yieldsNotice`

- Stop: `location_type=STOP`, `zone_id=null`.
- Fare rules: two rules for the same `route_id`; one without zone fields, one
  with `origin_id` set.
- Expected: exactly one `StopWithoutZoneIdNotice(stop)`.
- Rationale: the presence of even one zone-field fare rule for the route is
  sufficient to trigger a notice.

### `stop_zoneIdProvided_noNotice`

- Stop: `location_type=STOP`, `zone_id` is non-null.
- Fare rules: six rules covering all combinations of zone/route fields.
- Expected: no notices.
- Rationale: stop has `zone_id`; it is skipped in the inner check.

### `allLocationTypesExceptStop_noNotice`

- Stops: all `GtfsLocationType` values except STOP, each tested with and
  without `zone_id`.
- Fare rules: six rules covering all combinations of zone/route fields.
- Expected: no notices for any non-STOP location type.
- Rationale: validator skips rows where `location_type != STOP`.

### `emptyFareRule_allStopLocationTypes_noZoneId_noNotice`

- All `GtfsLocationType` values, each with `zone_id=null`.
- Fare rules: empty list (`ImmutableList.of()`).
- Expected: no notices.
- Rationale: guard step 1 — empty `fare_rules.txt` exits immediately.

### `emptyFareRule_allStopLocationTypes_zoneId_noNotice`

- All `GtfsLocationType` values, each with `zone_id` set.
- Fare rules: empty list (`List.of()`).
- Expected: no notices.
- Rationale: guard step 1 — empty `fare_rules.txt` exits immediately.

### What is NOT covered by the Java test suite

- `fare_rules.txt` entirely absent from the feed.
- `stop_times.txt` absent from the feed.
- `trips.txt` absent from the feed.
- Stop not referenced in any `stop_times` row.
- Stop's `trip_id` from `stop_times` not found in `trips.txt`.
- Stop's `route_id` from `trips.txt` not found in `routes.txt`.
- Fare rule with zone fields but null `route_id` (global zone rule, not tied
  to any specific route).
- Multiple stops violating in one feed (multiple notices).
- All stops valid (no notices expected when all stops have `zone_id`).

## 7. Implementation notes

### Algorithm strategy

The Java implementation is a nested-loop chain:
  stop -> stop_times -> trips -> routes -> fare_rules match.

In Polars, this chain is naturally expressed as a series of joins, which is
both more efficient and idiomatic:

```
stops (location_type=0, zone_id null)
  JOIN stop_times ON stop_id
  JOIN trips ON trip_id
  JOIN fare_rules (zone-only) ON route_id
```

If any row survives all joins, the stop is a violator.

### Guard implementation

```python
if "fare_rules" not in feed or feed["fare_rules"].is_empty():
    return []

fare_rules = feed["fare_rules"]
zone_cols = ["origin_id", "destination_id", "contains_id"]
has_zone_structure = fare_rules.select(
    pl.any_horizontal([pl.col(c).is_not_null() for c in zone_cols if c in fare_rules.columns])
).to_series().any()
if not has_zone_structure:
    return []
```

### Recommended Polars approach

```python
def validate_stop_zone_id(
    feed: dict[str, pl.DataFrame], ctx: ValidationContext
) -> list[Notice]:
    if "fare_rules" not in feed or feed["fare_rules"].is_empty():
        return []

    fare_rules = feed["fare_rules"]
    zone_cols = [c for c in ("origin_id", "destination_id", "contains_id")
                 if c in fare_rules.columns]

    # Guard: at least one zone column is used anywhere
    if not fare_rules.select(
        pl.any_horizontal([pl.col(c).is_not_null() for c in zone_cols])
    ).to_series().any():
        return []

    # Build set of route_ids that appear in zone-dependent fare rules
    zone_fare_routes = (
        fare_rules
        .filter(pl.any_horizontal([pl.col(c).is_not_null() for c in zone_cols]))
        .select("route_id")
        .drop_nulls()
        .unique()
    )

    if "stops" not in feed or "stop_times" not in feed or "trips" not in feed:
        return []

    stops = feed["stops"]
    stop_times = feed["stop_times"]
    trips = feed["trips"]

    # Candidate stops: location_type=0, zone_id null
    candidates = stops.filter(
        (pl.col("location_type") == 0) & pl.col("zone_id").is_null()
    ).select("stop_id", "stop_name", "csv_row_number")

    if candidates.is_empty():
        return []

    # Trace: candidates -> stop_times -> trips -> routes
    violators = (
        candidates
        .join(stop_times.select("stop_id", "trip_id"), on="stop_id", how="inner")
        .join(trips.select("trip_id", "route_id"), on="trip_id", how="inner")
        .join(zone_fare_routes, on="route_id", how="inner")
        .select("stop_id", "stop_name", "csv_row_number")
        .unique(subset=["stop_id"])  # one notice per stop
    )

    notices: list[Notice] = []
    for row in violators.iter_rows(named=True):
        notices.append(
            StopWithoutZoneIdNotice(
                stop_id=row["stop_id"],
                stop_name=row["stop_name"],
                csv_row_number=row["csv_row_number"],
            )
        )
    return notices
```

### Polars vs plain Python

- The guard checks (empty fare_rules, no zone structure) use simple Polars
  aggregations and are naturally vectorized.
- The main logic is a multi-way join chain: use Polars joins throughout; do
  not loop over stops in Python.
- `unique(subset=["stop_id"])` enforces one notice per stop (mirrors the Java
  `break` after first matching route).
- Notice construction iterates over a small violations DataFrame;
  `iter_rows(named=True)` is acceptable there.

### Notice dataclass

```python
@dataclass
class StopWithoutZoneIdNotice:
    code: ClassVar[str] = "stop_without_zone_id"
    severity: ClassVar[str] = "INFO"
    stop_id: str
    stop_name: str
    csv_row_number: int
```

### Notice code derivation

The Java class is `StopWithoutZoneIdNotice`. The Python notice code follows
snake_case convention: `"stop_without_zone_id"`.

### Feed dict keys

- `"stops"` — `stops.txt`
- `"fare_rules"` — `fare_rules.txt`
- `"stop_times"` — `stop_times.txt`
- `"trips"` — `trips.txt`
- `"routes"` — `routes.txt` (used in Java to resolve route objects, but in the
  Polars join approach `routes.txt` is not strictly needed because the join on
  `route_id` goes directly from `trips.route_id` to `fare_rules.route_id`
  without needing to look up route objects; however if the schema requires
  `routes.txt` presence, add a guard)

### Validator registration

Required tables: `["stops", "fare_rules", "stop_times", "trips"]`.

Optional table: `"routes"` (used in Java but the Polars join skips the
routes table and goes trips -> fare_rules directly on `route_id`; this is
behaviorally equivalent because the Java only uses `route.routeId()` as a
lookup key, which is the same value as `trips.route_id`).

Feature flag: none needed. The validator self-guards on the presence and
content of `fare_rules.txt`.

### One-notice-per-stop guarantee

The Java implementation emits the notice and then calls `break` to stop
iterating routes for that stop. The Polars approach achieves the same result
by calling `.unique(subset=["stop_id"])` on the violators DataFrame before
iterating to build notices.

### Null `route_id` in fare_rules

A fare rule row may have zone fields (`origin_id` etc.) but no `route_id`
(a global zone rule). The Java code adds such a rule to the
`routesWithZoneFieldsDefined` multimap under the key `null`. The Java
`containsKey(route.routeId())` check then never matches null because actual
routes always have non-null `route_id` strings. The Polars implementation's
`drop_nulls()` on `zone_fare_routes` achieves identical behavior: global zone
rules with null `route_id` are silently excluded from the match set.

# Analysis: OverlappingFrequencyValidator

## 1. Purpose

Detects when two `frequencies.txt` entries for the same trip overlap in time, meaning the start time of one entry falls strictly before the end time of a preceding entry (when entries are sorted by start time).

## 2. Input tables

| Table | Columns used |
|---|---|
| `frequencies.txt` | `trip_id`, `start_time`, `end_time`, `headway_secs`, `csv_row_number` (internal row index) |

All five columns are required by the schema (`trip_id`, `start_time`, `end_time`, and `headway_secs` are all `@Required`). `csv_row_number` is the 1-based source row number tracked by the loader.

## 3. Validation logic

The check is an interval-overlap sweep per trip. Steps:

1. **Group by `trip_id`**: Partition all rows from `frequencies.txt` into groups, one per distinct `trip_id`. If the table is absent or empty, there are no groups and no notices.

2. **Sort each group**: Within each group, sort rows by `(start_time, end_time, headway_secs)` in ascending order. This secondary/tertiary sort is a tie-breaking convention — it does not affect the correctness of the overlap check for distinct start times, but it determines which row is labeled `prev` vs. `curr` when two rows share a start time.

3. **Adjacent pair scan**: Iterate through consecutive pairs `(prev, curr)` in the sorted group. For each pair, check whether `curr.start_time < prev.end_time`. The comparison is strictly less-than; equal times do not trigger the notice (i.e., `curr.start_time == prev.end_time` is valid — entries may abut).

4. **Emit notice on overlap**: If `curr.start_time < prev.end_time`, emit one `overlapping_frequency` notice carrying `prev`'s row number, `prev`'s end time, `curr`'s row number, `curr`'s start time, and the shared `trip_id`.

5. **Continue scanning**: The scan does not short-circuit after finding one overlap. It continues through all consecutive pairs in the sorted group, potentially emitting multiple notices per trip.

### Overlap condition (formal)

Two entries X and Y (where `X.start_time <= Y.start_time` after sorting) directly overlap if and only if:

```
Y.start_time < X.end_time
```

Note: the Java sort places X before Y when `X.start_time <= Y.start_time`. After sorting, the scan only examines adjacent pairs, so it catches direct overlaps between neighbors. For three mutually overlapping intervals, two notices are emitted: one for the first-second pair and one for the second-third pair.

### Time comparison

GTFS time strings have the format `HH:MM:SS` where the hour component may exceed 23 (e.g., `25:00:00` for a service past midnight). The Python implementation must convert time strings to a comparable integer (total seconds since midnight) before sorting and comparing, since lexicographic string comparison would fail for hours >= 10 with different digit counts (e.g., `"9:00:00"` vs `"10:00:00"`). However, the regex validator enforces `\d{1,2}:\d{2}:\d{2}`, so one-digit hours are possible.

Time-to-seconds conversion: `h * 3600 + m * 60 + s`.

## 4. Notices emitted

### `overlapping_frequency` (ERROR)

Emitted when two `frequencies.txt` entries for the same trip have overlapping time windows.

| Field | Type | Source | Description |
|---|---|---|---|
| `prev_csv_row_number` | integer | `prev` row's 1-based CSV row number | Row number of the first (earlier-starting) frequency entry |
| `prev_end_time` | string | `prev.end_time` (HH:MM:SS) | End time of the first frequency entry |
| `curr_csv_row_number` | integer | `curr` row's 1-based CSV row number | Row number of the overlapping (later-starting) frequency entry |
| `curr_start_time` | string | `curr.start_time` (HH:MM:SS) | Start time of the overlapping frequency entry |
| `trip_id` | string | `prev.trip_id` (same as `curr.trip_id`) | The shared trip identifier |

Severity: ERROR.

Multiple notices may be emitted per trip if more than two entries in the group overlap.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| `frequencies.txt` absent from feed | No notices; validator receives an empty or missing table and returns early. |
| `frequencies.txt` present but empty (zero data rows) | No notices; no pairs to examine. |
| Only one entry for a trip | No pairs exist; no notices. |
| Two entries with the same `start_time` | Sorted by `(start_time, end_time, headway_secs)`. The entry with the smaller `end_time` is `prev`. Since `curr.start_time == prev.start_time`, the condition `curr.start_time < prev.end_time` simplifies to `prev.start_time < prev.end_time`, which is always true (schema enforces `start_time < end_time`). A `DuplicateKeyNotice` is also emitted by the schema-level PK check (separate load-time validator), but `overlapping_frequency` is still emitted by this validator regardless. |
| Entries provided out of start-time order | Validator sorts them internally; ordering in the CSV file does not matter. |
| Adjacent entries touching exactly (`curr.start_time == prev.end_time`) | No notice; the condition is strictly less-than. |
| Three overlapping entries | Two notices: one for the first-second pair and one for the second-third pair after sorting. |
| Entries for different trips whose windows overlap | No notice; overlaps are only checked within a single `trip_id` group. |
| `start_time` or `end_time` null for a row | Schema marks both as `@Required`. If null values reach the validator (e.g., load-time validation was lenient), the time-to-seconds conversion will fail or produce null. The implementation should guard against null times — rows with null `start_time` or `end_time` should be skipped or handled gracefully. |

## 6. Test contracts

### `validSequentialInOrder`

- Input: trip `"t0"`, rows 2 and 3 with windows `05:00–07:00` and `07:00–10:00` (in order).
- Expected: no notices. Touching windows are valid.

### `validSequentialReversed`

- Input: trip `"t0"`, rows 2 and 3 with windows `07:00–10:00` and `05:00–07:00` (reversed in file).
- Expected: no notices. Validator sorts by start time; touching is still valid.

### `validWithGap`

- Input: trip `"t0"`, rows 2 and 3 with windows `05:00–07:00` and `08:00–10:00`.
- Expected: no notices. A gap between entries is valid.

### `validDifferentTrips`

- Input: two rows for different trips `"t0"` (`05:00–07:00`) and `"t1"` (`06:00–10:00`).
- Expected: no notices. Overlap check is per-trip only.

### `overlappingPartially`

- Input: trip `"t0"`, row 2 `05:00–07:00`, row 3 `06:00–10:00`.
- Expected: one `overlapping_frequency` notice with `prev_csv_row_number=2`, `prev_end_time="07:00:00"`, `curr_csv_row_number=3`, `curr_start_time="06:00:00"`, `trip_id="t0"`.

### `overlappingIncludedSameStart`

- Input: trip `"t0"`, row 2 `05:00–07:00`, row 3 `05:00–06:30`.
- After sort by `(start_time, end_time, headway_secs)`: row 3 (`05:00–06:30`, headway 300) comes before row 2 (`05:00–07:00`, headway 600) because `06:30 < 07:00`.
- Expected: one `DuplicateKeyNotice` (from load-time PK check) AND one `overlapping_frequency` notice with `prev_csv_row_number=3`, `prev_end_time="06:30:00"`, `curr_csv_row_number=2`, `curr_start_time="05:00:00"`, `trip_id="t0"`. Note prev/curr are flipped relative to file order due to sort.

### `overlappingIncludedSameEnd`

- Input: trip `"t0"`, row 2 `05:00–07:00`, row 3 `06:30–07:00`.
- Expected: one `overlapping_frequency` notice with `prev_csv_row_number=2`, `prev_end_time="07:00:00"`, `curr_csv_row_number=3`, `curr_start_time="06:30:00"`, `trip_id="t0"`.

### `overlappingIncluded`

- Input: trip `"t0"`, row 2 `07:00–12:00`, row 3 `08:00–11:00` (row 3 fully contained within row 2).
- Expected: one `overlapping_frequency` notice with `prev_csv_row_number=2`, `prev_end_time="12:00:00"`, `curr_csv_row_number=3`, `curr_start_time="08:00:00"`, `trip_id="t0"`.

### `overlappingThreeIntervals`

- Input: trip `"t0"`, row 2 `05:00–05:25`, row 3 `05:00–05:15`, row 4 `05:20–05:40`.
- After sort: row 3 (`05:00–05:15`, h=300) → row 2 (`05:00–05:25`, h=600) → row 4 (`05:20–05:40`, h=300).
- Expected: one `DuplicateKeyNotice` (rows 2 and 3 share `trip_id,start_time`) AND two `overlapping_frequency` notices:
  1. `prev=row3, prev_end="05:15:00", curr=row2, curr_start="05:00:00"` (pair 1-2 after sort).
  2. `prev=row2, prev_end="05:25:00", curr=row4, curr_start="05:20:00"` (pair 2-3 after sort).

## 7. Implementation notes

### Algorithm choice

Per AGENTS.md, plain Python algorithms are preferred over forced Polars when they are clearer and safer. The interval sweep is inherently sequential (each step depends on the previous sorted entry), making it a natural plain-Python loop. However, the grouping and sorting can use Polars efficiently before handing off to the per-group loop.

Recommended approach:

1. Use Polars to extract the frequencies table and convert time strings to integer seconds.
2. Group by `trip_id` using `partition_by("trip_id")` or `group_by("trip_id")` to get per-trip DataFrames.
3. For each per-trip DataFrame, sort by `(start_time_secs, end_time_secs, headway_secs)` and collect to Python rows.
4. Run the adjacent-pair sweep in plain Python.

### Time string to integer seconds

GTFS time strings remain as `Utf8` (string) in the loaded DataFrame — they are validated by regex but not cast to a numeric type by the loader. The validator must convert them to comparable integers. A pure Python helper:

```python
def _time_to_secs(t: str) -> int:
    h, m, s = t.split(":")
    return int(h) * 3600 + int(m) * 60 + int(s)
```

In Polars, this can be applied as a column expression using `str.split` and arithmetic, or via `map_elements` for simplicity. Storing as a new column `start_secs` and `end_secs` before sorting avoids repeated parsing.

### Sort key matches Java exactly

Java sorts by `Comparator.comparing(startTime).thenComparing(endTime).thenComparing(headwaySecs)`. The Python sort must match: `(start_secs, end_secs, headway_secs)` ascending.

### Notice field naming

Java notice fields use camelCase (`prevCsvRowNumber`, `prevEndTime`, `currCsvRowNumber`, `currStartTime`, `tripId`). Python notice dataclass fields should use snake_case: `prev_csv_row_number`, `prev_end_time`, `curr_csv_row_number`, `curr_start_time`, `trip_id`.

The `prev_end_time` and `curr_start_time` fields should be stored as the original time string (e.g., `"07:00:00"`), not as integers, to match the Java output format.

### Notice code

`"overlapping_frequency"` (derived from Java class name `OverlappingFrequencyNotice` following the project's snake_case convention).

### Feed dict key

`frequencies.txt` → `"frequencies"` key in `feed`.

### Guard for missing/empty table

```python
frequencies = feed.get("frequencies")
if frequencies is None or frequencies.is_empty():
    return []
```

### Interaction with DuplicateKeyNotice

When two rows share the same `(trip_id, start_time)`, the schema-level PK duplicate check emits a `DuplicateKeyNotice`. That is separate from this validator. This validator still runs on those rows and will emit `overlapping_frequency` as well, since two entries with the same start time always overlap (as long as each has `start_time < end_time`, which the end-range check enforces). The two notices coexist; the `overlapping_frequency` validator does not skip duplicate-key rows.

### Validator registration

Requires: `["frequencies"]`. No cross-table join needed; the check is entirely within `frequencies.txt`.

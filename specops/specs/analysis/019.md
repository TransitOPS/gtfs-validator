# Analysis: FeedExpirationDateValidator

## 1. Purpose

Validates that the feed's declared end date in `feed_info.txt` extends far enough into the future relative to the current validation date.

The GTFS Best Practices for Dataset Publishing define two thresholds:

1. **7-day threshold**: At any time, the published GTFS dataset should be valid for at least the next 7 days. Failure to meet this threshold is the more urgent concern and is checked first.
2. **30-day threshold**: When possible, the GTFS dataset should cover at least the next 30 days of service. Failure to meet this threshold (but not the 7-day threshold) is a softer recommendation.

The two thresholds are mutually exclusive: only one notice is ever emitted per row. If the 7-day condition triggers, the 30-day condition is skipped (via an early `return`). If the 7-day condition does not trigger, the 30-day condition is evaluated. If neither triggers, no notice is emitted.

The validator operates on each `feed_info.txt` row independently. Because `feed_info.txt` is a single-row table, at most one notice will ever be generated in practice.

If `feed_end_date` is absent (not set in the row), the entire check is skipped — no notice is emitted.

## 3. Validation logic

### Skip conditions

- If `feed_info.txt` is absent or empty, no rows are processed and no notices are emitted.
- If `feed_end_date` is null (absent from the row), skip this row entirely — no notice is emitted.

### Algorithm

Let:
- `current_date` = the validation date (from `ctx.date_for_validation`)
- `current_date_plus_7` = `current_date + 7 days`
- `current_date_plus_30` = `current_date + 30 days`

For each row in `feed_info.txt` where `feed_end_date` is non-null:

**Step 1 — 7-day check:**

```
if feed_end_date < current_date_plus_7:
    emit feed_expiration_date_7_days(
        csv_row_number=row.csv_row_number,
        current_date=current_date,
        feed_end_date=row.feed_end_date,
        suggested_expiration_date=current_date_plus_7,
    )
    STOP (do not check 30-day threshold)
```

The comparison is strict less-than (`<`). The `current_date_plus_7` boundary itself does NOT trigger the 7-day notice.

**Step 2 — 30-day check (only reached if Step 1 did not trigger):**

```
if feed_end_date < current_date_plus_30:
    emit feed_expiration_date_30_days(
        csv_row_number=row.csv_row_number,
        current_date=current_date,
        feed_end_date=row.feed_end_date,
        suggested_expiration_date=current_date_plus_30,
    )
```

The comparison is again strict less-than. The `current_date_plus_30` boundary itself does NOT trigger the 30-day notice.

If `feed_end_date >= current_date_plus_30`, no notice is emitted.

### Pseudocode

```
current_date       = ctx.date_for_validation
plus_7             = current_date + timedelta(days=7)
plus_30            = current_date + timedelta(days=30)

for each row in feed_info where row.feed_end_date is not null:
    end_date = row.feed_end_date

    if end_date < plus_7:
        emit feed_expiration_date_7_days(
            csv_row_number=row.csv_row_number,
            current_date=current_date,
            feed_end_date=end_date,
            suggested_expiration_date=plus_7,
        )
        continue  # skip 30-day check for this row

    if end_date < plus_30:
        emit feed_expiration_date_30_days(
            csv_row_number=row.csv_row_number,
            current_date=current_date,
            feed_end_date=end_date,
            suggested_expiration_date=plus_30,
        )
```

### What is NOT checked here

- Whether `feed_end_date` is a valid date (handled at load time via type casting).
- Whether `feed_start_date` precedes `feed_end_date` (handled by load-time end-range check in `load_validators.py`).
- Whether `feed_end_date` is present at all when it is recommended (that is a recommendation check; here, absence simply skips the expiration check).
- Whether `feed_start_date` is valid (handled separately).

## 4. Notices emitted

### `feed_expiration_date_7_days`

Severity: **WARNING**

Emitted when `feed_end_date` is less than 7 days after the current validation date (i.e., the feed expires in 6 days or fewer, or has already expired). The GTFS Best Practices require that a published dataset remain valid for at least the next 7 days.

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending row |
| `current_date` | string (YYYYMMDD) | The current validation date |
| `feed_end_date` | string (YYYYMMDD) | The declared feed end date |
| `suggested_expiration_date` | string (YYYYMMDD) | `current_date + 7 days` (the minimum acceptable end date) |

### `feed_expiration_date_30_days`

Severity: **WARNING**

Emitted when `feed_end_date` is at least 7 days away but less than 30 days after the current validation date (i.e., the feed expires in 7–29 days inclusive). The GTFS Best Practices recommend that a dataset cover at least the next 30 days of service.

| Field | Type | Description |
|---|---|---|
| `csv_row_number` | int | CSV row number of the offending row |
| `current_date` | string (YYYYMMDD) | The current validation date |
| `feed_end_date` | string (YYYYMMDD) | The declared feed end date |
| `suggested_expiration_date` | string (YYYYMMDD) | `current_date + 30 days` (the recommended minimum end date) |

## 5. Edge cases

- **`feed_end_date` absent (null)**: Skip the row entirely. No notice.
- **`feed_end_date` in the past**: Triggers `feed_expiration_date_7_days`. The past date is less than `current_date + 7`, so the 7-day notice fires.
- **`feed_end_date` is exactly today (`current_date`)**: `current_date < current_date + 7` is true, so triggers `feed_expiration_date_7_days`.
- **`feed_end_date` is `current_date + 6`**: Triggers `feed_expiration_date_7_days` (strict `<` with `current_date + 7`).
- **`feed_end_date` is exactly `current_date + 7`**: Does NOT trigger the 7-day notice (boundary excluded). Evaluates 30-day check: `current_date + 7 < current_date + 30` is true, so triggers `feed_expiration_date_30_days`.
- **`feed_end_date` is `current_date + 29`**: Does NOT trigger 7-day notice. Triggers `feed_expiration_date_30_days`.
- **`feed_end_date` is exactly `current_date + 30`**: Does NOT trigger either notice. Both boundaries are excluded.
- **`feed_end_date` is beyond `current_date + 30`**: No notice.
- **Month/year rollover**: Arithmetic is calendar date arithmetic; `current_date + 7` and `current_date + 30` correctly roll over month and year boundaries. The Java test uses `TEST_NOW = 2021-01-25` specifically to exercise the month rollover (Jan 25 + 7 = Feb 1, Jan 25 + 30 = Feb 24).
- **`feed_info.txt` absent**: No rows; no notices.
- **`feed_info.txt` empty (header only)**: No rows; no notices.
- **Multiple rows** (spec violation, but possible before loader enforcement): Each row is checked independently; both notices are emitted per violating row.
- **Only one notice per row**: If the 7-day condition fires, the 30-day condition is not evaluated and only one notice is emitted.

## 7. Implementation notes

### Validator type

Single-table, row-level validator. No joins, no cross-row state, no cross-table lookups required.

The validator depends on an external input — the current validation date — which is available via `ctx.date_for_validation` (a `datetime.date` object stored in `ValidationContext`).

### Validator signature

```python
def validate_feed_expiration_date(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

### Skip logic

```python
if "feed_info" not in feed or feed["feed_info"].is_empty():
    return []
```

### Polars implementation strategy

`feed_info.txt` is a single-row table, so performance is not a concern. The cleanest implementation iterates over non-null `feed_end_date` rows and applies sequential threshold checks.

```python
from datetime import timedelta
import polars as pl
from gtfs_validator.notices import Notice, Severity
from gtfs_validator.context import ValidationContext

def validate_feed_expiration_date(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
    if "feed_info" not in feed or feed["feed_info"].is_empty():
        return []

    current_date = ctx.date_for_validation
    plus_7  = current_date + timedelta(days=7)
    plus_30 = current_date + timedelta(days=30)

    df = feed["feed_info"].filter(pl.col("feed_end_date").is_not_null())
    notices: list[Notice] = []

    for row in df.iter_rows(named=True):
        end_date    = row["feed_end_date"]          # datetime.date after load-time cast
        row_number  = row["csv_row_number"]

        if end_date < plus_7:
            notices.append(Notice(
                code="feed_expiration_date_7_days",
                severity=Severity.WARNING,
                fields={
                    "csv_row_number":          row_number,
                    "current_date":            current_date.strftime("%Y%m%d"),
                    "feed_end_date":           end_date.strftime("%Y%m%d"),
                    "suggested_expiration_date": plus_7.strftime("%Y%m%d"),
                },
            ))
        elif end_date < plus_30:
            notices.append(Notice(
                code="feed_expiration_date_30_days",
                severity=Severity.WARNING,
                fields={
                    "csv_row_number":          row_number,
                    "current_date":            current_date.strftime("%Y%m%d"),
                    "feed_end_date":           end_date.strftime("%Y%m%d"),
                    "suggested_expiration_date": plus_30.strftime("%Y%m%d"),
                },
            ))

    return notices
```

Because `feed_info.txt` is a single-row table, `iter_rows` over the filtered subset imposes no performance concern.

### Notice codes (Python)

| Java notice class | Python notice code | Severity |
|---|---|---|
| `FeedExpirationDate7DaysNotice` | `feed_expiration_date_7_days` | WARNING |
| `FeedExpirationDate30DaysNotice` | `feed_expiration_date_30_days` | WARNING |

### Date arithmetic

The Java implementation uses `GtfsDate.plusDays(int)` which delegates to `LocalDate.plusDays`, providing correct calendar arithmetic (respecting month lengths and leap years). The Python equivalent is `datetime.date + timedelta(days=N)`, which is equally correct.

The test uses `TEST_NOW = 2021-01-25` specifically because adding 7 days rolls over to February 1 (month boundary) and adding 30 days rolls over to February 24 (month boundary). This confirms the implementation must use proper calendar arithmetic, not naive 30-day arithmetic.

### YYYYMMDD formatting of date fields in notices

The Java `GtfsDate` type serializes to `YYYYMMDD` strings. In Python, use `date.strftime("%Y%m%d")` to produce the same format for all three date fields in the notice (`current_date`, `feed_end_date`, `suggested_expiration_date`).

### Mutual exclusivity of notices

The two notice types are mutually exclusive: only one can be emitted per row. The `elif` in the Python pseudocode above enforces this. Never emit both notices for the same row.

### Relationship to load-time validation

The following are handled at load time and must not be duplicated here:

- `feed_end_date` type validation (valid YYYYMMDD date string).
- `feed_start_date` end-range check relative to `feed_end_date` (`feed_start_date <= feed_end_date`).
- Single-row enforcement for `feed_info.txt`.
- Required field presence checks for `feed_publisher_name`, `feed_publisher_url`, `feed_lang`.

This validator adds only the Best Practices date coverage checks on top of those load-time checks.

### Python schema reference

The `FEED_INFO` table definition in `src/gtfs_validator/schemas.py` includes `feed_end_date` typed as `_DATE` and marked `_REC` (recommended). No schema changes are needed. After the two-phase load, `feed_end_date` values are `datetime.date` objects (or `null` if absent).

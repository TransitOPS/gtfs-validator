# Analysis: ShapeToStopMatchingValidator

## 1. Purpose

For each shape in `shapes.txt`, validate that the stops of every trip referencing that
shape can be geometrically matched to the shape: specifically, that no stop is too far
from the shape, no stop has too many ambiguous candidate positions on the shape, and
that matched stop positions appear in the same order along the shape as the trip's
stop sequence.

## 2. Input tables

| Table | Columns used |
|---|---|
| `stops.txt` | `stop_id`, `stop_name`, `stop_lat`, `stop_lon`, `parent_station`, `location_type` |
| `trips.txt` | `trip_id`, `route_id`, `shape_id`, `csv_row_number` |
| `routes.txt` | `route_id`, `route_type` |
| `stop_times.txt` | `trip_id`, `stop_id`, `stop_sequence`, `shape_dist_traveled`, `csv_row_number` |
| `shapes.txt` | `shape_id`, `shape_pt_lat`, `shape_pt_lon`, `shape_pt_sequence`, `shape_dist_traveled` |

All five tables must be present for any validation to run.

## 3. Validation logic

This validator implements a complex geometric matching algorithm between stop
sequences and shapes. The logic is organized as follows.

### Step 1: Guard on empty tables

If any of the five tables (`stops`, `trips`, `stop_times`, `shapes`, `routes`) is
empty, return immediately with no notices.

### Step 2: Iterate over each shape

Group `shapes.txt` rows by `shape_id`. For each shape group:

1. Look up all trips that reference this `shape_id`.
2. If no trips reference the shape, skip it (no notices for shapes without trips).
3. Build a `ShapePoints` object from the shape group (see Section 3a below).

### Step 3: Deduplicate trips by stop-sequence fingerprint

Before processing the trips for a shape, maintain a set of already-processed
"trip hashes". A trip hash is computed from the sequence of `(stop_id,
shape_dist_traveled)` pairs in its stop times. If two trips produce the same hash,
they have identical stop sequences and shape dist values, so only the first is
processed. This avoids emitting duplicate notices for trips that serve identical
stop sequences.

Hash algorithm (FarmHash fingerprint64):
1. Start with `putInt(stopTimes.size())`.
2. For each stop time in sequence order: `putInt(len(stop_id))`, `putUnencodedChars(stop_id)`, `putDouble(shape_dist_traveled)`.

### Step 4: For each unique trip

For each trip that is not a duplicate:

#### 4a: Route lookup guard

Look up the route by `route_id` from the trip. If the route is not found, skip this
trip silently (broken FK is reported by a different validator).

#### 4b: Determine station size

Determine `station_size` from the route type:
- `route_type == RAIL (2)` → `LARGE`
- All other route types → `SMALL`

This affects the distance threshold for the first and last stops in LARGE-station
routes: they use `max_distance * large_station_multiplier` (default 4x) instead of
the base threshold.

#### 4c: Build stop points

Build a `StopPoints` list from the trip's stop times (ordered by `stop_sequence`):
- For each stop time, resolve the stop location from `stops.txt` using
  `stop_id`. If the stop has no lat/lon, walk up the `parent_station` chain (up to
  3 levels) to find coordinates. Fall back to (0, 0) if none found.
- Each stop point carries: its resolved `(lat, lon)`, its `shape_dist_traveled`
  (if any), a reference to the stop time row, and a `is_large_station` flag which
  is `True` only when `station_size == LARGE` AND the stop is the first or last stop
  in the trip's sequence.

#### 4d: Geo-distance matching (always performed)

Run `matchUsingGeoDistance(stopPoints, shapePoints)` and report its problems (see
Section 3b). This is the closest-point geometric matching.

#### 4e: User-distance matching (conditional)

If AND ONLY IF both of the following are true:
- The last stop point has a non-zero `shape_dist_traveled` (stop points have user
  distance)
- The last shape point has a non-zero `shape_dist_traveled` (shape points have user
  distance)

Then also run `matchUsingUserDistance(stopPoints, shapePoints)` and report its
problems.

### Section 3a: ShapePoints construction

Given a sorted list of shape rows (sorted by `shape_pt_sequence`):
- Track cumulative `geo_distance`: start at 0.0; for each consecutive pair, add the
  great-circle distance in metres between consecutive lat/lon points (using S2Earth
  formula, see Section 7).
- Track `user_distance` as the running maximum of `shape_dist_traveled` (coercing
  null to 0.0).
- Each ShapePoint stores: `(geo_distance, user_distance, location_as_S2Point)`.
- `hasUserDistance()` is true if the last shape point's `user_distance > 0.0`.

### Section 3b: Geo-distance matching algorithm

Input: a list of stop points and a list of shape points (both non-empty).

For each stop point, compute `potential_matches`: all local-minimum closest points on
the shape that are within `max_distance` of the stop (see algorithm below).

- If any stop's `potential_matches` is empty (stop too far), the matching fails for
  the entire trip and returns the problems accumulated so far.
- Otherwise, run a dynamic-programming best-assignment step to find an assignment of
  one match per stop where geo-distances along the shape are strictly non-decreasing,
  minimizing the total sum of `geo_distance_to_shape`.
- If no feasible assignment exists for a stop (because all candidate matches would
  require going backwards along the shape), emit a `STOPS_MATCH_OUT_OF_ORDER` problem.

Potential match computation per stop:
1. Scan all consecutive edge segments of the shape.
2. Project the stop location onto each edge; compute geo distance from stop to the
   closest point on that edge.
3. Track local-minimum "runs" of segments within `max_distance`. When the shape moves
   away beyond `max_distance` after being close, record the accumulated local minimum
   as a potential match.
4. If `potential_matches.size() > potentialMatchesForStopProblemThreshold` (default 20),
   emit `STOP_HAS_TOO_MANY_MATCHES` problem (this is not a fatal error; matching
   continues).
5. If `potential_matches` is empty (all segments are too far), find the single closest
   point on the entire shape; emit `STOP_TOO_FAR_FROM_SHAPE` problem and abort this
   trip's matching.

Default thresholds:
- `max_distance_from_stop_to_shape_in_meters` = 100.0
- `large_station_distance_multiplier` = 4.0 (used for first/last stops on RAIL routes)
- `potential_matches_for_stop_problem_threshold` = 20

### Section 3c: User-distance matching algorithm

Input: same stop points and shape points.

For each stop point:
- If it has a user distance (`shape_dist_traveled > 0`): interpolate a unique
  position on the shape at that user distance (starting search from the last matched
  index to enforce monotonicity).
- If it has no user distance: fall back to geo-distance potential matching (same
  algorithm as Section 3b).

After computing one match per stop, run the same best-assignment DP. Then validate
that each matched position is within `max_distance` of the stop; if not, emit
`STOP_TOO_FAR_FROM_SHAPE` problems.

### Step 5: Problem filtering and deduplication

When reporting problems for a trip:

1. Skip any problem where `stop_time.stop_id` is empty (stop times without a
   `stop_id` are ignored entirely).
2. For `STOP_TOO_FAR_FROM_SHAPE` problems only: maintain a per-shape set of already-
   reported `stop_id` values (`reportedStopIds`). If a `stop_id` has already been
   reported as too-far for the current shape (from a previous trip), skip it. This set
   is shared across all trips for the same shape, so each problematic stop is reported
   at most once per shape.
3. For `STOP_HAS_TOO_MANY_MATCHES` and `STOPS_MATCH_OUT_OF_ORDER`: always emit (no
   deduplication).

## 4. Notices emitted

### `stop_too_far_from_shape` (WARNING)

Emitted when a stop is more than `max_distance_from_stop_to_shape_in_meters` (default
100 m) from its best match on the shape, using geo-distance matching.

| Field | Type | Source | Description |
|---|---|---|---|
| `trip_csv_row_number` | integer | `trip.csv_row_number` | Row of the trip in `trips.txt` |
| `shape_id` | string | `trip.shape_id` | Shape referenced by the trip |
| `trip_id` | string | `trip.trip_id` | Trip ID |
| `stop_time_csv_row_number` | integer | `stop_time.csv_row_number` | Row of the offending stop_time in `stop_times.txt` |
| `stop_id` | string | `stop_time.stop_id` | Stop ID that is too far |
| `stop_name` | string | resolved from `stops` | Name of the stop (empty string if not found) |
| `match` | lat/lng | computed | The closest location on the shape to the stop |
| `geo_distance_to_shape` | float | computed | Distance in metres from stop to shape |

Deduplicated: only the first trip (per shape) that finds a stop too far causes a
notice for that `stop_id`. Subsequent trips referencing the same shape and stop emit
no additional notice.

### `stop_too_far_from_shape_using_user_distance` (WARNING)

Emitted when user-distance matching is used (both stop times and shape have
`shape_dist_traveled`) and a stop's user-distance-matched location is more than
`max_distance_from_stop_to_shape_in_meters` from the stop.

Same fields as `stop_too_far_from_shape`. The only difference is the notice code.
User-distance matching uses the same `reportedStopIds` set as geo-distance matching,
so the same stop is not reported twice across both matching modes.

### `stop_has_too_many_matches_for_shape` (WARNING)

Emitted when a stop has more than `potential_matches_for_stop_problem_threshold`
(default 20) candidate positions within `max_distance` on the shape.

| Field | Type | Source | Description |
|---|---|---|---|
| `trip_csv_row_number` | integer | `trip.csv_row_number` | Row of the trip in `trips.txt` |
| `shape_id` | string | `trip.shape_id` | Shape referenced by the trip |
| `trip_id` | string | `trip.trip_id` | Trip ID |
| `stop_time_csv_row_number` | integer | `stop_time.csv_row_number` | Row of the stop_time |
| `stop_id` | string | `stop_time.stop_id` | Stop ID with many matches |
| `stop_name` | string | resolved from `stops` | Name of the stop (empty string if not found) |
| `match` | lat/lng | computed | Closest match on shape (minimum geo_distance_to_shape among candidates) |
| `match_count` | integer | computed | Number of candidate matches found |

No deduplication across trips for this notice type.

### `stops_match_shape_out_of_order` (WARNING)

Emitted when two consecutive stops (by stop_sequence) match the shape in opposite
order to their position in the trip's sequence — i.e., stop B matches at a point
along the shape that comes before stop A's match, even though A precedes B in the
trip.

| Field | Type | Source | Description |
|---|---|---|---|
| `trip_csv_row_number` | integer | `trip.csv_row_number` | Row of the trip in `trips.txt` |
| `shape_id` | string | `trip.shape_id` | Shape referenced by the trip |
| `trip_id` | string | `trip.trip_id` | Trip ID |
| `stop_time_csv_row_number1` | integer | `stop_time1.csv_row_number` | Row of the first (out-of-order) stop_time |
| `stop_id1` | string | `stop_time1.stop_id` | Stop ID of the first stop |
| `stop_name1` | string | resolved | Name of the first stop |
| `match1` | lat/lng | computed | Best shape match for the first stop |
| `stop_time_csv_row_number2` | integer | `stop_time2.csv_row_number` | Row of the second (preceding) stop_time |
| `stop_id2` | string | `stop_time2.stop_id` | Stop ID of the second (earlier in sequence) stop |
| `stop_name2` | string | resolved | Name of the second stop |
| `match2` | lat/lng | computed | Best shape match for the second stop |

Note on field naming: `stopTime1` in the Java constructor is the current (later in
sequence) stop that failed to find a feasible assignment. `stopTime2` is the previous
stop. The names "1" and "2" in the notice fields follow the constructor argument order,
not temporal order — `1` is the later stop (the one that broke ordering), `2` is the
earlier stop.

No deduplication across trips for this notice type.

## 5. Edge cases

| Scenario | Expected behavior |
|---|---|
| Any of the five input tables is empty | Return immediately, no notices. |
| A shape has no trips referencing it | Skip the shape entirely, no notices. |
| Trip references a `route_id` not in `routes.txt` | Skip the trip silently (FK error reported elsewhere). |
| Multiple trips with identical stop-sequence fingerprint for the same shape | Only the first trip is processed; subsequent duplicates are silently skipped. |
| `stop_time.stop_id` is empty/null | That stop time is skipped in all problem reporting; no notice emitted for it. |
| Stop not found in `stops.txt` | `getStopOrParentLatLng` returns `(0, 0)` (S2LatLng.CENTER); `stopNameForStopTime` returns empty string `""`. The stop will very likely appear too far from the shape. |
| Stop has no lat/lon but has `parent_station` | Walk up to parent (up to 3 levels); use parent's lat/lon. If still no coordinates, fall back to (0, 0). |
| Stop is too far on geo-distance but within range on user-distance (or vice versa) | Each matching mode is evaluated independently; both can emit notices. |
| Both stop points and shape points lack `shape_dist_traveled` | User-distance matching is skipped (only geo-distance matching runs). |
| Only shape points have `shape_dist_traveled` | User-distance matching is skipped (stop points must also have user distance). |
| Only stop points have `shape_dist_traveled` | User-distance matching is skipped (shape points must also have user distance). |
| A stop has too many matches (> threshold) | `STOP_HAS_TOO_MANY_MATCHES` is emitted; matching continues with those candidates (not a fatal abort for the trip). |
| A stop has no matches within `max_distance` | `STOP_TOO_FAR_FROM_SHAPE` is emitted; matching aborts for this trip (no out-of-order check possible). |
| Same stop appears as too-far in multiple trips on the same shape | Only the first occurrence generates a notice; subsequent occurrences are deduplicated by `reportedStopIds`. |
| Shape has only one point | `matchFromLocation` handles this as a special case (single-point shape always returns that one point as the match). Multi-match detection across segments does not trigger. |
| First or last stop on a RAIL route | Distance threshold is multiplied by `large_station_distance_multiplier` (default 4.0 → 400 m effective threshold). |

## 7. Implementation notes

### Overall approach: pure Python geometry + Polars for data loading

This validator combines Polars for loading/grouping data with pure Python for the core
matching algorithm. Per AGENTS.md: "Use plain Python algorithms for
graph/geometry/interval logic when clearer and safer than forcing Polars."

The matching algorithm is inherently sequential (dynamic programming across stops in
sequence order, shape segment scanning) and cannot be vectorized over rows in a
meaningful way. Implement it as Python functions.

### Algorithm decomposition

Implement as a module `validators/shape_to_stop_matching.py` with these pieces:

1. **Data loading helpers** (use Polars):
   - Load each table from the `feed` dict.
   - Group shapes by `shape_id` using `group_by`.
   - Build `trip_id → stop_times` lookup (group `stop_times` by `trip_id`).
   - Build `shape_id → trips` lookup (group `trips` by `shape_id`).
   - Build `stop_id → stop` dict for coordinate/name resolution.

2. **`build_shape_points(shape_rows: list[dict]) -> list[ShapePoint]`**:
   - Sort by `shape_pt_sequence`.
   - Accumulate geo distance using great-circle formula (see below).
   - Track running max of `shape_dist_traveled`.

3. **`resolve_stop_location(stop_id: str, stops_by_id: dict) -> tuple[float, float]`**:
   - Walk `parent_station` chain up to 3 levels.
   - Return (lat, lon) from first stop with coordinates; else (0.0, 0.0).

4. **`build_stop_points(stop_times: list[dict], stops_by_id: dict, is_large_route: bool) -> list[StopPoint]`**:
   - Resolve location for each stop time.
   - Mark first and last as `is_large_station` if route is RAIL.

5. **`compute_trip_hash(stop_times: list[dict]) -> int`**:
   - Replicate the FarmHash fingerprint. Since Python does not have FarmHash natively,
     use a stable alternative (e.g., `hashlib` SHA256 or FNV) on a deterministic
     string encoding of `(stop_id, shape_dist_traveled)` pairs. Important: the hash
     only needs to be consistent within a single validation run (not across runs or
     versions). A simpler `tuple.__hash__` of `(tuple of (stop_id, shape_dist_traveled))`
     can work if Python's hash seed is fixed (set `PYTHONHASHSEED=0`) — but more
     robustly, compute a custom hash over the bytes manually.

6. **`match_using_geo_distance(stop_points, shape_points, settings) -> MatchResult`**:
   Pure Python implementation of the closest-point matching algorithm described in
   Section 3b.

7. **`match_using_user_distance(stop_points, shape_points, settings) -> MatchResult`**:
   Pure Python implementation of user-distance interpolation with fallback to geo
   matching for stops without user distance (Section 3c).

8. **`find_best_assignment(potential_matches_per_stop, stop_points) -> (list[Match], list[Problem])`**:
   DP algorithm: for each stop's candidate matches, find the lowest-score assignment
   where geo distances along the shape are non-decreasing.

### Great-circle / geodesic distance

Use the S2Earth formula (Earth mean radius = 6,371,010 m):

```python
import math

EARTH_RADIUS_METERS = 6_371_010.0

def geo_distance_meters(lat1: float, lon1: float, lat2: float, lon2: float) -> float:
    phi1, phi2 = math.radians(lat1), math.radians(lat2)
    dphi = phi2 - phi1
    dlambda = math.radians(lon2 - lon1)
    a = math.sin(dphi / 2)**2 + math.cos(phi1) * math.cos(phi2) * math.sin(dlambda / 2)**2
    return 2 * math.atan2(math.sqrt(a), math.sqrt(1 - a)) * EARTH_RADIUS_METERS
```

For projecting a stop point onto a shape edge (the closest point on a line segment),
use the S2 geometry closest-point formula. Since the S2 library is not available in
Python, implement the spherical edge-projection using vector math:

```python
# Convert lat/lon to unit 3D vector (S2Point equivalent)
def latlng_to_s2point(lat_deg: float, lon_deg: float) -> tuple[float, float, float]:
    lat, lon = math.radians(lat_deg), math.radians(lon_deg)
    return (math.cos(lat) * math.cos(lon),
            math.cos(lat) * math.sin(lon),
            math.sin(lat))

```

This is a non-trivial spherical geometry implementation. Refer to the S2 library
documentation or use a well-known pure-Python S2 alternative if one is added to the
project's dependencies. Alternatively, for a pragmatic approximation acceptable for
the distances involved (stops are within 100–400 m of shapes), use planar projection
via a local tangent-plane approximation.

**Recommendation**: add `s2sphere` or `spherical-geometry` as a project dependency
to get accurate S2-equivalent computations. If not available, implement the spherical
closest-point formula directly.

### `hasUserDistance` semantics

A stop point or shape point "has user distance" if and only if the **last** point's
`shape_dist_traveled > 0.0`. Null values are treated as 0.0.

### Performance notes

This is the most computationally expensive validator in the suite. For each shape, for
each non-duplicate trip, for each stop time, the algorithm iterates over all shape
segments (O(S)) to find candidate matches. For a shape with S segments and a trip with
T stops, cost is O(T * S) per trip. With many trips sharing the same shape, the trip-
hash deduplication significantly reduces redundant work.

Use Python dicts for all lookups (`stop_id → stop`, `trip_id → stop_times`, `shape_id
→ trips`) built once before the main loop, not repeated DataFrame filters.

Do not convert large DataFrames to Python lists globally. Instead, collect each group
(one shape at a time, one trip's stop_times at a time) to avoid excessive memory use.

### Complexity caveat

This validator is substantially more complex than other validators in the suite due to
the spherical geometry and DP matching algorithm. It is the one case where the AGENTS.md
guideline "use plain Python algorithms for graph/geometry logic" applies most strongly.
The core matching code should live in a helper module (e.g.,
`validators/shape_to_stop_matching_util.py`) with comprehensive unit tests independent
of the validator entry point.

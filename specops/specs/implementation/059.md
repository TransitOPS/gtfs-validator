# Implementation: StopRequiredLocationValidator

## 1. Module Location

**Validator:** `src/gtfs_validator/validators/stop_required_location.py`

No new shared utilities are required. The validator reads only `stops.txt`
and performs a single vectorized filter pass. No cross-table joins are
needed.

## 2. Function Signature

```python

from gtfs_validator.context import ValidationContext
from gtfs_validator.notices import Notice, Severity


def validate_stop_required_location(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

`ctx` is accepted for interface consistency but is not used by this
validator. No fields from `ValidationContext` are needed.

## 3. Notice Definitions

### `stop_without_location` (ERROR)

Emitted once per row where `location_type` is STOP (0), STATION (1), or
ENTRANCE (2) and at least one of `stop_lat` / `stop_lon` is null (absent or
unparseable).

```python
Notice(
    code="stop_without_location",
    severity=Severity.ERROR,
    fields={
        "csv_row_number": <int>,      # 1-based row number injected by loader
        "stop_id":        <str>,      # stops.stop_id of the offending row
        "location_type":  <int>,      # 0, 1, or 2
    },
)
```

One notice is emitted per offending row; there is no aggregation. If
`stop_lat` is present but `stop_lon` is null (or vice versa), the notice is
still emitted — partial presence is treated identically to full absence.

## 4. Implementation Approach

### Skip conditions

```
if "stops" not in feed:
    return []
if feed["stops"].is_empty():
    return []
```

No column-level guard is applied for `location_type`. If `location_type` is
absent from the DataFrame (column not in file header), the GTFS spec implies
all rows default to type 0 (STOP), which requires coordinates. In that case
the filter must treat every row as a potential STOP. The implementation
handles this via the `location_type` column presence check described below.

### Constants

```python
_REQUIRED_LOCATION_TYPES: list[int] = [0, 1, 2]  # STOP, STATION, ENTRANCE
```

### Column-absence handling

The loader injects `null` for cell-level missing values but does not add
columns that were absent from the file header. Two columns must be handled
defensively:

- `stop_lat` absent from header → treat all rows as having null lat → use
  `pl.lit(True)` for the `lat_missing` expression.
- `stop_lon` absent from header → same; use `pl.lit(True)` for
  `lon_missing`.
- `location_type` absent from header → all rows default to STOP (0), which
  is in `_REQUIRED_LOCATION_TYPES`. Substitute `pl.lit(0)` for the
  `location_type` column expression so the filter still runs correctly.

### Algorithm (pseudocode)

```
stops = feed["stops"]

# Determine location_type expression
if "location_type" in stops.columns:
    loc_type_expr = pl.col("location_type")
else:
    loc_type_expr = pl.lit(0)  # all rows default to STOP

# Determine lat/lon missing expressions
lat_missing = pl.col("stop_lat").is_null()  if "stop_lat" in stops.columns
              else pl.lit(True)
lon_missing = pl.col("stop_lon").is_null()  if "stop_lon" in stops.columns
              else pl.lit(True)

offenders = stops.filter(
    loc_type_expr.is_in(_REQUIRED_LOCATION_TYPES)
    & (lat_missing | lon_missing)
)

for row in offenders.iter_rows(named=True):
    emit Notice(
        code="stop_without_location",
        severity=Severity.ERROR,
        fields={
            "csv_row_number": row["csv_row_number"],
            "stop_id":        row["stop_id"],
            "location_type":  row["location_type"] if "location_type" in stops.columns else 0,
        },
    )
```

### Why `iter_rows` is acceptable

The number of offending rows is bounded by the size of `stops.txt`. The
check is inherently row-producing (one notice per row) so the iteration cost
is irreducible. There is no vectorized alternative that avoids constructing
individual `Notice` objects.

### Null semantics

The two-phase loader in `loading.py` casts `stop_lat` and `stop_lon` to
`Float64`. Rows where the raw CSV cell was empty or unparseable result in a
Polars `null` in the typed column. The filter expression `pl.col(...).is_null()`
correctly captures both cases.

### UNRECOGNIZED location_type values

Any integer value not in `{0, 1, 2, 3, 4}` is treated as UNRECOGNIZED and
is not in `_REQUIRED_LOCATION_TYPES`, so those rows produce no notice. This
matches the Java behavior where `GtfsLocationType.UNRECOGNIZED` is excluded
from the required-coordinates check.

## 5. Registry Entry

Add the import alongside the other `stops`-dependent validators at the top of

```python
from gtfs_validator.validators.stop_required_location import (
    validate_stop_required_location,
)
```

Add the entry to `VALIDATOR_REGISTRY` grouped with the other
`requires=["stops"]` entries (after `stop_name`, before or after
`stop_access` — keep the stops group together):

```python
ValidatorEntry(
    name="stop_required_location",
    fn=validate_stop_required_location,
    requires=["stops"],
),
```

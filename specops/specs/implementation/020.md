# Implementation: FeedServiceDateValidator

## 1. Module Location

**Validator:** `src/gtfs_validator/validators/feed_service_date.py`

No new shared utilities are required. The validator reads only
`feed_info.txt` and performs a pure field-presence check with no date
arithmetic and no use of `ValidationContext`.

## 2. Function Signature

```python
from __future__ import annotations

import polars as pl

from gtfs_validator.context import ValidationContext
from gtfs_validator.notices import Notice, Severity


def validate_feed_service_date(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
```

`ctx` is accepted to satisfy the uniform validator signature
`(feed: dict[str, pl.DataFrame], ctx: ValidationContext) -> list[Notice]`
but is not used. No current-date logic or context field access is needed.

## 3. Notice Definitions

### `missing_feed_info_date`

Severity: **WARNING**

Emitted when exactly one of `feed_start_date` / `feed_end_date` is
present in a `feed_info.txt` row. The notice identifies which field is
missing by name so consumers can pinpoint exactly what to add.

```python
Notice(
    code="missing_feed_info_date",
    severity=Severity.WARNING,
    fields={
        "csv_row_number": <int>,    # CSV row number of the offending row
        "field_name": <str>,        # "feed_end_date" or "feed_start_date"
    },
)
```

The `field_name` field takes exactly two possible values:

- `"feed_end_date"` — when `feed_start_date` is present but `feed_end_date` is absent.
- `"feed_start_date"` — when `feed_end_date` is present but `feed_start_date` is absent.

At most one notice is emitted per row. Because `feed_info.txt` is
declared `single_row=True` in `schemas.py`, at most one notice is ever
emitted in practice.

## 4. Implementation Approach

### Skip conditions

```python
if "feed_info" not in feed or feed["feed_info"].is_empty():
    return []
```

No additional row-level skip is needed: the per-row logic already handles
the "both absent" and "both present" cases by emitting nothing.

### Algorithm

For each row in `feed_info.txt`, check field presence and emit at most
one notice per row:

```
for each row in feed["feed_info"]:
    has_start = row["feed_start_date"] is not None
    has_end   = row["feed_end_date"]   is not None

    if has_start and not has_end:
        emit missing_feed_info_date(
            csv_row_number=row["csv_row_number"],
            field_name="feed_end_date",
        )
    elif not has_start and has_end:
        emit missing_feed_info_date(
            csv_row_number=row["csv_row_number"],
            field_name="feed_start_date",
        )
```

The two branches are mutually exclusive. No date arithmetic is performed;
the check is purely about field presence (null vs. non-null).

### Polars implementation

`feed_info.txt` is a single-row table, so `iter_rows(named=True)` is
appropriate and imposes no performance concern. After the two-phase
load, `feed_start_date` and `feed_end_date` are either `datetime.date`
objects or `None` if absent or unparseable.

```python
def validate_feed_service_date(
    feed: dict[str, pl.DataFrame],
    ctx: ValidationContext,
) -> list[Notice]:
    """Warn when feed_info.txt provides only one of feed_start_date / feed_end_date."""
    if "feed_info" not in feed or feed["feed_info"].is_empty():
        return []

    notices: list[Notice] = []

    for row in feed["feed_info"].iter_rows(named=True):
        has_start = row["feed_start_date"] is not None
        has_end   = row["feed_end_date"]   is not None

        if has_start and not has_end:
            notices.append(
                Notice(
                    code="missing_feed_info_date",
                    severity=Severity.WARNING,
                    fields={
                        "csv_row_number": row["csv_row_number"],
                        "field_name": "feed_end_date",
                    },
                )
            )
        elif not has_start and has_end:
            notices.append(
                Notice(
                    code="missing_feed_info_date",
                    severity=Severity.WARNING,
                    fields={
                        "csv_row_number": row["csv_row_number"],
                        "field_name": "feed_start_date",
                    },
                )
            )

    return notices
```

### What is not checked here

The following are handled at load time and must not be duplicated:

- Type validation of `feed_start_date` and `feed_end_date` (valid
  YYYYMMDD strings; load-time casting produces `datetime.date` or null).
- End-range check: `feed_start_date <= feed_end_date` (enforced by
  `load_validators.py` via the `end_range` annotation on `FEED_INFO`'s
  `feed_start_date` column, `er=_ER("feed_end_date", allow_equal=True)`).
- Single-row enforcement for `feed_info.txt` (`single_row=True` in
  `FEED_INFO`).
- Required field presence for `feed_publisher_name`, `feed_publisher_url`,
  `feed_lang`.
- Recommendation hints for both date fields being absent (no notice from
  this validator when both are null; that is a separate concern).

### Schema reference

`FEED_INFO` in `src/gtfs_validator/schemas.py`:

- `feed_start_date`: typed `_DATE` (`datetime.date` after load), annotated
  `_REC` (recommended), with `er=_ER("feed_end_date", allow_equal=True)`.
- `feed_end_date`: typed `_DATE`, annotated `_REC`.
- `csv_row_number`: injected by the loader as `Int64` on every loaded table.

No schema changes are needed.

## 5. Registry Entry

In `src/gtfs_validator/validators/__init__.py`, add the import with the
other `feed_info`-dependent validators:

```python
from gtfs_validator.validators.feed_service_date import validate_feed_service_date
```

Append the entry to `VALIDATOR_REGISTRY` after the existing
`feed_expiration_date` entry to keep `feed_info`-dependent validators
grouped together:

```python
ValidatorEntry(
    name="feed_service_date",
    fn=validate_feed_service_date,
    requires=["feed_info"],
),
```

All tests construct minimal `feed` dicts with Polars DataFrames and call
`validate_feed_service_date` directly. The `ctx` fixture uses an
arbitrary fixed date since this validator does not use it.
